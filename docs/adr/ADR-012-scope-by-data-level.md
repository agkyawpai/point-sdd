# ADR-012: Permission scope follows the data level — company master · branch data · shared records (amends ADR-011 #7) · Amendment 1: private level

**Status:** Accepted — owner 01/Oct/2026 (question 22:16 "Manager က သူ့ Branch မှာရှိတဲ့ Service တွေ Setting တွေကို Manage မလုပ်နိုင်ဘူး ဖြစ်သွားမှာပေါ့ …" → choice **A — "Scope က အဆင့် ဆုံးဖြတ်"**). **Supersedes ADR-011 #7 in part** (the sentence "a code declared `company` is effective only through a company-scope assignment") and ADR-011 action item 1 (`scope` field → `level`). Everything else in ADR-011 stays. **Amended in place — [Amendment 1](#amendment-1-02oct2026--owner-one-sheet-c1--e6--f10--f11) (02/Oct/2026 — owner one-sheet "အကုန်လုံး OK" 00:06, items C1 / E6 / F10 / F11):** a fourth level **`private`** (company-only data — a branch-scope grant reaches nothing, not even read-only), **company-wide money rows** and the **company P&L** need company scope (API Part 7), **audit rows** without a branch / pay rows / staff-document rows need company scope (API Part 8); status stays **Accepted**. Marked **[A1]** below.
**Date:** 01/Oct/2026 · Amendment 1: 02/Oct/2026 (+ fix-up 02/Oct: staff-advance taker private — A1-1 · review fixes 02/Oct — independent review R1-6 / R2-3 / R3-6 / R3-9: **`receivable.issue` is private → 18 private codes**; backup and import reads need company scope; `site.*` keys written only through P8.WEB.02 · reconcile 02/Oct: staff-advance taker = company-scope `payroll.view` or `receivable.issue`; an `audit.view` holder always sees their own rows; employee-targeted rows carry the employee's primary branch — A1-1 / A1-3)
**Deciders:** Owner (decided) · dev team

> **မြန်မာ အတိုချုပ်** — Permission ✔ တစ်ခုက **ဘယ်အထိ ရောက်လဲ** ကို **data အဆင့်** က ဆုံးဖြတ်တယ် (code နာမည်က မဟုတ်)။ Data ၃ မျိုး —
> (1) **Company master** (company တစ်ခုလုံး တစ်ခုတည်း — service နာမည် / category / option, role, leave type, cancel reason, company setting တန်ဖိုး, branch အသစ် ဖွင့် / ပိတ်) → **ပြင်ခွင့် = company scope ✔ ရှိမှ**; branch scope နဲ့ ✔ ထားရင် **ကြည့်ရုံ (read-only)**။
> (2) **Branch data** (branch တစ်ခုချင်း — ဒီ branch မှာ ဒီ service ရောင်း / ကြာချိန်, ဈေး, eligibility, schedule, ခွင့်, booking, branch setting override, branch profile, ဝန်ထမ်း) → **ကိုယ့် scope ထဲက branch ပဲ**။
> (3) **Shared record** (customer — company တစ်ခုလုံး မျှသုံး) → ✔ ရှိရင် branch scope ဖြစ်ဖြစ် ရ; ဒါပေမဲ့ **booking / sale history ကတော့ ကိုယ့် branch ပဲ** မြင်။
> ဥပမာ — Admin က "Hair Dye" service ကို company တစ်ခုလုံးအတွက် ဖန်တီး → Branch A Manager (`service.update`, branch scope = A) က **A မှာ ရောင်း / မရောင်း + ကြာချိန်** ကို ပြင်ရ; service နာမည် / option / B branch ကို **မပြင်ရ** (screen မှာ read-only)။ Setting လည်း အတူတူ — Manager က A ရဲ့ branch override (ဥပမာ ကားခ) ပြင်ရ; company တန်ဖိုး (ဥပမာ slot interval) ကြည့်ရုံ။ D-ROLE-07 ("Manager = assigned branches, company-wide မရ") နဲ့ ကိုက် — company master ကို ပြောင်းတာ company scope ပဲ ရ; **ချွင်းချက် = customer** (shared — `customer.update` ✔ ရှိရင် branch scope နဲ့လည်း customer row တစ်ခုတည်းကို ပြင်ရ, branch အကုန် မြင် — D-CUS-01; seed မှာ `customer.delete` = Admin ပဲ)။
> **[A1] ပြင်ဆင်ချက် ၁ (02/Oct — owner C1 / E6 / F10 / F11):** အဆင့် (၄) **Private** ထပ်တိုး — **လစာ / commission / advance (ထုတ်ပေး / ပြင် / ပြန်ဆပ်မှတ် / ဖျက် — `receivable.issue` ပါ; review ပြင်ဆင်ချက် 02/Oct) / payroll category / report ⑦ / ဝန်ထမ်း document** = company scope ✔ ရှိမှ **ကြည့်ရ၊ ပြင်ရ**; branch scope နဲ့ ✔ ထားရင် **ဘာမှ မရ** (ကြည့်ရုံတောင် ✖ — company master လို read-only မဟုတ်)။ **Branch မပါတဲ့ ငွေ row** (company တစ်ခုလုံး expense / income) နဲ့ **company P&L** = company scope ပဲ — Manager က ကိုယ့် branch P&L ပဲ (လစာ = စုစုပေါင်း တစ်ကြောင်း — E6)။ **Audit log** — branch မပါတဲ့ row = company scope; လစာ row = company scope `payroll.view`; ဝန်ထမ်း document row = `employee.documents` (F10 / F11)။

## Context
- 🔒 D-ROLE-03 (permission AND branch scope), D-ROLE-05 (scope per assignment), D-ROLE-07 (Admin = company-wide + branch; Manager = assigned branches, no company-wide), D-SVC-01 / 02 (company master service, per-branch sale / price / duration), D-CUS-01 (company-level customer), D-PLT-16 (settings: company value + branch override per key).
- ADR-011 #7 (01/Oct 21:20) declared every code `company` or `branch` and ignored a `company` code granted through a branch-scope assignment. Applied to Part 1 / 2 this made `service.*` and `settings.view` company-only, so a branch Manager could not decide what *their* branch sells or change *their* branch's settings — and Part 2 put the per-branch sale switch (P2.SVC.06) under the company-only `service.update`.
- Owner, 01/Oct 22:16: a Manager must manage their branch's services and settings; the earlier intent was "the admin creates a company-wide service, then each branch has it or not" — guard the company-wide part, not the branch part. The owner chose **A — the data level decides** (alternatives below).
- The DB already separates the levels: company master rows carry `company_id` (D-ORG-03 #2: roles, services, categories, leave types, cancel reasons, company settings rows); branch data carries `branch_id` (`branch_services`, `service_prices`, `employee_service_eligibilities`, `schedule_*`, `bookings`, branch settings rows); customers are company rows used by every branch (D-CUS-01) whose history lives in branch tables.
- **[A1] 02/Oct/2026 — owner one-sheet (items C1 / E6 / F10 / F11, "အကုန်လုံး OK" 00:06):** pay data (payroll, salaries, advances / loans, commission plans) is **Admin only — a Manager may not even look at it with branch scope** (C1); a Manager sees their branch P&L with salary as **one total line** (E6); managers never see pay changes in the audit log (F10); staff documents are a separate code, Admin only (F11). Neither original level fits: as *company master* a branch-scope grant would still read pay data; as *branch data* a Manager would see their branch's salaries. API Parts 5 / 7 / 8 (🔒 D-API-06 / 08 / 09) were written against cross-part contract 1 ("ADR-012 amendment") — see [Amendment 1](#amendment-1-02oct2026--owner-one-sheet-c1--e6--f10--f11).

## Decision
1. **Every endpoint target has a data level, and the guard checks the grant against it** (API-PERM-02 v1.4, API-PERM-07):

   | Data level | Examples | A **write** passes when … | A **read** (management, `view⁺`) |
   | --- | --- | --- | --- |
   | **Company master** | company profile · branch create / deactivate · roles · service categories, service master fields, options, order, archive · leave types · booking cancel reasons · company setting values · maintenance mode | the caller holds the code through a **company-scope** assignment | any grant of the module (any scope) — **read-only** for branch-scope holders |
   | **Branch data** | a branch's own profile · per-branch sale + duration (`branch_services`) · prices · eligibility · patterns / shifts · leave on behalf / approve · employees (P1-RULE-11 target set) · role assignment · branch setting overrides · bookings | the grant's scope **covers the target branch** (company scope covers all); a request touching several branches needs every one of them | filtered to the grant's branches |
   | **Shared record** | customers (D-CUS-01) | the caller holds the code through **any** active assignment | the record is visible; **branch-attached history inside it** (bookings, visits, sales, statistics) is filtered to the caller's **read scope** (P1-RULE-05) |
   | **Private** [A1] | pay data — commission plans / assignments / preview, payroll runs / entries / admin payslips, salaries, allocation shares, payroll categories, receivable reads, balances **and writes (`receivable.issue` — review fix 02/Oct)**, report ⑦ — and staff documents (owner C1 / F11) | the caller holds the code through a **company-scope** assignment — else 403 `company_scope_required` | **company scope only** — a branch-scope grant reaches **nothing** (not even read-only); lists answer 403 too (there is no branch slice of private data) |
   | **Company-wide money rows** [A1] | expenses / manual incomes with `branch_id` NULL, the **company P&L** (API Part 7) | a **company-scope** grant of the (mixed) code — else 403 `company_scope_required` | company scope only — for branch scope they are **left out** of lists and a single read answers 404 (unlike company master, branch scope does not read them) |

   **[A1] Audit rows** (API Part 8, owner F10): `audit.view` is a branch-level code, but rows **without a branch** need company scope (a holder's own rows are always visible to them), **pay rows** need company-scope `payroll.view` and **staff-document rows** company-scope `employee.documents` (Amendment 1, A1-3).

2. **Each code declares a `level`** in `permissions.json` (replaces ADR-011's `scope`): `company` (acts only on company master), `branch` (acts only on branch data), `mixed` (acts on both — the endpoint decides per request; Parts 1–3: `service.view`, `service.update`, `settings.view`, `settings.update`; **[A1]** Parts 4–8 add `discount.view`, `expense.*`, `income.*`, `pnl.view`, `website.view`, `website.update`, `data.export`), `shared` (`customer.*`), **[A1] `private`** (company scope only — the 18 codes of A1-1). The level drives the role-matrix hint (AD-PERM-07 v1.4; *Private* hint — A1) and the client `can(code, { branchId?, level? })` helper; the server always decides by the endpoint's target.
3. **A branch-scope grant of a company-level code is not ignored any more** — it gives read-only access to that module's company master (the menu opens, controls are hidden — AD-PERM-02) and nothing else. **Exception (review fix 02/Oct — R3-6):** for `import.run`, `backup.view` and `backup.restore` the **reads need company scope too** (Part 8 P8.IMP.01–08, P8.BAK.01 / 02 — import files hold every branch's data, backup runs are system-wide state; same as the jobs panel P1.SYS.05) — API-PERM-03 / 07. A write attempt answers **403 `company_scope_required`** (new error code, API-ERR-02). **[A1]** This read-only rule does **not** apply to `private` codes — a branch-scope grant of a private code gives no access at all.
4. **Mixed endpoints decide per request:** P1.SET.03 / 04 without `branch_id` = company value (company scope), with `branch_id` = branch override (branch covered, key must be branch-overridable — else 400 `setting_scope`); P2.SVC.06 checks **each item's branch** (all must be covered); P2.SVC.01 `sold=all` answers only for a `branch_id` the grant covers (else an empty page).
5. **Guard rails unchanged** (ADR-011 #6): company admin = company-scope assignment of a role with all five role codes; no escalation (a non-admin grants only codes **and scopes** they hold); last-admin lockout; new codes auto-granted to company-admin roles. Maintenance mode stays company-scope `settings.update` (API-AUTH-06).
6. **Seeds follow the levels** (D-ROLE-09, ★ owner reviews before go-live): Manager seed regains `service.view` + `service.update` (their branches' sale / duration; master read-only) and `settings.view` + `settings.update` (their branches' overrides; company values read-only). Admin = every code, company scope. Barber unchanged. **[A1]** The Manager seed holds **no private code** (Parts 5 / 8 — owner C1 / F1 / F11).

## Amendment 1 (02/Oct/2026 — owner one-sheet C1 / E6 / F10 / F11)

*Status unchanged — Accepted. Source: owner one-sheet "အကုန်လုံး OK" (02/Oct/2026 00:06) + cross-part contract 1 of API Parts 4–8; applied in API Part 5 P5-RULE-01 / 18, Part 7 P7-RULE-01 / 17, Part 8 P8-RULE-01 / 05 / 06 (🔒 D-API-06 / 08 / 09); Part 0 API-PERM-02 / 03 / 06 #5 / 07 take the same wording (v1.5).*

**A1-1 · New level `private` (company-only data).** Read **and** write need the code through a **company-scope** assignment. A branch-scope grant of a private code reaches **nothing** — no read-only view (unlike company master, Decision #3), the menu stays hidden, and **lists answer 403 `company_scope_required` as well** (a private list is not scope-filtered: there is no branch slice of it — an exception to API-PERM-03 "lists never 403"). Decorators `@Can(code, { level: 'private' })` and `@CanView(module, { level: 'private' })`.
- **Private codes (18 — 17 in the first text of this amendment + `receivable.issue`, review fix 02/Oct):** Part 5 — `commission.view` · `commission.create` · `commission.update` · `commission.delete` · `commission.assign` · `payroll.view` · `payroll.create` · `payroll.update` · `payroll.delete` · `payroll.finalize` · `payroll.pay` · `payroll_category.view` · `payroll_category.create` · `payroll_category.update` · `payroll_category.delete` · **`receivable.issue`**; Part 8 — `report_commission_payroll.view` (report ⑦) · `employee.documents` (staff documents — owner F11). Seed: Admin only.
- **Private data and the code that opens it:** salary history and scheduled changes, branch-allocation shares, **receivable (advance / loan) reads and balances**, the payroll outstanding list, admin payslips → `payroll.view⁺`; commission plans, assignments, preview → `commission.view⁺`; payroll categories → `payroll_category.view⁺` or `payroll.view⁺`; report ⑦ → `report_commission_payroll.view`; staff-document attachments → `employee.documents` (every URL audited — ADR-014); **SALARY-category and payroll (source 3) expense rows** in Part 7 → company-scope `payroll.view` (everyone else gets them excluded from lists, 404 on a single read, and sees salary in the P&L as **one total line** — owner E6).
- **Staff advance taker (fix-up 02/Oct — owner C1 + D-FIN-06):** a drawer advance / loan (Part 7 cash out of type 2 EMPLOYEE_BALANCE) keeps its **amount and reason** as branch data — `cashout.view⁺` / `closing.view⁺` readers need them for the cash count — but **the taker of a staff advance is shown only to payroll viewers**: the employee, the note (= the receivable's reason) and the receivable link go to company-scope holders of `payroll.view` **or** `receivable.issue` (both private, Admin seed — reconcile 02/Oct: the code that records, edits and cancels the advance also shows whose it is) and the employee themself; everyone else gets `employee: null` + `employee_hidden: true` ("Staff advance") — in the cash-out list / read, the closing movements, report ⑤ and exports; its audit rows count as **pay rows** (A1-3) (Part 7 P7-RULE-01, Part 8 P8-RULE-06 / 15).
- **`receivable.issue` is private** (review fix 02/Oct — independent review R1-6, owner C1 + C2; the first text of this amendment made it a branch-level special code with only the *reads* private): its endpoints — issue, change, cash repayment, cancel (Part 5 P5.RCV.03–06) — return the full receivable with balance and repayments, which owner C1 keeps from branch managers, so a branch-scope grant now reaches nothing (403 `company_scope_required`). Seed unchanged: Admin only (owner C2). Editing or cancelling a **staff-advance cash out** in Part 7 needs it too, next to `cashout.update` / `cashout.delete` (R2-3 — creating one already did).
- **Not private:** attendance (`attendance.*`, `attendance_qr.*`) is branch data; own data (own payslips, own advances, *My earnings*) stays `@Self()` with no code (API-PERM-04).

**A1-2 · Company-wide money rows and the company P&L need company scope** (Part 7 P7-RULE-01 / 17). Expenses and manual incomes with `branch_id` NULL and the P&L without `branch_id` are read and written only through a **company-scope** grant of the mixed code (`expense.*`, `income.*`, `pnl.view`). For a branch-scope holder: lists leave them out (the `company_wide` filter is ignored), a single read answers 404, a write 403 `company_scope_required`. Branch-scope `pnl.view` = the P&L of the covered branches only, salary as one total line (owner E6). Decorator: an optional branch path whose empty value is private — `@Can('expense.create', { branch: 'body.branch_id?', empty: 'private' })`.

**A1-3 · Audit rows** (Part 8 P8-RULE-06 — owner F10 / F11). `audit.view` is a **branch**-level code (Manager seed — 🔒 D-AUD-01 "manager = assigned branches") with three row rules: rows **without** a `branch_id` (roles, company settings, company master, logins, branch create, multi-branch purchases …) need **company scope**; **pay rows** (payroll / commission / salary / receivable tables and `payroll.` · `payroll_category.` · `commission.` · `salary.` · `receivable.` actions, source-3 or SALARY-category expenses, EMPLOYEE_BALANCE cash outs) need company-scope **`payroll.view`** (EMPLOYEE_BALANCE cash-out rows: `payroll.view` **or** `receivable.issue` — reconcile 02/Oct); **staff-document rows** need company-scope **`employee.documents`**. **Own rows (reconcile 02/Oct):** a holder always sees the rows they authored themselves (`actor_user_id` = caller) in addition to the rows of their branches — private rows keep their own rule; an employee-targeted action carries the acted-on branch, else the employee's primary branch (earliest active assignment), NULL without one (Part 0 API-AUD-01). Hidden rows are left out of lists (no count leak) and a single read answers 404. Decorator `@Can('audit.view', { branch: 'row' })` (row-level filter).

**A1-4 · Level notes from Parts 4–8 (no further level).** New **mixed** codes: `discount.view` (codes read-only at branch scope, requests per branch — Part 4), `expense.*` / `income.*` (branch rows + company-wide rows A1-2 — Part 7), `pnl.view` (Part 7), `website.view` / `website.update` (company scope = the whole site, branch scope = own branches' hours / closures, no twin code — owner F7, Part 8), `data.export` (never alone — always on top of the source's own read right and with the same scope — owner F2, ADR-015). **Two-branch and multi-line records** (stock transfers, purchases per line — Part 6): a **read** passes when the grant covers **any** of the record's branches (`'entity.from_branch_id|entity.to_branch_id'`, `entity.items[].branch_id`); **writes keep "every branch touched"** (Decision #1). Settings of module `website` (`site.*` — company values only, never branch-overridable) are written **only through P8.WEB.02** with **company-scope `website.update`** — P1.SET.03 / 04 are read-only for these keys (400 `setting_scope`), so no endpoint picks its code by key (Part 8 P8-RULE-11, review fix 02/Oct — R3-9; Decision #4 otherwise unchanged).

## Options Considered

### Option A: Data level decides (chosen)
| Dimension | Assessment |
|-----------|------------|
| Complexity | Medium — each endpoint names its level; mixed endpoints check per request / per item |
| Cost | No new codes; matrix unchanged except a level hint |
| Scalability | Every later part classifies its targets with the same three levels |
| Team familiarity | High — mirrors the DB (`company_id` vs `branch_id` rows) |

**Pros:** what the owner asked; one code per action keeps the matrix small; the Manager can run their branch without touching company master data (D-ROLE-07); customers stay shared (a `customer.update` holder at any scope edits the one company row — by design, D-CUS-01) while history stays private to each branch.
**Cons:** "same code, different reach" must be explained in the matrix (hint per level) and tested per level.

### Option B: Separate branch codes (`service.branch_update`, `settings.branch_update` …)
| Dimension | Assessment |
|-----------|------------|
| Complexity | Low per endpoint |
| Cost | More rows / special-action boxes in the matrix |
| Scalability | Every company module would need a twin code |
| Team familiarity | High |

**Pros:** explicit. **Cons:** doubles codes for several menus and splits one menu over two matrix rows; not the owner's choice.

### Option C: Keep ADR-011 #7 (company code only through company scope)
**Cons:** a branch Manager cannot manage their branch's services or settings — rejected by the owner (22:16).

### Option D: A branch-scope grant of a company code acts company-wide
**Cons:** a branch Manager could rename services or change company settings for every branch — contradicts 🔒 D-ROLE-07.

## Trade-off Analysis
- **Reach vs. simplicity.** A keeps one code per action (CRUD matrix stays readable — ADR-011) and moves the "how far" question to data the system already knows (which table, which branch). The cost is a per-endpoint level declaration that the lint rule checks (API-PERM-02).
- **Shared customers.** A company-level customer must be findable from every branch (D-CUS-01 / 03 auto-match), but one branch's history is not another branch's business — the shared level gives exactly that split.

## Consequences
- Easier: Manager seed works as the owner expects; Part 3 customers fit without exceptions; later parts (website hours per branch, stock per branch, closing per branch) need no twin codes.
- Harder: tests per level (company write refused for branch scope with `company_scope_required`; per-item branch checks; shared-record history filtering); the matrix explains levels.
- Revisit when: a module needs a *different* branch actor than its company actor (e.g. a branch may edit some master fields) — then add a field-group special code (ADR-011 #2) rather than widening the level.
