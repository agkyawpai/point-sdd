## 1. Rules specific to this part

**P3-RULE-01 · One customer identity function.** 🔒 D-CUS-02/03, F-BK-21 + owner #7. `matchOrCreateCustomer(phone, name, actor)` is the only way a booking (staff or public) or a walk-in FINISH (Part 4) finds its customer: normalise the phone to E.164 (API-DATA-06; a leading `0` = Myanmar +95; else 400 `phone_invalid`), then `INSERT … ON CONFLICT (company_id, phone_normalized) DO NOTHING` + `SELECT … FOR UPDATE` (so two first-time bookings for one phone never create two rows). Found **archived** → restored (`archived_at = null`, `status = 1`, audit `customer.restore`, `warnings[]` `customer_restored`); found **INACTIVE** → `status = 1` (audit `customer.reactivate`, `warnings[]` `customer_reactivated`); not found → created with `name` = the name typed (audit `customer.create`, actor = the booking creator or `system` for an online booking). The customer's own `name` is never overwritten by a booking (F-BK-19 — the booking keeps its own `customer_name`). Creating a customer this way needs **no** `customer.create` code (D-CUS-03 "auto"); the explicit *Add customer* screen does (P3.CUS.03).

**P3-RULE-02 · Customer status, archive, visibility.** 🔒 D-CUS-07/09 + owner #7. `status` 1 ACTIVE / 0 INACTIVE; `archived_at` = soft delete. **Inactive** = hidden from P3.CUS.01 by default (`status` filter shows it), still matched by phone (P3-RULE-01 re-activates it), never blocks a booking — the website included. **Archive** (P3.CUS.07) hides the row everywhere except `include_archived=true`; it is refused while the customer has a BOOKED / STARTED booking (409 `customer_has_active_bookings { count }`); the phone stays reserved (unique incl. archived — F-BK-21) and comes back through P3-RULE-01 or P3.CUS.08. No merge, no hard delete, no e-mail field (D-CUS-02/05, D-DAT-05).

**P3-RULE-03 · Shared record, branch history.** 🔒 D-CUS-01 + ADR-012 (shared level) + owner #9. Every `customer.*` code works through **any** active assignment (a Barber with branch scope sees every customer — one company list, D-CUS-01). What hangs **inside** the customer — bookings, visits, sales, refunds, statistics, timeline, upcoming bookings — is filtered to the caller's **read scope** (P1-RULE-05; company scope = everything). Statistics (AD-CUS-02, computed, never stored — D-CUS-07): `visit_count` (FINISHED visits whose sale belongs to the customer — Part 4), `total_spent_amount` (Σ FINISHED `sales.total_amount` − Σ kind-1 `refunds.amount`), `last_visit_at`, `no_show_count` (bookings cancelled with the system NO_SHOW reason — by the timer or by staff, owner #3; history only, never a restriction — D-CUS-09), `cancelled_count`, and **`preferred_employee`** (🔒 D-CUS-08 + owner #6): among the customer's last `customer.preferred_barber_window` (5) FINISHED visits, the `performed_by_employee_id` with ≥ `customer.preferred_barber_min_visits` (3); if the settings ever allow two (e.g. 2 of 5), the one with more visits, then the most recent; otherwise `null` ("–").

**P3-RULE-04 · Booking create — one pipeline for staff and public.** 🔒 D-BKG-03..12, 21..23, D-SVC-04..08, ADR-004 + ⚠️ order. Steps 1–2 run before the DB transaction (no network call — Turnstile — is ever made inside it); steps 1 (again) and 3–8 run inside one transaction:
1. **Token / replay** (API-IDEM-03): `manage_token` = 43 characters base64url (32 random bytes) else 400 `validation`. The token hash is looked up first (a cheap read, so a replay never needs a captcha) and **again inside the transaction under `pg_advisory_xact_lock` on the hash** (so two concurrent submits of one token are serialised): if `sha256(token)` already exists → same identifying fields (`branch_id`, `booked_employee_id`, `starts_at`, `phone_normalized`) → **200** + `Idempotent-Replayed: true` + the booking and `manage_url` (no captcha / rate-limit check on a replay — a Turnstile token is single-use, the retry carries a new one or none); different → 422 `idempotency_mismatch`. A unique violation on `manage_token_hash` at insert (23505) is mapped back to this lookup, never to `slot_taken` / `active_booking_exists`.
2. **Public only** (P3-RULE-10): IP attempt limit (before Turnstile), honeypot, Turnstile, phone attempt limit, ≤ `booking.public_max_services` items, branch **ACTIVE** (a branch with `is_public = false` is accepted — P3-RULE-10; review fix 02/Oct).
3. **Items and date** — the Part 2 checks in this order: items (`service_inactive`, `category_inactive`, `not_sold_here`, `variant_required` — 422 with `errors[]`), HOME needs `home_address` (422 `home_address_required`) and BRANCH must not carry `home_address` / `home_address_note` (400 `validation` — DB `bookings_home_chk`), date inside the window (422 `outside_window` — public **and** staff, D-BKG-06), closure (422 `date_closed`), barber assigned + eligible for every item on the date (HOME → `home_allowed`) (422 `not_eligible` / `not_assigned_to_branch`).
4. **Customer** — P3-RULE-01 (the customer row stays locked `FOR UPDATE` until commit).
5. **Price** — the Part 2 quote in-process (P2-RULE-05) for `business_date` (= MMT date of `starts_at`), the barber and the location → snapshot per item (`unit_price_amount`, `duration_minutes`, `buffer_minutes`) + `transport_fee_amount` (HOME — branch setting `home_service.transport_fee_amount` at create time, default **0** = the shop pays (D-SVC-06; never null for HOME); null for BRANCH). If the request carries `expected_total_amount` (required on the public API) and the computed total differs → 409 `price_changed` with the new quote (the screen shows the new price before the customer confirms — D-BKG-12 spirit, FE-BK-10).
6. **Slot** — the Part 2 availability function in-process (P2-RULE-10) for that barber and date: `starts_at` must be one of the offered slots (on the grid, after now, block inside one free interval incl. buffer and HOME travel); otherwise 409 `slot_taken` with `next_free` (≤ 3 nearest free starts for the same barber — AD-CAL-05, FE-BK-11).
7. **One active booking — public only, checked last** (after price and slot pass, so a probe with a wrong price or a taken slot learns nothing — P3-RULE-10): with the customer row still locked, any BOOKED / STARTED booking of that customer (any channel) → 422 `active_booking_exists` with **no details** (🔒 D-BKG-09 — staff bookings are never limited, AD-BKG-06).
8. **Insert** `bookings` (BOOKED, `channel` 1 ONLINE / 2 STAFF, `created_by_user_id` for STAFF, block times — P3-RULE-05, `manage_token_hash`) + `booking_items` (`sort_order` = request order). The DB EXCLUDE is the last line (🔒 D-BKG-08 first success wins → 409 `slot_taken`).
9. **After commit:** realtime `booking.created`, notification `booking.new` to the booked barber when someone else created it (D-BKG-23, AD-TODAY-04), no-show jobs (P3-RULE-08), audit `booking.create`. Response **201** `Booking` / `PublicBooking` + **`manage_url`** (`<site origin>/booking/<token>` — built from the raw token received; never stored, never logged) + **staff only** `warnings[]` (`customer_restored`, `customer_reactivated`, `customer_has_upcoming_booking { starts_at }` — AD-BKG-06 info note); the public response never says whether the phone was known.

**P3-RULE-05 · Snapshot and block.** 🔒 D-SVC-04/07, D-SCH-03, F-BK-16, Part 2 §16 #1. `ends_at = starts_at + Σ duration_minutes`; `block_starts_at = starts_at − travel` and `block_ends_at = ends_at + Σ buffer_minutes + travel`, where `travel = home_service.travel_minutes` (branch setting, **read at create and when the location changes to HOME**; otherwise the booking's own travel `starts_at − block_starts_at` is reused — F-BK-16 snapshot) for HOME and 0 for BRANCH; `business_date` = MMT date of `starts_at` (DB CHECK). Totals are computed, never stored: `subtotal_amount = Σ unit_price_amount`, `total_amount = subtotal + transport_fee_amount`. Service names are joined from `services` (no name snapshot — F-BK-18); the sale (Part 4) snapshots names for the receipt.

**P3-RULE-06 · Reschedule = full edit, priced by D-BKG-12.** 🔒 D-BKG-12/13/15 + owner #10. Only a **BOOKED** booking (else 409 `invalid_transition`). The body may change `starts_at`, `booked_employee_id`, `location_type` (+ address), and `items`; the **branch** never changes (the request has no branch field — to move branch, cancel and book again) and neither do the phone / customer (owner #10 — a wrong number = cancel with "Other" + a new booking). Items are matched by `booking_item_id`: an item sent with its id and the same service + variant is **kept**; with its id and another variant / service = **changed**; without an id = **added**; an existing id not sent = **removed**. Pricing:
- **barber or location changed → every item repriced** for the new date (barber override / HOME prices — D-SVC-03/06; durations from the quote — P2-RULE-03) and the transport fee re-read (HOME; HOME → BRANCH nulls `home_address`, `home_address_note`, `transport_fee_amount` — DB `bookings_home_chk`);
- otherwise **changed / added items repriced**, **kept items keep their price, duration and buffer** (even if prices or durations changed since — D-BKG-12 "time only = original price"), transport fee kept. Kept items skip the active / sold / price checks (a service deactivated since must not block a time-only move — D-BKG-19) but the barber must still be assigned and eligible for them on the new date;
- `price_change.reason` = `barber_or_location_changed` · `items_changed` · `time_only`.
The availability check (P3-RULE-04 #3, #6) runs with this booking excluded and with the kept items' **snapshot** durations and the reused travel (so a time-only move needs exactly the old block length). `POST …/reschedule/preview` (staff P3.BKG.07, public P3.PUB.10) returns the proposed booking, per-item `repriced` + reason, old → new totals and `available` without writing; the confirm call may send `expected_total_amount` (required on the public API) → 409 `price_changed` if it moved. Kept / changed rows are updated in place (`sort_order` renumbered in two steps — first `+ 1000`, then the final 1..n — because of the unique `(booking_id, sort_order)` index), added rows inserted, **removed rows deleted** — 🔒 **owner A2** (02/Oct/2026 00:06 — §13 #2, D-DAT-05 reading): the items of a BOOKED booking are its plan (nothing references them before START — Part 4), and the full before / after goes to the audit diff (`booking.reschedule`). The reschedule-availability endpoints (P3.BKG.11/12, P3.PUB.08/09) take `keep=<booking_item_id>` (kept item) and `item=<service_id>[:<variant_id>]` (new / changed items): **neither sent = all current items kept; otherwise exactly the listed items**; `employee_id` and `location_type` default to the booking's current values; when either differs from the booking every item is priced and timed by the quote (as the confirm will) — so the date strip and slots match what the confirm checks. After commit: `booking.updated` (old and new barber), notification `booking.rescheduled` to the booked barber(s) unless they did it themselves (D-BKG-15), no-show jobs replaced (P3-RULE-08).

**P3-RULE-07 · Cancel.** 🔒 D-BKG-14/16, D-BKG-21 + owner #3. Only a **BOOKED** booking (STARTED → the visit is marked INCOMPLETE in Part 4; CANCELLED is final — 409 `invalid_transition`). Body `{ reason_id, note? }` (API-DATA-11): the reason must be active and non-archived; `requires_note` → `note` required (400 `reason_required`). The **system NO_SHOW reason** (`system_code` 1): **staff only**, any time while BOOKED — owner #3: when the customer does not come (or phones to say they won't), staff cancel at once with it so the slot re-opens before the 40 minutes, and it counts in the no-show history (D-CUS-09); **customers never see or use it** (422 `reason_not_allowed` — FE-MNG-04). An inactive or archived reason → 422 `reason_not_allowed` too. Writes `status 0`, `cancelled_at`, `cancel_reason_id`, `cancel_note`, `cancelled_by_actor` (1 CUSTOMER via the link · 2 STAFF · 3 SYSTEM no-show timer) and `cancelled_by_user_id` (STAFF). After commit: `booking.cancelled`, notification `booking.cancelled` to the booked barber unless they did it (D-BKG-15; AD-TODAY-04 "Cancelled by customer"), pending no-show jobs become no-ops, audit `booking.cancel`.

**P3-RULE-08 · No-show timer.** 🔒 D-BKG-17 + owner #2 / #3 + ADR-002. On create / reschedule the API enqueues, in the same transaction, `booking.noshow_alarm` at `starts_at` and `booking.noshow_autocancel` at `starts_at + 40 min`, with data `{ booking_id, starts_at, snooze_seq }`. **Jobs are never replaced or de-duplicated by key** (pg-boss `singletonKey` would silently drop the new job while an old one is queued): every job re-checks under the booking row lock (P3-RULE-09) that the booking is still BOOKED, that `starts_at` equals its data and (alarm) that `snooze_seq` is current — a stale job is a no-op. **Alarm recipients** (owner #2 — "the booked barber + that branch's manager") = the booked barber + users holding `booking.update` **through a branch-scope assignment that lists the branch**, + company-scope holders **who are assigned to that branch (`employee_branches`) on that date** — so an Admin is alarmed only for the branch they work at, not for every booking of every branch: realtime `booking.noshow_alarm` to their `user:` rooms + notification `booking.noshow_alarm` (AD-BKG-09). **Snooze** (P3.BKG.10 — booked barber or `booking.update`): silences the alarm and re-schedules it 10 minutes later, at most **4** snoozes per booking (422 `snooze_limit`); the count = the `booking.noshow_snooze` audit rows of the booking for its current `starts_at` (append-only, survives job archiving) — no DB column; the new alarm job carries `snooze_seq = count`; the 4th snooze silences until the auto-cancel. Without a snooze the alarm card simply stays (no repeated pushes). **Auto-cancel** at +40: P3-RULE-07 with the NO_SHOW reason, actor 3 SYSTEM; a later arrival is a walk-in (Part 4). **Manual no-show cancel** = P3.BKG.09 with the NO_SHOW reason (owner #3). START (Part 4) ends the timer (status 2). **Closures (review fix 02/Oct — R3-22, owner F8):** both jobs also re-check, under the same row lock, whether the booking's `business_date` lies inside a **non-archived `branch_closures` range of its branch**; if it does, the job is a **no-op** — no alarm, no auto-cancel. A closure saved over existing bookings never cancels them (Part 8 P8-RULE-12): they are listed in the closure response and in P2.SHF.07 (`branch_closed`), and staff phone the customer and reschedule or cancel (P3.BKG.08 / 09 — the no-show reason stays available by hand). For such a booking `Booking.noshow` is `null` and P3.BKG.10 answers 422 `noshow_too_early` (no alarm ever fires). The check is made when the job runs, so a closure created after the booking counts, and a future closure archived before the booking's time restores the normal timer.

**P3-RULE-09 · Status ownership.** 🔒 D-BKG-18, D-DB-08 (F-P4-13). Part 3 writes only 1 BOOKED (create) and 0 CANCELLED (cancel / no-show). **Part 4** writes 2 STARTED (`POST /v1/visits { booking_id }` — the booking's items become the visit's planned lines) and 3 COMPLETED (sale FINISHED or visit INCOMPLETE). Reschedule, details edit, cancel and snooze need BOOKED (409 `invalid_transition` otherwise). **Every writer — staff and public endpoints, the no-show jobs and Part 4 START — first locks the row** (`SELECT … FROM bookings WHERE id = $1 FOR UPDATE`) and re-checks `status = 1` (jobs also `starts_at`), so an auto-cancel can never cancel a booking that START has just started, a reschedule can never rewrite a cancelled booking, and START never copies `booking_items` that a reschedule is replacing (a job that loses the race is a no-op; an endpoint answers 409 `invalid_transition`). A booking is never reactivated (D-BKG-16) and never deleted (D-DAT-05). **v1.1 (Part 4 — owner B4, P4-RULE-02 / 05 / 10 / 11):** at START the booking's items become SERVICE lines priced from the booking snapshot when the performer is the booked barber; when the **performer ≠ the booked barber**, each line costs the **lower** of the booking snapshot and the actual performer's quote on the booking date (`warnings[] booked_price_kept` / `performer_price_lower`). START emits **`booking.started`**; FINISH (P4.SAL.10) and INCOMPLETE (P4.VIS.06) set 3 COMPLETED and emit **`booking.updated`** (status 3) to the branch and the booked barber (§8; payloads — Part 4 §10).

**P3-RULE-10 · Public booking specifics.** 🔒 D-BKG-01/09/10/11/21, D-CUS-04/05, API-LIM-01, API-PUB-02 + owner #1 / #8.
- **Branch** = `?branch=<code>` (D-BKG-01); must be **ACTIVE** (unknown or inactive → 404). **`is_public` is not checked here** (review fix 02/Oct — R3-1): it only hides the branch from the website listing, the branch pages and the sitemap (Part 8 P8.PUB.01–03), while its booking link and QR keep working (DB Part 8: "is_public = false ⇒ not shown on the website; the booking link still works"; FE-IA-03; Part 8 P8-RULE-13) — every public endpoint of this part (P3.PUB.01–06 by `branch`, P3.PUB.07–12 by token) follows this rule. Only ACTIVE services in ACTIVE categories sold at the branch (FE-BK-05).
- **Spam** (create only): hidden honeypot field `website` must be empty and the **Turnstile** token (`captcha_token`) must verify server-side for the site hostname (failure or a filled honeypot → 403 `captcha_failed`, same answer; Turnstile unreachable for 3 s → 503 `captcha_unavailable` → FE-BK-16 panel); **10 attempts / hour / IP** (setting `booking.public_rate_limit_per_hour`; checked **before** Turnstile; every non-replay create attempt counts, successful or not) and **3 attempts / hour / phone** (every attempt that passes the captcha counts, so the one-active-booking answer can't be probed for a phone) → 429 `rate_limited` + `retry_after`; in-memory counters (one instance — ADR-008). Replays (P3-RULE-04 #1) are not counted.
- **≤ 5 services** per website booking and per website reschedule (setting `booking.public_max_services`, default 5 — owner #8) → 422 `too_many_services`; staff = no limit.
- **One active booking** per phone on the website (P3-RULE-04 #7 — checked last, after price and slot) — the message never reveals the existing booking (D-BKG-09).
- **Cutoff** (owner #1): reschedule and cancel through the link are allowed while `now < starts_at − booking.customer_change_cutoff_minutes` (default **120**); after it → 422 `change_cutoff_passed` and the manage page shows "please call the branch" (FE-MNG-05). Staff are never limited by it (D-BKG-12). The new time of a customer reschedule follows normal availability (no lead time — D-BKG-23).
- **Token handling:** the manage token is the only key (no OTP, no account — D-BKG-10, D-CUS-04); it travels in the path `/v1/public/bookings/{token}…` and in the create bodies (`manage_token`, with `captcha_token`); Caddy, the API logger, Sentry (`beforeSend`) **and the audit interceptor redact** the path segment (`/public/bookings/***`), the site page route (`/booking/***` — Caddy and Next.js logs) and the body fields `manage_token` / `captcha_token` — the raw token is never written to `audit_events` (D-BKG-11 "hash only"); responses are `Cache-Control: no-store` and the site page sends `Referrer-Policy: no-referrer` + `noindex` (FE-MNG-01). A malformed or unknown token → 404 `not_found`, identical body (no hint whether a booking exists). Nothing is ever sent to the customer (D-CUS-05) — the `.ics` file is built in the browser from the manage-page data (owner #5, REC-36 ✅).
- **Public DTOs** (API-PUB-02): no customer name or phone (only `phone_masked` on the manage page — `09•••••123`; the HOME address appears only on the manage page of that booking — API-PUB-02 exception), no staff phone / e-mail, barber photo / specialty only when `public_profile` is on, no internal ids of users, no buffer / block fields, no cancel reasons with `system_code`. Branch codes are matched case-insensitively (`?branch=b3` works — FE Postel). A booking made inside the cutoff is `can_change = false` from the start (the review step says so — FE-BK-10).

**P3-RULE-11 · Permissions — levels, reads, own bookings.** 🔒 D-ROLE-03/07, ADR-011, ADR-012 + owner #9.
- **Levels:** customers = **shared** (any assignment; history filtered — P3-RULE-03) · bookings = **branch data** (the booking's branch must be covered) · cancel reasons = **company master** (writes need company scope; branch scope = read-only).
- **Operational reads — any staff in read scope, no code:** P3.CUS.02 (phone lookup — the booking drawer and the walk-in FINISH need it, AD-FORM-10), P3.CRS.01 (active reasons for the cancel dialog), P3.BKG.02 (calendar feed — names, times, services; never phones). Plus the Part 2 operational reads (quote, availability, options, picker).
- **Own bookings — no code** (owner #9, 🔒 D-BKG-13, D-ROLE-07 "own work"): the caller is the booking's **booked barber** (`booked_employee_id` = caller's employee). Create (the caller is assigned to the branch on the date), read, edit details, reschedule (time / services / location — **changing the barber needs `booking.update`**), cancel, snooze. `GET /v1/me/bookings` lists them.
- **Management reads — `booking.view⁺` / `customer.view⁺` / `booking_cancel_reason.view⁺`:** the bookings list, someone else's booking detail (includes the customer phone and home address), customer list / detail / timeline, archived cancel reasons.
- **Writes for others** — `booking.create` (any barber of a covered branch), `booking.update` (reschedule / edit / snooze), `booking.delete` (cancel, incl. the no-show reason); fake website bookings are cancelled with `booking.delete` (D-BKG-21).
- **Search (P1.SYS.04, 🔒 D-SRC-01):** group `customers` needs `customer.view⁺` (shared) and returns ACTIVE, non-archived customers only (owner #7); group `bookings` = bookings in the `booking.view⁺` scope, or the caller's own bookings when they hold no booking code — §6.
- **Shared writes:** a branch-scope holder of `customer.update` / `customer.delete` changes the one company-wide customer row (D-CUS-01 — that is what "shared" means, ADR-012); seeds keep `customer.delete` with the Admin and `customer.update` with Admin + Manager.
- **Decorators:** "code **or** self" endpoints use `@Can(code, { branch, orSelf: 'entity.booked_employee_id' })` (API-PERM-02 v1.4).

**P3-RULE-12 · Notifications and realtime.** 🔒 D-NTF-01..03, D-BKG-15/23. In-app only; nothing goes to customers (D-CUS-05). Types (category 1 BOOKING — catalogue in `notifications.json`, Part 8; `default_recipient_rule` 3 TARGET_USER for the first three, 2 BRANCH_MANAGERS for the alarm, whose actual recipients are computed per booking — P3-RULE-08): `booking.new` (to the booked barber when someone else — website or another staff member — creates it), `booking.rescheduled` (to the old and the new booked barber, unless they did it), `booking.cancelled` (to the booked barber unless they did it; payload `cancelled_by_actor` so Today shows "Cancelled by customer"), `booking.noshow_alarm` (P3-RULE-08 recipients). Realtime events — §8. Events are emitted after commit (API-RT-02); jobs are enqueued inside the transaction (ADR-002).

**P3-RULE-13 · One slot-release path, audit.** 🔒 D-BKG-20 (§6.4b A-3 waitlist preparation), D-AUD-01. Cancel, no-show cancel (timer or staff) and reschedule all leave through one domain function that emits the internal event `booking.slot_released { branch_id, employee_id, block }` after commit (no consumer in V1 — the waitlist hook). Audit actions: `customer.create / update / deactivate / reactivate / archive / restore`, `booking.create / update / reschedule / cancel / noshow_snooze / noshow_autocancel`, `booking_cancel_reason.create / update / archive / reorder`; reschedule stores the before / after diff (items included). **`branch_id` of these rows follows API-AUD-01** (review fix 02/Oct): booking actions = the booking's branch; customer and cancel-reason actions = NULL (shared / company master — read at company scope only, Part 8 P8-RULE-06).
