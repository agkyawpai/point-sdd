## 1. Rules specific to this part

**P1-RULE-01 · One user per employee.** 🔒 D-EMP-02. There is no standalone user API: `POST /v1/employees` creates the `users` row (email, status 2 INVITED) and the `employees` row in one transaction; `users` is only ever read through `/me` or the employee's Access tab. Email is unique (`users.email`), checked case-insensitively (⚠️ stored lower-cased).

**P1-RULE-02 · Login identity.** 🔒 D-AUTH-02 / 08. Login succeeds only for an email that exists in `users` with `status ∈ (1 ACTIVE, 2 INVITED)` and whose employee is `1 ACTIVE`. First successful login on an INVITED user: `status → 1`, `activated_at` set (D-AUTH-03). Google: on first Google login the Google email must equal `users.email`; `google_subject` is stored and checked afterwards (D-AUTH-08).

**P1-RULE-03 · OTP.** 🔒 D-AUTH-04. 8 digits, HMAC hash stored, 5-minute expiry, single use, only the latest OTP is valid (older rows are invalidated on a new request), 60-second resend cooldown, 5 consecutive failures → `login_locked_until = now + 20 min`, counter reset on success. Request / verify responses are **neutral** (same 202 for unknown or disabled email; verify always answers `otp_invalid` for unknown / expired / wrong, never "no such user"). **v1.6:** (owner S9) verify also has the per-IP cap of API-LIM-02 — 10 attempts per hour per IP → 429 `rate_limited` (`retry_after`), counted before any look-up, counter change or audit write. (owner S10) The lock answer stays as written: a locked existing address answers `login_locked`, an unknown address keeps answering `otp_invalid` — the two can be told apart after five failures; accepted for V1. (owner S5) Field codes of the login form inside 400 `validation`: `email_invalid` (the `email` member is not an address — P1.AUTH.01 / .02) and `otp_format` (the `code` member is not 8 digits — P1.AUTH.02); an over-long e-mail is `too_big` (API-ERR-03).

**P1-RULE-04 · Session checks.** 🔒 D-AUTH-06. Guard order on every staff request: cookie → session row (`revoked_at IS NULL`) → `users.status = 1` → `employees.status = 1` → maintenance (API-AUTH-06) → permission (API-PERM-02). `last_seen_at` is updated at most every 5 minutes. A status change on the user / employee revokes all sessions in the same transaction with `revoke_reason = 4 ACCOUNT_INACTIVE`.

**P1-RULE-05 · Branch scope resolution and read scope.** 🔒 D-ROLE-03/05. The guard builds the caller's **grant set** once per request from `employee_roles` (active: `revoked_at IS NULL`) × `role_permissions` × `employee_role_branches`: `{ code → { company: bool, branch_ids: Set } }`. A permission is granted for branch *B* if any grant has `company = true` or `B ∈ branch_ids`. **Read scope** (v1.3 — from Part 2 P2-RULE-11) = branches of the caller's active `employee_branches` assignments ∪ branches covered by any grant (all branches when any grant is company-scope); operational reads (ADR-011 #4) and realtime branch rooms (API-RT-01) use it, so a barber with no permission code still reads their own branches. Role or scope changes take effect on the next request (D-ROLE-06) and emit `session.updated`. **How far a grant reaches depends on the data level of the target** (v1.4 — P1-RULE-13, API-PERM-07, ADR-012).

**P1-RULE-06 · Own-earnings effective flag.** 🔒 D-DSH-03 (v5.2.8) + D-COM-04. `effective_show_own_earnings = COALESCE(employees.show_own_earnings, setting dashboard.show_own_earnings_all)`; computed server-side, returned in `/me` and used by Part 4 / 5 to include or omit the commission estimate (AD-POS-07) and earnings widgets. Changing either input emits `session.updated` to affected users.

**P1-RULE-07 · Public profile fields.** 🔒 D-WEB-01, D-UX-05 (v5.2.8). `public_profile`, `public_specialty_mm/_en`, `photo_url` (through `photo_attachment_id` — v1.5, the stable media path of Part 8 P8-RULE-04) are edited with `employee.update`; `public_rating` with `employee.rating_update` (both branch-scopable — whoever the admin gives the code to, ADR-011). Any change enqueues `site.content_changed { tags: ['barbers'] }`. `public_rating` is validated to the DB CHECK (1.0–5.0 step 0.5, or null).

**P1-RULE-08 · Settings resolution.** 🔒 D-PLT-16. `settings.json` (code) defines `{ key, type, default, scope: company|branch, validation, label_key, help_key, module, impact_key? }`. Effective value for (`key`, `branch_id?`) = branch row (if scope allows and exists) → company row → default. Writes validate against `type` / `validation`, write the row (upsert), the DB trigger writes `settings_history`, the API emits `settings.changed` (`site.*` keys and their `site.content_changed` event are written by Part 8 P8.WEB.02 with the same store functions). Keys are never free-form: an unknown key → 404 `error.not_found`; a branch override on a company-only key → 400 `error.setting_scope`. Key format follows the DB CHECK `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$`. Rows are never deleted (reset = update to the parent value — P1.SET.04). **v1.5 (Parts 5 / 6 / 8):** keys of module **`website`** (`site.*` — Part 8 §17, company scope only) are **read-only in this part**: P1.SET.03 / 04 refuse them with 400 `setting_scope`, and they are written only through Part 8 **P8.WEB.02** (`website.update`, company scope — one write path with the image linking, the single transaction, `expected_updated_at` and the revalidation tags; review fix 02/Oct — R3-9; `settings.update` never covers them). The same holds for **`system.maintenance`**, written only by P1.SYS.03 (and the restore authorisation P8.BAK.03); every **`payroll.*`** and **`attendance.*`** key is **company-only** (a branch override → 400 `setting_scope` — Part 5 §17); a key whose type is a reference (`ref:<table>`, e.g. `stock.refund_damaged_reason_id` → `stock_adjustment_reasons`) must point to an ACTIVE row (400 `validation`, `errors[].code = reason_inactive` — Part 6 P6-RULE-07).

**P1-RULE-09 · Archive, never delete.** 🔒 D-DAT-05. Branches, roles, employees have status / `archived_at`; there is no `DELETE` on them. A role with active assignments cannot be archived (409 `error.role_in_use`); a branch with active employee assignments or open bookings / sales cannot be deactivated (409 `error.branch_in_use` with counts).

**P1-RULE-10 · Audit actions in this part.** 🔒 D-AUD-01 + AD-AUD-01. `login.success`, `login.failed`, `login.locked`, `session.revoked`, `employee.create`, `employee.update`, `employee.status`, `employee.invite_resend`, `employee.invite_cancel`, `employee.branch_assign` / `branch_end`, `employee.role_assign` / `role_revoke`, `employee.rating_set`, `role.create` / `update` / `permissions_set` / `archive`, `branch.create` / `update` / `status`, `company.update`, `settings.set` / `settings.reset`, `system.maintenance`, and — **v1.6 (owner S13)** — **`permission.sync`**: written by the start-up catalogue sync (D-ROLE-08) when a run changed something; a system row (`source = 3`, `branch_id` NULL — read at company scope only). The first-admin command writes `employee.create` / `employee.role_assign` with `source = 3` (P1-RULE-14). Login failures are audited with the attempted email hashed (⚠️ privacy) and the IP. **`branch_id` of these rows follows API-AUD-01** (review fix 02/Oct): branch update / status and a branch setting override = that branch; branch assignment / end = the assignment's branch; other employee-targeted actions (create, update, status, role assign / revoke, rating, invites, sessions) = the employee's **primary branch** (earliest active assignment — Part 5 P5-RULE-04; reconcile 02/Oct, 🔒 D-AUD-01 "manager = assigned branch"), NULL when the employee has no active assignment; company, role, company-setting, maintenance and login rows = NULL (read at company scope only — Part 8 P8-RULE-06).

**P1-RULE-11 · Scope of employee-targeted actions.** 🔒 D-ROLE-03/05 + ⚠️. For every `employee.*` / `role.assign` action the **target branch set** = the target employee's active branch assignments; the caller needs the code with company scope or with a branch scope that overlaps that set (an employee with no assignment is reachable only by company-scope holders). `employee.create` with branch scope: the initial `branch_ids` must lie inside the caller's scope. `PATCH /v1/employees/{id}` is **field-grouped**: each field group needs its own code (table in P1.EMP.04); a request containing a field the caller may not change → 403 `forbidden` with `errors[]` naming the fields.

**P1-RULE-12 · Company admin and the last-admin rule.** 🔒 (owner 01/Oct 21:20 — sheet #25 = A; ADR-011, API-PERM-06). A **company-admin role** = a role whose permission set contains **all five** role codes `role.view`, `role.create`, `role.update`, `role.delete`, `role.assign`; a **company admin** = a user with an active **company-scope** assignment of such a role (the seed Admin role has every code — D-ROLE-09 — so it qualifies). Company admins are exempt from the no-escalation check (they may grant any catalogue code); everyone else may grant only codes and branch scopes they hold. The **last active company admin** is protected: P1.EMP.05 (status → 0 / 2 / 3), P1.EMP.11b (revoke of the qualifying assignment), P1.RL.05 (removing any of the five role codes from that role) and P1.RL.06 (archiving that role) answer 409 `last_admin`. `sync.code_tables` adds newly deployed codes to every company-admin role (audited `role.permissions_set`, actor = system; ⚠️ default on — the admin may untick).

**P1-RULE-13 · Data levels in this part (v1.4 — 🔒 owner choice A, ADR-012, API-PERM-07).**
| Level | Part 1 targets | Write needs |
| --- | --- | --- |
| **Company master** | company profile (P1.CO.02) · new branch (P1.BR.02) · branch deactivate / re-activate (P1.BR.05) · roles and their permission sets (P1.RL.02/04/05/06) · **company** setting values (P1.SET.03/04 without `branch_id`) · maintenance mode (P1.SYS.03) | the code through a **company-scope** assignment — else 403 `company_scope_required` |
| **Branch data** | the branch's own profile (P1.BR.04) · every employee action (P1-RULE-11 target set) · branch assignment (P1.EMP.07/08) · role assignment / revoke (P1.EMP.11/11b — the assigned branches must lie inside the caller's scope) · **branch** setting overrides (P1.SET.03/04 with `branch_id`) | the grant covers the target branch(es) |
**Reads:** roles (P1.RL.01/03) and the permission catalogue are company master — any `role.*` grant at any scope reads them (a branch Manager holding `role.assign` sees the role list to assign from). Settings are **mixed** (P1.SET.01/05): any `settings.*` grant reads the company values; branch values only for branches its grant covers. The client knows each code's level from the shared `permissions.json` and hides company-master write controls from branch-scope holders (AD-PERM-02, AD-PERM-07 v1.4).

**P1-RULE-14 · The first company admin of an environment (v1.6 — 🔒 owner S6, review §0.11).** There is no endpoint for it — nobody can sign in yet. An operator runs a command on the server: `docker compose exec api node dist/cli/admin-create.js --email <e> --name-mm <n> --code <c> [--name-en <n>]` (from source: `pnpm admin:create`). In one transaction it creates the `users` row (`status = 2 INVITED`), the `employees` row and a company-scope assignment of the seed **Admin** role. It **succeeds only while no active company admin exists** — an employee with status ACTIVE who holds an unrevoked company-scope assignment of a company-admin role (P1-RULE-12), whatever the user's status: an admin who is still INVITED counts, so a second run before the first sign-in is refused. Otherwise — and when the e-mail or the employee code already exists — it exits with status 1 and changes nothing. `--code` (the employee code) is required: `employees.employee_code` is NOT NULL and the code generator of P1.EMP.02 (`employee.code_format`) arrives with the employee screens; without `--code` the command exits with status 1. Audit rows: `employee.create` and `employee.role_assign` with `source = 3` and `after_data.operator` = the operating-system user. The person then signs in like any invited employee (P1-RULE-02).

**P1-RULE-15 · Signing in again in the same browser (v1.6 — 🔒 owner S14).** When a sign-in succeeds (P1.AUTH.02 code verify, P1.AUTH.04 Google callback, P1.AUTH.06 hand-off) on a request that carries a still valid `point_session` cookie, the session of that cookie is revoked with `revoke_reason = 1 LOGOUT` in the same transaction that creates the new session (audit `session.revoked`, event `session.revoked`). One browser holds one session; the device list shows one row per device.

## 10. Permission codes introduced by Part 1 (🔒 for `permissions.json` — 21 codes · ADR-011 + ADR-012)

Rule (owner 01/Oct 21:20 — ADR-011): **one module per menu, CRUD columns** `view` · `create` · `update` · `delete` (only the actions that exist for the menu) **+ named special actions**; no `manage` code. `delete` = archive / deactivate, never a hard delete (D-DAT-05). `<module>.view⁺` in the endpoint tables = `<module>.view` **or any other code of the same module** (API-PERM-06). Reference / operational reads (company info, branch summaries, the employee picker, `/me`) need no code. **Level** (v1.4 — ADR-012, replaces *Scope*): `company` = acts on company master only (a branch-scope grant reads it, never writes) · `branch` = branch data in the grant's scope · `mixed` = company values need company scope, branch values need the branch (P1-RULE-13) · **`private`** (v1.5 — contract 1, owner C1; used by Part 5 / 8 codes, none in Part 1) = company-only data: read and write need company scope, a branch-scope grant reaches nothing (API-PERM-07).
