## 1. Rules specific to this part

**P6-RULE-01 · Data levels, reads and who may act.** 🔒 D-ROLE-03/07, ADR-011, ADR-012 + owner D2 / D4.
- **Company master** (write = company scope; a branch-scope grant reads read-only — API-PERM-07): product categories and products (names, category, SKU, sellable, **company sell price**, default threshold, status, archive — F-P6-01/02), suppliers, stock adjustment reasons.
- **Branch data** (the target branch must be covered): stock levels and the branch threshold override, the movement ledger, usage, manual adjustments, counts. **Purchases** = branch data **per line** (the header has no branch — D-STK-02): a read passes when **any** line's branch is in scope, a write (edit, request post, post, cancel) needs **every** line's branch (a create / replace checks every line in the body — `body.items[].branch_id`). **Transfers** = branch data on **two** branches: read = sending **or** receiving branch in scope; create, edit, send, cancel = the **sending** branch; receive = the **receiving** branch, or the receiver themselves (owner D4).
- **Operational reads — any staff in read scope, no code** (P1-RULE-05): P6.CAT.01 (active categories), P6.PRD.02 (product picker with stock at a branch — POS product line, usage, purchase / transfer / count forms), P6.SUP.02 (supplier picker), P6.RSN.01 (active reasons).
- **Self (no code):** P6.STK.06 (my usage entries), P6.TRF.02 (transfers I may receive), and receive / read of a transfer where the caller is the named receiver or, for a BRANCH_STAFF transfer, an active staff member of the receiving branch (owner D4).
- **`stock.view⁺`** (API-PERM-06 #4) = `stock.view` or any other `stock.*` code — so a Barber holding only `stock.usage` may open *Stock levels* and *Movements* of their branches **read-only**. That matches 🔒 D-ROLE-07 ("branch operations view-only") and AD-POS-04 (the POS already shows stock); purchases (costs) stay behind `purchase.view⁺`.
- **Decorators** (API-PERM-02): purchases use `@Can(code, { branch: 'entity.items[].branch_id' })` (every) for writes and the **any-of** form for reads; transfers use `branch: 'entity.from_branch_id'`, `'entity.to_branch_id'` with `orSelf: 'transfer.receiver'` for receive, and the any-of form `'entity.from_branch_id|entity.to_branch_id'` for reads (Part 0 amendment — §15).

**P6-RULE-02 · `StockLedger.post` — the only writer of stock.** 🔒 D-STK-06, F-P6-04/05 + cross-part contract 4. Every quantity change in the system goes through one in-process function, inside the **caller's** transaction:
`StockLedger.post(tx, actor_user_id, movements: [{ branch_id, product_id, movement_type, quantity_delta, ref: { purchase_item_id | stock_transfer_item_id | sale_item_id | refund_item_id | stock_count_item_id }?, adjustment_reason_id?, note?, occurred_at, client_request_id? }]) → { movements, levels, warnings }`
1. Sort the pairs by (`branch_id`, `product_id`); `INSERT … ON CONFLICT (branch_id, product_id) DO NOTHING` the missing `branch_stock_levels` rows (quantity 0); `SELECT … FOR UPDATE` them **in that order** (one lock order everywhere — no deadlock between FINISH, a transfer and a count).
2. INSERT the movements: `business_date` = MMT date of `occurred_at` (D-PLT-15 — DB CHECK); `recorded_by_user_id` = actor; the DB enforces type ⇔ sign ⇔ single reference and one movement per reference (F-P6-05 — a 23505 on a reference index = a double post → 409 `invalid_transition`; on `client_request_id` = a replay — P6-RULE-12).
3. `quantity_on_hand += Σ delta`, `updated_at = now()` (the cache — same transaction, F-P6-04).
4. Low-stock evaluation per touched row (P6-RULE-04) and `warnings[]` (`negative_stock`, `low_stock` — P6-RULE-03).
5. After commit (API-RT-02): realtime `stock.changed` (+ `stock.low`) and notifications.
**Lock order** (one order in every part — independent review R1-8): **day lock (advisory `DayLock`, Part 7) first → payroll lock (advisory `PayrollLock`, Part 5) → sale → visit → booking → payments → receipt counter → cash-out / closing rows → the header row of this part (purchase / transfer / count — `FOR UPDATE`) → stock level rows last** (step 1, sorted). The endpoints of this part take **no day lock**: stock is not part of the cash closing (🔒 D-FIN-06 — closings count cash and KBZPay only), so a closed day never blocks a stock movement; Part 4 takes its own `DayLock` as the **first** lock of FINISH / refund, long before it calls this function. Every transaction of this part runs **READ COMMITTED** with its locks taken first and every check after them (REPEATABLE READ READ ONLY is for reports only — ADR-015). Users of the function: Part 4 FINISH (SALE_OUT) and refunds (SALE_RETURN_IN + damaged write-off — P6-RULE-11), and every endpoint of this part.

**P6-RULE-03 · Stock never blocks work.** 🔒 F-P6-04, AD-POS-04 + owner D5. A sale, usage, transfer send or adjustment may take a quantity below zero; the response carries `warnings[] negative_stock { branch_id, product_id, quantity_on_hand }` and the level's `state = "negative"` (danger badge — §6.3, AD-RPT-03 flag). The only refusals are data rules: an **archived** product (422 `product_archived`), an inactive product where the action creates new demand (sale — Part 4 `product_not_sellable`; purchase line — 422 `product_inactive`), and a manual adjustment / count that would move nothing (delta 0).

**P6-RULE-04 · Low stock.** 🔒 D-STK-06, D-NTF-03 + owner D6 / F12, research E5 / E6. Effective threshold = `branch_stock_levels.low_stock_threshold` (branch override — `stock.update`, owner D6: the branch's manager sets it) else `products.default_low_stock_threshold` (company — `product.update`); both null = never low. **Low = quantity_on_hand ≤ threshold** ("at or below" — research E6). On every touched row (P6-RULE-02 #4) and on a threshold change (P6.STK.02): low and `low_stock_notified_at IS NULL` → set it to now, emit `stock.low`, notify once; above the threshold and notified → set it back to `NULL` (re-arms). Recipients (`stock.low`, owner D6 + F12): company-scope holders of `stock.view` (fallback: company admins) **and** holders of `stock.view` through a branch-scope assignment listing that branch (+ company-scope holders assigned to that branch). The Part 6 DBML comment setting `stock.low_stock_notify_roles` is **dropped** (research E5 — recipients follow the notification catalogue, AD-NTF-02).

**P6-RULE-05 · Products.** 🔒 F-P6-01/02, D-PAY-03, D-DB-04, D-DAT-05, AD-STK-01.
- `name_mm` required, `name_en` optional (the English receipt falls back to MM — 🔒 D-PAY-06); name unique per company among non-archived, `sku` optional and unique (409 `already_exists`); unit = pcs (🔒 D-STK-01 — no unit field).
- `is_sellable = true` ⇒ `sell_price_amount` required (≥ 0); `false` (shop-use — colour, shampoo) ⇒ no price (400 `validation` — DB `products_sell_price_chk`); switching to shop-use clears the price. One **company price** (branch override ⏭ — F-P6-02); the sale line snapshots it at add time (Part 4 `list_price_amount`), so a price change never touches open or finished sales.
- `status` 0 INACTIVE (P6.PRD.05): no new sales or purchase lines; existing stock can still be used, moved, counted and adjusted. **Archive** (P6.PRD.06 — `product.delete`) is refused while (a) any branch quantity ≠ 0 or a **SENT transfer** carries the product (in transit — research E8) → 409 `product_has_stock { branches[], in_transit_quantity }` ("Move or adjust the remaining 3 pcs first" — AD-STK-01), or (b) a DRAFT purchase, DRAFT transfer, IN_PROGRESS count or OPEN sale line has it → 409 `product_in_open_documents`. A category is archived only when empty (409 `category_in_use { count }` — one context shape in Parts 2 / 6 / 7).

**P6-RULE-06 · Barber usage — "used up a bottle / box".** 🔒 D-STK-04, AD-STK-05 + owner D7, sheet G (c). `POST /v1/stock-usages` (P6.STK.05 — `stock.usage`, Barber seed) with **`Idempotency-Key`** writes one USAGE_OUT of `−quantity` (default **1**, 1–99) — the ≤ 3-tap flow: *Used up* → product → *Save*.
- **Product list** (P6.PRD.02 `purpose=usage`, owner D7 a): **every ACTIVE product**, shop-use (`is_sellable = false`) first, the caller's 5 most recent usages on top (`recent`); any non-archived product is accepted (inactive leftovers too).
- **Branch:** `branch_id` if sent; otherwise the branch of the caller's **open clock-in** (Part 5 **`Attendance.openRecordOf(employee_id)`** — the caller's open attendance record or none; owned by Part 5), else today's **single** shift branch (Part 2 `schedule_shifts`), else the **only** assigned branch; otherwise 422 `branch_required { branch_ids }` (the UI asks once). The branch must be covered by the caller's `stock.usage` grant (403 `out_of_scope`).
- **Double tap** (G (c)): the key is stored in `stock_movements.client_request_id` (partial unique — DB Part 6 v1.2); a retry → 200 + `Idempotent-Replayed` with the same movement; same key with another product / branch / quantity → 422 `idempotency_mismatch`. Only fields the request **sent** are compared: with `branch_id` omitted the branch is **not** compared on a replay (the stored movement's branch stands), so a clock-in / clock-out between the tap and the retry never gives a false mismatch. A client unsure whether the tap was saved asks Part 4 **P4.REQ.01** `GET /v1/me/requests/{client_request_id}` (`resource_type` `stock_movement`; 404 = not saved → retry with the same key — AD-NET-02).
- **No self-undo** (owner D7 b): a wrong tap is corrected by a manager's manual adjustment (+qty, reason "Entry error" — P6-RULE-07). Optional `adjustment_reason_id` / `note` (the DB allows a reason on USAGE_OUT). The *Usage by barber* report groups by `recorded_by_user_id`.

**P6-RULE-07 · Manual adjustments and the refund write-off.** 🔒 D-STK-05, F-P6-08 + owner D9, B8 a, research E10.
- `POST /v1/stock-adjustments` (P6.STK.07 — `stock.adjust`, Manager seed, `Idempotency-Key`): MANUAL_ADJUST ± quantity (≠ 0) with a **reason from the ACTIVE master list** (422 `reason_inactive`; DB CHECK) + optional note. Positive = found / returned; negative = damaged / lost / expired / entry error. The manager posts it directly; **notification `stock.adjusted`** to company-scope `stock.adjust` holders (fallback company admins), minus the actor (owner D9 / F12).
- **Reasons** (P6.RSN): company master, **disable only, never delete** (🔒 D-STK-05 — no `archived_at`); `name_mm` unique incl. disabled rows (DB index).
- **Refund write-off** (owner B8 a — cross-part contract 4): Part 4 P4.RFD.02 sends `back_to_stock` per refunded product line and P4-RULE-14 calls `StockLedger.post(tx, actor_user_id, movements[])`; `true` → SALE_RETURN_IN `+quantity`; `false` (damaged / not returned) → SALE_RETURN_IN **and** MANUAL_ADJUST `−quantity` with `adjustment_reason_id` = setting **`stock.refund_damaged_reason_id`** (seeded reason "ပျက်စီး — customer ပြန်ပေး / Damaged — customer return"), note = the RF number, recorded by the refunder — no `stock.adjust` code needed (part of `sale.refund`), no separate `stock.adjusted` notification (`sale.refunded` already reaches the admins). The reason the setting points at cannot be disabled (409 `reason_in_use_by_setting`) and the setting accepts only an ACTIVE reason (Part 1 P1.SET.03 validation → 400 `validation`, `errors[].code = reason_inactive` — `settings.json` type `ref:stock_adjustment_reasons`).

**P6-RULE-08 · Purchases.** 🔒 D-STK-02, F-P6-03, F-P7-05, D-FIN-03/05/08 + owner D1 / D2 / D3, research E4.
- **Lifecycle:** 1 DRAFT → 2 POSTED (immutable) or 0 CANCELLED (DRAFT only — DB CHECK). The list filter `post_requested=true` (P6.PUR.01) applies the same test (index `audit_events (entity_type, entity_id, occurred_at)` — DRAFTs only, a small set). The **Admin posts** (`purchase.post`, Admin seed). **Carve-out — 🔒 F-P7-04 / F-P7-05 (independent review R2-6):** the purchase expense is an automatic source, so it is **APPROVED by DB CHECK** (`expenses_status_fields_chk`: only source 1 may be PENDING — the stock is already on the shelf). Owner **E4** ("auto-approve only for a company-scope approver, never one's own") and 🔒 D-FIN-03 ("non-admin entries need approval") govern **MANUAL** expenses / incomes; here the control is the code **`purchase.post`** itself (Admin seed — owner D2): whoever the owner grants it to — also through a branch-scope role — posts purchases whose expenses are APPROVED at once. Oversight = the purchases list, the expense list (source 4) / report ⑩ and the audit rows; no new notification type.
- **Review step** (owner D3): P6.PUR.03 returns `totals_by_branch[]` (lines, quantity, amount = the expense each branch will get) and `total_amount`; the post body repeats `expected_total_amount` → 409 `total_changed { total_amount }` if a line changed since the review (AD-CONF-01 "Post purchase" dialog).

Realtime `stock.purchase_posted`; notification `stock.purchase_posted` to the drafter when someone else posted; audit `purchase.post` (interceptor row — `purchases`, `purchase_items` and `stock_movements` have **no** DB audit trigger, P6-RULE-15; the expense rows get the `expenses` trigger rows of Part 7 — D-AUD-02).
- **Drawer cash** (owner D1): a purchase never touches the cash drawer. When stock is paid from a branch drawer, the closer records a **Cash Out** with the CASH_MOVEMENT reason **"Stock purchase payment — recorded in Stock"** (Part 7 seed — contract 6): cash leaves the drawer (closing), no second expense. "Supplier" (EXPENSE) stays for non-stock bills.

- **Draft lines** (P6.PUR.05 PUT): matched by `id` — kept / changed in place, new inserted, missing **removed**; ≥ 1 line (an empty `items` → 400 `validation` — schema `minItems: 1`). The removed DRAFT lines are **deleted** with the full before / after in the audit diff (`purchase.update_items`) — **🔒 owner 02/Oct/2026, OPEN-40 OK ((c) = A)**: the same reading as owner answer A2 for booking items — a DRAFT has posted nothing (no stock or money effect, nothing references the line). The endpoint, body and response are unchanged and no DB file is changed for it.

**P6-RULE-09 · Transfers — two steps, two branches.** 🔒 D-STK-03 / REC-14, F-P6-06, AD-STK-04 + owner D4 / D5, research E7.
- **Lifecycle:** 1 DRAFT (edit / cancel) → 2 **SENT** (stock leaves: TRANSFER_OUT `−quantity_sent` per line at the sending branch — "in transit") → 3 **RECEIVED** (TRANSFER_IN `+quantity_received` per line with quantity > 0 at the receiving branch). 0 CANCELLED from DRAFT only. No separate approve / dispatch step (REC-14 — the employee carries it).
- **Draft** (P6.TRF.03/05/06 — `transfer.create` / `update` on the sending branch): `from ≠ to` (422 `same_branch` — DB CHECK); receiver = **1 EMPLOYEE** (an ACTIVE employee assigned to the receiving branch today — 422 `receiver_not_at_branch`; picker P1.EMP.09 `branch_id` + `date`) or **2 BRANCH_STAFF**; lines: product non-archived (inactive leftovers may be moved), `quantity_sent` ≥ 1, one line per product (409 `duplicate_line`). The sending branch never changes (cancel + new). Quantity inputs start empty (AD-STK-04). Every draft write (P6.TRF.05 / 06 / 09) locks the `stock_transfers` row `FOR UPDATE`, re-checks DRAFT and sets `updated_at` (R2-11); lines removed by P6.TRF.06 follow the purchase rule — deleted with the full audit diff `transfer.update_items` (P6-RULE-08; owner 02/Oct/2026, OPEN-40 OK (c)).
- **Send** (P6.TRF.07 — `transfer.send`, idempotent by state): lock the transfer row; DRAFT only (SENT / RECEIVED → 200 current state); receiver re-checked; `StockLedger.post` TRANSFER_OUT per line, below zero allowed (`warnings[] negative_stock` — owner D5); `sent_at`, `sent_by`. Notification **`stock.transfer_sent`** (toast — AD-NTF-03) + realtime to the named receiver, or to every active staff member of the receiving branch (BRANCH_STAFF).
- **Receive** (P6.TRF.08 — owner D4): allowed to the **named receiver** (EMPLOYEE), to **any active staff member assigned to the receiving branch** (BRANCH_STAFF) — both **without a code** — and always to `transfer.receive` holders covering the receiving branch (e.g. when Ko Aung is off). The transfer row is locked `FOR UPDATE` and re-checked SENT. Body = every line once with `quantity_received` (0–100,000) and `difference_reason` when it differs from `quantity_sent` (400 `reason_required` — DB CHECK); there is **no receive note** (`stock_transfers.notes` is the draft note and no other column exists — independent review R2-18; a difference is explained in the line's `difference_reason`). TRANSFER_IN `occurred_at` = `received_at`. **Shortfall** = charged to the sending branch in reports (no extra movement — F-P6-06); **over-receipt** is allowed with the reason, flagged `over` and notified (research E7). Notifications: `stock.transfer_received` to the creator and the sender (minus the actor); `stock.transfer_difference` to company-scope `transfer.view` holders when any line is short or over. Idempotent by state: RECEIVED with the same quantities → 200; different → 409 `invalid_transition`.
- **Cancel** (P6.TRF.09 — `transfer.delete`): DRAFT only, reason in the audit row. SENT → 409 `invalid_transition` with `correction_path: "receive_zero_with_reason"` (stock already left; the receiving side enters 0 and the reason, so the loss shows in the shortfall report).

**P6-RULE-10 · Stock counts — blind entry, review, post.** 🔒 D-STK-05, F-P6-07, AD-STK-05, AD-WIZ-01 + owner D8 / D9.
- **Start** (P6.CNT.02 — `stock.count`): one IN_PROGRESS count per branch (409 `count_in_progress { count_id }` — DB partial unique). Scope (owner D8 — independent review R2-2): **whole branch** = **every ACTIVE, non-archived product of the company — whether or not the branch has a `branch_stock_levels` row yet (no row → `expected_quantity` 0)** — plus every INACTIVE non-archived product whose quantity at the branch ≠ 0; **chosen categories** (`category_ids`) = the same rule limited to the products of those categories; no product → 422 `nothing_to_count`. One `stock_count_items` row per product; `expected_quantity` = the quantity at start (snapshot — F-P6-07; the level row, or 0); no level row is created at start (the COUNT_ADJUST at post creates it — P6-RULE-02 #1). A product the branch does not keep is counted **0**. The requested scope is not stored (`stock_counts` has no column for it — it is in the audit row `stock_count.start`); the DTO field `category_ids` is **computed** = the distinct `products.category_id` of the count's items. A product found on the shelf but not listed is added with P6.CNT.05 (expected = the quantity at that moment).
- **Blind entry** (owner D8): while IN_PROGRESS, `GET` (P6.CNT.03) and the entry responses return `expected_quantity` / `difference_quantity` = **null**; the counter types what is on the shelf (P6.CNT.04 — bulk, `null` = not counted yet, optional reason / note per line; several phones may count together — realtime `stock.count_updated` "18 / 24 counted"). Each entry request (P6.CNT.04 / 05) locks the `stock_counts` row `FOR UPDATE`, re-checks IN_PROGRESS (409 `invalid_transition`) and sets `updated_at` — so an entry can't land after the post read the lines (R2-11); between entries the lines stay last-write-wins. Blindness is a screen rule, not a security boundary (a `stock.view⁺` holder can still open *Stock levels*).
- **Review** (P6.CNT.06 — owner D8): expected, counted and difference per line, tabs *Uncounted* / *Different*, summary (short / over quantities, approximate cost from the last purchase unit cost — display only, F-P6-03).
- **Post** (P6.CNT.07 — `stock.count`, the manager may post — owner D9): the count row `FOR UPDATE`; every line counted (422 `count_incomplete { uncounted }`); one **COUNT_ADJUST** per line with difference ≠ 0, `delta = counted − expected`, `ref = stock_count_item_id`, **`occurred_at` = `posted_at`**, and **no reason or note on the movement** (DB `stock_movements_type_refs_chk` requires `adjustment_reason_id IS NULL` for type 7 — the line's optional reason / note stay on `stock_count_items`; the ledger DTO reads them through the reference — independent review R2-19) (F-P6-07: movements after the start stay as recorded — count when the shop is quiet); `posted_at` / `by`; idempotent by state. Notification **`stock.count_posted`** to company-scope `stock.count` holders when any difference ≠ 0 (owner D9 / F12). **Cancel** (P6.CNT.08): IN_PROGRESS → 0 CANCELLED, nothing posted, reason in the audit row.

**P6-RULE-11 · Sales and refunds (Part 4 calls).** 🔒 D-PAY-03/05, F-P6-09 + cross-part contract 4, owner B8 a, D5.
- **Add product line** (Part 4 P4.SAL.04): the POS picker is P6.PRD.02 `purpose=sale` (ACTIVE sellable products with the quantity at the sale branch — AD-POS-04); nothing moves until FINISH; stock never blocks (`warnings[] negative_stock`).
- **FINISH** (P4-RULE-10 stock step): `StockLedger.post` one **SALE_OUT** `−quantity` per active (non-removed) PRODUCT line at the sale branch, `ref = sale_item_id`, `occurred_at = finished_at` (late entry: the entered time). A cancelled / INCOMPLETE sale moves nothing.
- **Refund** (P4-RULE-14): per refunded PRODUCT line **SALE_RETURN_IN** `+refund_items.quantity` (`ref = refund_item_id`) and, when `back_to_stock = false`, the write-off of P6-RULE-07.
- Product lines get their share of the sale discount and are never commissionable (🔒 D-PAY-04 v5.2.7, D-COM-02) — Part 4 / 5 concerns; this part only moves quantities.

**P6-RULE-12 · Idempotency, locks and concurrency.** 🔒 D-VIS-10, API-IDEM-02/04/05 + contract 15, sheet G (c), research E3.
- **`Idempotency-Key` required** (row-creating, table has `client_request_id`): **P6.STK.05 usage** and **P6.STK.07 manual adjustment** only — identifying fields (usage) `branch_id`, `product_id`, `quantity`; (adjustment) `branch_id`, `product_id`, `quantity_delta`, `reason_id`. Replay → 200 + `Idempotent-Replayed: true`; in progress → 409 `idempotency_in_progress`; mismatch → 422 `idempotency_mismatch` (only fields the request sent are compared — an omitted usage `branch_id` is not, P6-RULE-06); missing → 400 `idempotency_key_required`.
- **Idempotent by state, no key** (contract 15): purchase post, transfer send / receive, count post, cancels — the row is locked `FOR UPDATE`, a repeat returns 200 with the current state, a move on → 409 `invalid_transition`.
- **Drafts** (purchase, transfer, count start) carry no key: a duplicate draft is visible and cancellable; a duplicate count start hits the one-in-progress index (409).
- **Optimistic concurrency:** master rows and drafts send `expected_updated_at` (409 `conflict` — API-IDEM-04); count lines are last-write-wins (realtime keeps phones in step).
- **Child rows never race their header** (independent review R2-11): line replace (P6.PUR.05, P6.TRF.06), header edits, request-post, cancels and count entries (P6.CNT.04 / 05) take `SELECT … FOR UPDATE` on the purchase / transfer / count row first and re-check DRAFT / IN_PROGRESS; all of them except request-post bump the header `updated_at`. Lock order: header row → stock level rows (P6-RULE-02).
- **Later states** (AD-DET-03, API-PERM-05): any write on a POSTED **purchase** and any edit of a CANCELLED one → 409 `invalid_transition` (`context.correction_path` for POSTED — R2-21, never 423; a repeated cancel → 200); edits and line writes on a SENT / RECEIVED / CANCELLED **transfer** → **409 `invalid_transition`** as well (reconcile 02/Oct — the same answer as a POSTED purchase, never 423 `locked`; `context.correction_path` = `receive_zero_with_reason` for a SENT one — the receiving side enters what really arrived and the reason — none for RECEIVED / CANCELLED); every other wrong order (cancel of a SENT transfer, entry on a POSTED count …) → 409 `invalid_transition`. This part answers no 423.

**P6-RULE-13 · In transit and the Stock report.** 🔒 D-STK-03, D-RPT-01 ⑩ + research E8. Quantities on SENT transfers are in **no** branch's `quantity_on_hand` (the sender is already reduced, the receiver not yet increased). Every place that asks "is there still stock?" adds them: the product archive guard (P6-RULE-05), product detail (`in_transit_quantity`), stock levels (`incoming_quantity`), the dashboard "Transfers in transit" card (AD-DSH-04) and report ⑩ (levels + low / negative, movements, usage by barber, purchases, **in transit**, short / over receipts, count differences, write-offs by reason — AD-RPT-04; Part 8 builds it from the views of this part).

**P6-RULE-14 · Nightly ledger check and recompute.** 🔒 F-P6-04 + owner H (5), ADR-002. Job **`stock.reconcile_levels`** (cron 01:30 MMT, read-only): compares every `quantity_on_hand` with Σ `stock_movements` per (branch, product) in **one SQL statement** (one snapshot — a movement committing during the run can't show as a false mismatch); any mismatch → notification **`stock.level_mismatch`** (company admins) listing the pairs, and the job result in `GET /v1/system/jobs` (P1.SYS.05). Nothing is changed automatically. **P6.STK.08** (`stock.update` for the branches touched) recomputes the cache from the ledger under the same row locks (no movement written; audit `stock.levels_recomputed` with before / after).

**P6-RULE-15 · Notifications, realtime, audit.** 🔒 D-NTF-01..03, D-AUD-01/02 + owner D6 / D9 / F12. In-app only. Types and events — §11. Audit actions (interceptor): `product_category.create / update / archive / restore / reorder`, `product.create / update / archive / restore`, `supplier.create / update / archive / restore`, `stock_adjustment_reason.create / update / disable / enable / reorder`, `stock_level.threshold_update`, `stock.levels_recomputed`, `stock.usage`, `stock.adjust`, `purchase.create / update / update_items / request_post / post / cancel` (cancel reason), `transfer.create / update / update_items / send / receive / cancel` (cancel reason), `stock_count.start / update_items / add_item / post / cancel` (cancel reason). **No DB audit trigger covers a Part 6 table** — the 18 trigger tables of DB Part 8 (D-DB-12) are money tables of Parts 4 / 5 / 7; the audit of this part = the **interceptor rows** above, and `stock_movements` is itself the append-only ledger (the DB trigger `stock_movements_no_update` refuses UPDATE / DELETE). The expense rows a purchase post creates are audited by the `expenses` trigger (Part 7). The header comment of the DB Part 6 DBML ("stock_movements, purchases → DB trigger") is superseded by this rule (independent review R2-9 / R3-4 — the DB stays as it is). Audit `branch_id` (owner F10 — a row without a branch needs company scope to read): company-master rows = none; levels, movements, usage, adjustments, counts = their branch; a purchase = its lines' branch when they all share one, else none; a transfer = the acting side (draft / send / cancel = sending branch, receive = receiving branch).

**P6-RULE-16 · Go-live stock.** Owner F5 + D-DAT-01.
