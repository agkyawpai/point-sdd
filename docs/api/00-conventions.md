## 0. How to use this document

**API-META-01 · Precedence.** (1) Appendix A 🔒 decisions → (2) `db/` DBML + constraints → (3) UX guidelines (🔒 D-UX-03 / 04) → (4) this convention → (5) each part's endpoint file → (6) the OpenAPI document (generated from code; must match the part file). A conflict with a 🔒 decision = STOP and report (🔒 D-PLT-13).

**API-META-02 · IDs.** Conventions: `API-<AREA>-nn`. Endpoints: `<part>.<module>.<nn>` (e.g. `P1.AUTH.02`), cited in OpenSpec specs, PRs and tests next to decision IDs and UX rule IDs (🔒 D-PLT-17, AD-META-02).

**API-META-03 · Tags.** 🔒 = derived from a locked decision · ⚠️ = this design's rule (binding once the part is locked) · 🟡 = owner decision pending (default stated) · ★ = owner supplies a value.

**API-META-04 · What the API is for.** One NestJS backend (🔒 D-PLT-02), one PostgreSQL database, consumed by: the staff / admin PWA (`apps/web/app/staff/` tree, host `app.<domain>`), the public website and booking modal (`apps/web/app/site/` tree, host `<domain>` — server components + client; one Next.js process, host rewrite — ADR-001), the Android / Windows shells (same web app), background jobs (pg-boss — ADR-002; each job is owned by the part whose module implements its handler — ADR-002's owner column is canonical: `email.send`, `auth.cleanup` and `sync.code_tables` = Part 1, `site.revalidate` = Part 8; review fix 02/Oct — R3-24) and the website revalidation hook. **All business rules live in the API** (review §5.2): the Next.js layer never writes to the database or computes money.

**API-META-05 · Process.** Parts are designed and locked in DB order: **0 conventions → 1 Foundation & Access → 2 Catalogue & Scheduling → 3 Customers & Booking (+ public) → 4 Visits, Sales & Payments → 5 Commission, Payroll & Attendance → 6 Inventory → 7 Finance & Closing → 8 Platform (settings, notifications, attachments, audit, import, backup, website)**. Each part = Markdown design (endpoints, rules, permission codes, events, errors) + an OpenAPI 3.1 fragment; the OpenSpec change for a module cites both (D-PLT-17).

## 1. Shape of the API

**API-SHAPE-01 · Base URL and versioning.** 🔒 (owner 01/Oct 21:20 — ADR-009) The API is served **under the same origin as the web app, on the `/api` path** (`https://app.<domain>/api/v1/…` for staff, `https://<domain>/api/v1/public/…` for the site — Caddy routes `/api/*` and the Socket.IO path `/rt` to NestJS, everything else to Next.js; ADR-009). One origin = no CORS (CORS middleware is **not registered**), no cross-site cookie, no preflight on the barber's phone. ★ domain = ACT-05. **Edge rules (v1.2):** on `<domain>` Caddy forwards only `/api/v1/public/*`, `/api/v1/health` and `/api/v1/system/status` (everything else under `/api` → 404, so no staff login or session can happen on the public host); on both hosts `/api/v1/internal/*` is reachable only from the Docker network (Caddy → 404); the web app has **no route handlers under `/api`** (its internal hook lives at `/internal/*`, also blocked at the edge). `v1` is the only version in V1; a breaking change later = `/v2` for the changed resources only. No version in headers. (Paths in this document omit the `/api` prefix.)

**API-SHAPE-02 · Three surfaces, one codebase.** ⚠️
| Surface | Prefix | Auth | Who calls it | Data rule |
| --- | --- | --- | --- | --- |
| **Staff API** | `/v1/<module>/…` | Session cookie (§2) + permission + branch scope (§3) | Staff / admin PWA, shells | Full DTOs within the caller's scope |
| **Public API** | `/v1/public/…` | None; captcha on booking create; IP rate limit (§10) | Public website server components, the booking modal, the manage-link page | **Public DTOs only** (review §5.8): no customer data, no staff phone / email, no internal notes, no prices unless the rule says so (FE-BK-05). Separate controllers and DTO classes — never reuse a staff DTO |
| **Internal API** | `/v1/internal/…` | Secret header `X-Internal-Key` (env) + Docker-network only (Caddy returns 404 from outside and strips the inbound header — ADR-009). **Two secrets (review fix 02/Oct — R3-13):** **`INTERNAL_OPS_KEY`** — held only by the API, the backup sidecar and the restore script — is the only value `/v1/internal/*` accepts; **`INTERNAL_SSR_KEY`** — held by the API and the web container — only lifts the per-IP limit on `/v1/public/*` (API-LIM-01) and opens nothing under `/v1/internal/*`, so the internet-facing web container never holds the key of the backup-run endpoints | the backup sidecar and the restore script — `POST /v1/internal/backup-runs` (kinds 1–3 only), `PATCH` and `GET /v1/internal/backup-runs/{id}` (Part 8 P8.INT.01–03 — ADR-002 / 007; v1.5); the revalidation call itself goes API → `http://web:3000/internal/revalidate` (API-PUB-03); the web container's server-side calls to `/v1/public/*` carry `X-Internal-Key: <INTERNAL_SSR_KEY>` over the Docker network only to skip the per-IP limit (API-LIM-01 v1.5) | Minimal |

**API-SHAPE-03 · Resource naming.** ⚠️ Plural nouns, kebab-case path segments, snake_case JSON fields (same names as the DB columns — D-DB-01 — so devs never translate names): `/v1/bookings`, `/v1/cash-outs`, `/v1/stock-transfers`, field `booked_employee_id`. Nested only one level for ownership (`/v1/employees/{id}/roles`). Actions that are not CRUD are **verbs as sub-resources with POST**: `POST /v1/bookings/{id}/cancel`, `POST /v1/sales/{id}/finish`, `POST /v1/daily-closings/{branch_id}/{business_date}/close` (Part 7). No `GET` with side effects.

**API-SHAPE-04 · HTTP methods and status codes.** ⚠️
| Method | Use | Success |
| --- | --- | --- |
| GET | Read; never changes state | 200 |
| POST | Create a resource or run an action | 201 (created, `Location` header) · 200 (action result) · 202 (accepted, async job) |
| PATCH | Partial update (only fields sent) | 200 (returns the full resource) |
| PUT | Replace a whole value (settings, role permission set, opening-hours week) | 200 |
| DELETE | Only for things that may really disappear (own notification, own session, draft rows the DB allows) — never transactional data (🔒 D-DAT-05). "Reset" operations that keep the row use `POST …/reset` → 200 | 204 |
Errors: 400 validation · 401 not signed in · 403 no permission / out of scope / state forbids · 404 not found or not visible in scope (same body as 403 for security where noted) · 409 conflict (slot taken, duplicate reference, status transition, idempotency replay in progress) · 422 business rule (money mismatch, a write dated on a CLOSED branch-day — `day_closed`) · 423 locked (an immutable record edited directly — CLOSED closing row, FINALIZED+ payroll run, APPROVED / automatic expense or income — and a write dated inside a finalized payroll period, `payroll_finalized`; used where the UI shows a lock banner, AD-DET-03 — v1.5; **a FINISHED / CANCELLED sale and a POSTED purchase answer 409 `invalid_transition` with `context.correction_path` instead** — review fix 02/Oct, API-ERR-02) · 429 rate limit · 503 maintenance.

**API-SHAPE-05 · JSON only.** ⚠️ `Content-Type: application/json; charset=utf-8` both ways (multipart only for `POST /v1/attachments`). Unicode Myanmar as stored (Zawgyi is converted on the client — AD-FORM-13 — and rejected by the server if detected: `error.zawgyi_text`). **Binary responses (v1.5 — Parts 4 / 5 / 8):** files are returned in their own media type with `Content-Disposition` — receipts PDF / PNG (P4.RCP.01/02), payslips PDF / XLSX (P5.RUN.16, P5.PSL.03), synchronous exports CSV / XLSX (P8.EXP.01, ≤ 5,000 rows), import templates and error-row files (P8.IMP.02 / 08) and public media images (P8.PUB.05); errors on those endpoints are still `application/problem+json`.

## 2. Authentication and sessions

**API-AUTH-01 · Session cookie.** 🔒 D-AUTH-06 (REC-05) + ⚠️. Login (Google or email OTP — D-AUTH-01) creates a `user_sessions` row and sets cookie `point_session` = random 256-bit token (base64url); the DB stores only `token_hash`. Attributes: `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=34560000` (400 days — the browser cap) and **no `Domain` attribute** (host-only for `app.<domain>`, so the public site never receives it — ADR-009 / ADR-005; v1.2 fix); "stay signed in" means the server never expires the session, and the cookie is re-issued on the first successful request after it is 30 days old so it never hits the browser cap (⚠️). `SameSite=Strict` is not used because the return from Google sign-in would drop the cookie. **Shells and the iOS PWA:** after a system-browser Google login the cookie is set inside the WebView / standalone PWA by the app's own `POST /v1/auth/handoff { verifier }` call (polled; verifier / challenge pair, no secret in URLs — ADR-005, P1.AUTH.03/04/06); the OTP path sets it directly. Every request: session `revoked_at IS NULL` AND `users.status = 1` AND `employees.status = 1` (D-DB-03) → else 401 with `reason` from `revoke_reason` (AD-AUTH-01).

**API-AUTH-02 · CSRF.** 🔒 (owner 01/Oct 21:20 — ADR-005) Cookie-based auth needs CSRF protection: every mutating request (POST / PATCH / PUT / DELETE) must carry header `X-Requested-With: point-app` and an `Origin` / `Referer` equal to the app host (`https://app.<domain>` — one value, no allow-list, since there is no cross-origin caller — ADR-009); the API rejects others with 403 `error.csrf`. No CSRF tokens in forms. The public API has no cookie, so it is exempt (captcha + rate limit instead). The Socket.IO handshake cannot carry a custom header (WebSocket upgrade), so it is checked by cookie + `Origin` only (API-RT-01).

**API-AUTH-03 · Login endpoints.** 🔒 D-AUTH-01..04, D-AUTH-08 — specified in Part 1 (`P1.AUTH.*`). Neutral responses: OTP request always returns 202 (D-AUTH-04 "same message for unknown email").

**API-AUTH-04 · Devices.** 🔒 D-AUTH-05. `GET /v1/me/sessions`, `DELETE /v1/me/sessions/{id}`; admin `POST /v1/employees/{id}/sessions/revoke-all`. A new login creates an in-app notification for the user (`login.new_device`).

**API-AUTH-05 · `GET /v1/me` is the app bootstrap.** ⚠️ One call after login (and on focus) returns everything the shell needs: user (`id`, `email`, `ui_language`), employee (`id`, names, photo, `employee_code`), **permission grants with scope** (`[{ code, scope_type, branch_ids }]`), **effective flags** (`show_own_earnings` effective value — AD-DSH-01), branches in scope, today's branch (AD-TODAY-03), `system` block (default language, maintenance flag, current time in MMT), and a `settings` block of the few keys the client needs (slot interval, advance window, currency unit rules). The client's `can()` helper (AD-PERM-03) is built from this payload; a realtime `session.updated` event tells the client to refetch it (D-ROLE-06).

**API-AUTH-06 · Maintenance mode.** 🔒 D-PLT-08. When ON, non-admin requests get 503 `error.maintenance` with `{ until?: ISO, message_mm, message_en }`; holders of `settings.update` **with company scope** pass; `GET /v1/system/status` is always public. A restore authorisation turns maintenance on (Part 8 P8-RULE-10 — v1.5); **`/v1/backups/*` (P8.BAK.01–04) also passes for a caller holding `backup.restore` through a company-scope assignment** (review fix 02/Oct — R3-16: whoever authorised a restore must be able to see and cancel it without `settings.update`).

## 3. Permissions and branch scope

**API-PERM-01 · The API decides.** 🔒 D-ROLE-03 (permission AND branch scope, backend-enforced), D-ROLE-04 (grant-only union), D-ROLE-05 (scope per assignment), D-ROLE-08 (`permissions.json` is the source — synced to the `permissions` table on deploy). The UI only mirrors (AD-PERM-01).

**API-PERM-02 · Decorators — the target's data level is declared.** ⚠️ (review §5.5) + 🔒 ADR-012 (v1.4) + v1.5 (cross-part contract 1 — owner C1 / E6 / F10 / F11; Part 4–8 reports). Every staff endpoint declares exactly one of:
- `@Can('<code>', { level: 'company' })` — **company master** target (API-PERM-07): passes only when the caller holds the code through a **company-scope** assignment; a branch-scope holder gets 403 `company_scope_required`;
- `@Can('<code>', { level: 'private' })` (v1.5 — Parts 5 / 8) — **private** target (API-PERM-07): read **and** write pass only through a **company-scope** assignment; a branch-scope holder gets 403 `company_scope_required` on single reads, writes **and lists** (a private list has no branch slice — API-PERM-03);
- `@Can('<code>', { branch: 'body.branch_id' | 'params.id→entity.branch_id' | 'query.branch_id' | 'body.items[].branch_id' })` — **branch data**: the guard resolves the **branch of the target** (from the body / query, or by loading the entity's `branch_id`; a `[]` path = every listed branch) and requires a grant whose scope covers it (`scope_type = 1 COMPANY` covers all; `2 BRANCHES` covers the listed `employee_role_branches`). A path marked optional (`'body.branch_id?'`) makes the endpoint **mixed**: empty = company master target, present = that branch (P1.SET.03 / 04); **`empty: 'private'`** (v1.5 — Part 7) declares that the empty value is a **company-wide money row** instead — read and write need company scope, branch-scope holders never see it (`@Can('expense.create', { branch: 'body.branch_id?', empty: 'private' })` — API-PERM-03 / 07). **Multi-branch targets (v1.5 — Part 6):** on a **read** a multi-branch path is **any-of** — `'entity.from_branch_id|entity.to_branch_id'` (a transfer: the sending **or** the receiving branch) or `'entity.items[].branch_id'` (a purchase: **any** line's branch) passes when one listed branch is covered, and the response hides what lies outside the grant (Part 6 partial view); on a **write** every listed branch must be covered ("every" — unchanged). **`{ branch: 'row' }`** (v1.5 — Part 8 audit log) = row-level filter: the code is needed at any scope and the query keeps each row whose own `branch_id` the grant covers (rows without a branch only for company scope; private rows only with the private code at company scope — P8-RULE-06). Employee-targeted actions use the P1-RULE-11 target set;
- `@Can('<code>', { level: 'shared' })` — **shared record** (customers): passes with the code through **any** active assignment; branch-attached history inside the response is filtered to the caller's read scope;
- `@CanView('<module>', { level? })` — **management read** (`<module>.view⁺`, any scope): branch data filtered to the grants' branches, company master returned read-only, `level: 'shared'` = the record plus history filtered to the read scope, **`level: 'private'`** (v1.5) = company scope only (403 `company_scope_required` otherwise, lists included);
- any `@Can(…)` may add **`orSelf: '<path>'`** (e.g. `'entity.booked_employee_id'`, `'entity.requested_by_user_id'`) — the endpoint also passes when that path equals the caller's employee / user (own-record rule, API-PERM-04; Part 3 own bookings, Part 7 own expense / income requests) — **or `orSelf: '<resolver>'`** (v1.5), a named **actor-set resolver** that passes when the caller is in the set it computes: Part 4 `visit.lineActors`, `sale.checkoutActors`, `visit.incompleteActors`, `sale.readers` (P4-RULE-03) · Part 6 `transfer.receiver` (the named receiver, or receiving-branch staff for an all-staff transfer — P6-RULE-01); each resolver lives in its module and is defined in that part's rules — still **one** decorator;
- **`@Staff()` + a handler policy** (v1.5 — Part 8; generalised by review fix 02/Oct — R3-9): an endpoint whose required code depends on the **data it is given** declares `@Staff()` and names, in its part's endpoint table, the **handler policy** — a function that resolves the code(s) and scope from the request and applies the same guard checks (code, level, branch scope → 403 / 404) before any work is done. Two exist: the **owning-entity policy** of attachments (P8.ATT.02..05, P8-RULE-03 table — the guard loads the attachment's `entity_type` / `entity_id` and applies that entity's read or remove right, filtered per (entity, kind): own staging rows = self; staff documents = `employee.documents`, private) and the **export policy** of P8.EXP.01 (`kind` / `key` → `data.export` **plus** the source screen's read right, or the poster's view code — P8-RULE-08). No other endpoint picks its code at run time (P1.SET.03 / 04 use `settings.update` only — `site.*` keys are read-only there and written through P8.WEB.02);
- `@Staff()` — **operational read** (any signed-in staff, data filtered to the read scope — API-PERM-03) · `@Self()` (API-PERM-04) · `@Public()` (public API) · `@Internal()`.
A missing or second decorator fails the build (lint rule) — no endpoint is accidentally open, and every endpoint table in the part files names the level; a `@Staff()` endpoint that names a handler policy must call it as its first statement (same lint rule).

**API-PERM-03 · Lists are scope-filtered, never 403 (except private lists — v1.5).** ⚠️ `GET` list endpoints silently restrict to the caller's branches (AD-PERM-04); `branch_id` outside scope → empty result, not an error. Single-resource `GET` outside scope → **404** (don't reveal existence). Actions outside scope → 403 `error.forbidden`. **v1.6 (owner S12):** this is the general answer — a caller who holds the required code, but not for the target branch, gets 403 `forbidden` (`context.required`); 403 **`out_of_scope`** is returned only where a part's endpoint text names it (for example a listed item or branch outside the grant — Parts 2, 4, 6, 8). A caller **without the required code at all** gets 403 on both management lists and actions. **Two kinds of reads (v1.3 — ADR-011 #4):** *operational reads* (what POS, booking, calendar and pickers need — e.g. services sold at a branch, the price quote, shifts, availability, the employee picker) are open to every staff member inside their **read scope** (P1-RULE-05) and need no code; *management reads* (history, scheduled / future rows, matrices, archived rows, other employees' records) need `<module>.view⁺` (API-PERM-06). Each part marks every read endpoint as one or the other. *Reference lists* every screen needs for display names — branch summaries (`P1.BR.01`), company info (`P1.CO.01`) — return all rows with no sensitive fields (role names and the permission catalogue are **not** reference lists: P1.RL.01 / P1.PERM.01 need `role.view⁺` or `employee.view`); the client narrows pickers with `/me.branches_in_scope`. **Company master read by a branch-scope holder (v1.4 — ADR-012):** any code of the module, held at any scope, opens the module's management screen read-only; write controls are hidden (AD-PERM-02, `can(code, { level: 'company' })` is false). **Exception — imports and backups (review fix 02/Oct — R3-6):** `import.run`, `backup.view` and `backup.restore` are company-level codes whose **reads need company scope too** (P8.IMP.01–08, P8.BAK.01 / 02 — a branch-scope grant gets 403 `company_scope_required`): import files hold every branch's master data and shared customers, and backup runs are system-wide operational state, not reference master data — the same rule as the jobs panel P1.SYS.05. **Private and company-wide rows (v1.5 — contract 1):** a **private** list is **not** scope-filtered — it has no branch slice, so a caller holding the code only at branch scope gets 403 `company_scope_required` on the list exactly as on single reads and writes (Part 5 pay data incl. every receivable write — `receivable.issue`, Part 8 report ⑦ and staff documents); **company-wide money rows** (expenses / manual incomes with no branch) and the **company P&L** need company scope as well, but inside a list they are simply **left out** for branch-scope callers (a single read → 404, a write → 403 `company_scope_required` — Part 7 P7-RULE-01), and so are **audit rows without a branch** and private audit rows (Part 8 P8-RULE-06). Unlike company master data, branch-scope holders never read these.

**API-PERM-04 · Own-record rules.** ⚠️ Some endpoints are allowed without a permission because the caller is the subject: own leave requests, own clock-in, own payslips (D-PAYR-07), own notifications, own sessions, own bookings list (barber), own earnings (effective flag — else 403 `earnings_hidden`) and, v1.5: own attendance history and exceptions, own advances / loans (Part 5), own visits / sales and discount requests (Part 4 self sets), own stock usage and transfers addressed to me (Part 6), own cash outs and expense / income requests (Part 7), own uploads, own exports and *My day* (Part 8). These are declared `@Self()` and documented per endpoint.

**API-PERM-05 · State checks are separate from permission checks.** ⚠️ A user with the permission may still be refused by the record's state: an immutable record edited directly (closing row CLOSED, payroll run FINALIZED+, expense / income APPROVED or automatic) → 423 `error.locked` with `{ locked_by, locked_at, correction_path }` (AD-DET-03); a wrong status order → 409 `error.invalid_transition` — **which is also the one answer for any direct write on a FINISHED / CANCELLED sale** (`context.correction_path` = `adjustment` · `refund` · `difference_sale`) **on a POSTED purchase and on a SENT / RECEIVED / CANCELLED transfer** (review fix 02/Oct — R1-25 / R2-21; transfers — reconcile 02/Oct; never 423 `locked` for these — `context { status, correction_path? }`). **v1.5:** a write dated on a CLOSED branch-day → 422 `day_closed` (Part 7 `DayLock`, `correction_path: "reopen"`); a write whose date falls in a FINALIZED / PUBLISHED / PAID payroll period → 423 `payroll_finalized` (Part 5 `PayrollLock` — API-IDEM-06) — API-ERR-02.

**API-PERM-06 · Permission codes — CRUD per menu + named special actions, composed by the admin.** 🔒 D-ROLE-01/02 (permission = module → **action**), D-ROLE-08, D-ROLE-09 + owner 01/Oct 11:54 ("Manager ရဲ့ လုပ်ပိုင်ခွင့်ကို admin က permission မှာ လိုအပ်သလို adjust") and **01/Oct 21:20** ("Menu တစ်ခုချင်းစီကို CRUD … အကုန်လုံးကို check လုပ်ထားရင် Admin; Manager ဆိုရင် သူ့အတွက် check လုပ်မယ့် ဟာပဲ") — **ADR-011** (supersedes ADR-010). The API never hard-codes what a "manager" may do.
1. **Format `<module>.<action>`, one module per menu.** Actions = **`view` · `create` · `update` · `delete`** — only those that exist for the menu (Settings = view + update; Company = view + update; Prices = view + update + delete …). **No `manage` code.**
2. **Special actions** keep their own code when they are not plain CRUD or must be grantable without edit rights: approvals (`leave.approve`, `discount.approve`, `expense.approve`, `income.approve`, `attendance.resolve`), money / irreversible steps (`sale.finish_override`, `sale.refund`, `sale.adjust`, `sale.override_price`, `sale.late_entry`, `payment.verify`, `commission.assign`, `payroll.finalize`, `payroll.pay`, `receivable.issue`, `stock.usage`, `stock.adjust`, `stock.count`, `purchase.post`, `transfer.send` / `receive`, `closing.close` / `reopen`, `cashout.return`, `backup.view` / `restore`, `import.run`, **`data.export`** — v1.5, owner F2: exporting on top of the screen's own read right), assignment (`role.assign`, `employee.branch_assign`) and field groups the admin must give separately (`<module>.<field>_update`, e.g. `employee.rating_update`; **`employee.documents`** — v1.5, private, owner F11). `cashout.create`, `expense.create` and `income.create` are plain CRUD (Part 7). **Reports (v1.5 — owner F1, contract 13):** one module per report, **`report_<key>.view`** — ① `report_sales.view` · ② `report_barber_performance.view` · ③ `report_payments.view` · ④ `report_discounts_refunds.view` · ⑤ `report_closing_cash.view` · ⑦ `report_commission_payroll.view` (private) · ⑧ `report_attendance_leave.view` · ⑨ `report_bookings_customers.view` · ⑩ `report_stock.view`; report ⑥ = **`pnl.view`** (Part 7 — replaces the placeholder `finance.pnl.view`, never deployed).
3. **`delete` never hard-deletes** (🔒 D-DAT-05) — archive, deactivate or cancel (row kept), and its undo (re-activate).
4. **`<module>.view⁺`** (notation used in every part) = `<module>.view` **or any other code of the same module** — someone allowed to edit, delete or approve can always load what they act on. Management reads require `view⁺`; operational reads require none (API-PERM-03); the UI shows a menu item when the user holds any code of that module (AD-NAV-02, AD-PERM-02).
5. **Level (v1.4 — ADR-012, replaces the v1.3 "company code only through company scope" rule).** Every code declares a **`level`** in `permissions.json`: `company` (acts only on company master), `branch` (acts only on branch data), `mixed` (acts on both — the endpoint decides per request, e.g. `service.update`, `settings.update`), `shared` (customers), **`private`** (v1.5 — contract 1, owner C1 / F11: pay data, staff documents, report ⑦ — and, review fix 02/Oct (R1-6, owner C1 + C2), **`receivable.issue`**: its endpoints return the full receivable with balance and repayments — read **and** write need a company-scope grant; a branch-scope grant of a private code reaches **nothing**, not even read-only — API-PERM-07). What a grant reaches is decided by the **data level of the target** (API-PERM-07), not by the code alone: a branch-scope grant of a company-level code gives read-only access to that module's company master and nothing else (a branch Manager still changes no company master data — 🔒 D-ROLE-07; shared records are the deliberate exception: a `customer.*` holder at any scope edits the one company-wide customer row — D-CUS-01, ADR-012); a branch code is effective for the branches of its assignment (all branches with company scope — D-ROLE-05). Each part lists the codes it adds with module, action, kind (`crud` / `special`), level and the typical holder; `permissions.json` is assembled part by part and codes are never renamed after deploy (D-ROLE-08).
6. **Seed roles = Admin / Manager / Barber** (D-ROLE-09): Admin = every code, company scope; Manager = the codes whose "Seed" entry in each part's code table names Manager, branch scope (each grant reaches what the target's level allows — #5); Barber = the codes the parts mark for barbers (Part 3: `booking.view`, `customer.view`, `customer.create` · Part 4: `sale.late_entry`, `sale.create` · Part 6: `stock.usage`; Parts 1 / 2 / 5 / 7 / 8: none — v1.5) — own data and operational reads need none. The admin edits them freely in the matrix (AD-PERM-07).
7. **Guard rails fixed in code regardless of role** (P1-RULE-12): a **company-admin role** = a role containing **all five** role codes `role.view` + `role.create` + `role.update` + `role.delete` + `role.assign` (owner #25 = A); a **company admin** = a user with an active company-scope assignment of such a role. (a) **No privilege escalation** — a caller who is *not* a company admin can grant only codes they hold and only branch scopes inside their own; company admins can grant any catalogue code (otherwise a code deployed by a new part could never be granted). (b) **No last-admin lockout** — the last active company admin cannot be deactivated, cannot have the qualifying assignment revoked, none of the five role codes can be removed from that role, and the role cannot be archived (409 `last_admin` on P1.EMP.05 / P1.EMP.11b / P1.RL.05 / P1.RL.06). (c) On deploy, `sync.code_tables` adds every **new** code to each company-admin role (audited as `role.permissions_set` by the system actor — ⚠️ default on; the admin may untick afterwards).

**API-PERM-07 · Data levels (v1.4 — 🔒 owner choice A, ADR-012; v1.5 — + `private`, contract 1).** Every endpoint target is one of four levels; each part's endpoint tables name it:
| Level | What it is | Write passes when … | Management read (`view⁺`) |
| --- | --- | --- | --- |

| **Private** (v1.5 — contract 1, owner C1 / F11) | Company-only data no branch manager may see: commission plans, assignments and figures, payroll runs / entries / admin payslips, salaries, allocation shares, payroll categories, receivable reads and balances **and every receivable write — issue, change, cash repayment, cancel: `receivable.issue`** (Part 5 — review fix 02/Oct, R1-6; also needed to edit or cancel a staff-advance cash out in Part 7), report ⑦ `report_commission_payroll.view`, staff documents `employee.documents` and the audit rows of these tables (Part 8) | the code is held through a **company-scope** assignment — otherwise 403 `company_scope_required` | **company scope only** — a branch-scope grant reaches nothing, not even read-only; lists answer 403 too (not scope-filtered — API-PERM-03) |

**Company-wide rows (v1.5 — contract 1, owner E6 / F10):** expenses and manual incomes with `branch_id` NULL and the company P&L (Part 7), and audit rows without a branch (Part 8), need company scope to read **and** write; branch-scope holders never see them (lists leave them out, a single read → 404, a write → 403 `company_scope_required`). SALARY-category expense rows also need company-scope `payroll.view` (private — Part 7 P7-RULE-01); a branch P&L shows salary as one total line (owner E6).

No-escalation (#7 a) also covers scope: a non-admin may assign only branches inside their own grant of the code.

## 4. Data conventions

**API-DATA-01 · Identifiers.** 🔒 D-DB-01 UUIDv7, generated by the API (clients never choose ids; the only client-generated values are `client_request_id` / `Idempotency-Key` and the booking manage token — §6).

**API-DATA-02 · Money.** 🔒 D-PLT-04 whole MMK. JSON **integer** (never float, never string) in fields ending `_amount`. Rates are JSON numbers **exactly as the DB stores them** (v1.5 — Part 5 P5-RULE-20; v1.4 said "≤ 2 decimals"): `numeric(5,2)` for `service_charge_rate`, `tax_rate` (Part 4) and commission tier `rate_percent` (≤ 2 decimals); `numeric(7,4)` for `effective_rate_percent`, EARN / REVERSAL line `rate_percent` and allocation `ratio` (4 decimals — Part 5); the server never does arithmetic on floats (bigint / decimal library). Totals are always computed by the server; a client-sent total is ignored or validated (`error.amount_mismatch`).

**API-DATA-03 · Dates and times.** 🔒 D-PLT-05, D-PLT-15. Timestamps `*_at` = ISO 8601 with explicit offset, always rendered in Myanmar Time: `2026-10-01T14:30:00+06:30` (the API accepts any offset in input and normalises). Business dates `*_date` = `YYYY-MM-DD` (MMT). Times of day (opening hours, shift patterns) = `HH:mm` 24-hour on the wire (the formatter renders 12-hour — AD-FMT-03). `business_date` is **computed by the server** from the event time. **Client-sent times / dates (v1.5 — Parts 4–7)** are accepted only where a part allows them and are always validated: late entry times `started_at` / `completed_at` / `received_at` / `finished_at` (Part 4 — any business date of the branch that is **not closed**, owner B11 / 🔒 D-VIS-13) · cash out `occurred_at` and cash return `returned_at` (Part 7 — any earlier time on a not-closed day, never in the future — D-FIN-07) · `expense_date` / `income_date` (Part 7 — ≤ today, no lower bound) · purchase `purchased_at` (Part 6 — ≤ now) · manual attendance times (Part 5 — ≤ now, outside finalized payroll periods) · payroll `paid_at` (Part 5 — between publish and now). A future value → 422 `date_in_future`; a CLOSED branch-day → 422 `day_closed` (API-ERR-02).

**API-DATA-04 · Status and type codes.** 🔒 D-DB-03 + owner 01/Oct 21:20 (§12 #6). On the wire = the **smallint code** (e.g. `"status": 2`), with `x-enum-varnames` in OpenAPI so generated clients get `BookingStatus.STARTED`; labels come from the language file (`status.<table>.<CONST>`). Never strings on the wire (one source of truth).

**API-DATA-05 · Bilingual fields.** 🔒 D-DB-04. Both `*_mm` and `*_en` are returned as stored (EN may be null); the client applies the fallback (AD-L10N-03). Inputs: `*_mm` required, `*_en` optional. Free-text fields are single. The public API also returns both (the site renders per locale).

**API-DATA-06 · Phone numbers.** 🔒 D-CUS-02. Input accepts any format; the API normalises to E.164 (`phone_normalized`) and stores what was typed (`phone`). Responses include both; staff DTOs show `phone`, public DTOs never include customer phones (the manage page masks: `09•••••123` is produced by the API as `phone_masked`).

**API-DATA-07 · Snapshots.** 🔒 D-SVC-04, Part 3 / 4. Line items carry their snapshot fields (`unit_price_amount`, `duration_minutes`, `description_mm/en`) in responses; price lookups are server-side (`POST /v1/prices/quote`, Part 2 P2-RULE-05) — clients never send prices for services, only for explicit overrides with a reason (D-SVC-04, `sale.override_price`); a booked service done by another barber is charged the lower of the booking snapshot and that barber's quote (Part 4 P4-RULE-05, owner B4 — v1.5).

**API-DATA-08 · Pagination, filtering, sorting.** ⚠️ (AD-LIST-05) Lists are cursor-paginated: `?limit=25&cursor=<opaque>` → `{ "items": [...], "next_cursor": "..." | null, "total": n | null }` (`total` only when cheap). Filters are plain query params named like the fields (`branch_id`, `status` (repeatable), `from`, `to` = business dates, `q` = search text, `employee_id`). Sorting `?sort=-starts_at,customer_name` (prefix `-` = descending); each endpoint lists its allowed sort keys. Date presets are a client concern.

**API-DATA-09 · Search.** 🔒 D-SRC-01 + ⚠️. `GET /v1/search?q=` returns grouped results within scope (customers, bookings, sales by receipt number, employees); barber-like callers get customers + bookings only. Phone search normalises first (AD-NAV-05). **`sales` group (v1.5 — Part 4 P4-RULE-18):** `[{ id, receipt_number, finished_at, branch_id, total_amount }]` for `sale.view⁺` holders, exact or prefix receipt number; callers without it use the receipt lookup P4.RCP.03.

**API-DATA-10 · Responses are complete resources.** ⚠️ Create / update / action responses return the full resource as `GET` would (plus `warnings: []` where the UI shows non-blocking notes — e.g. printer, negative stock). Lists return list DTOs (fewer fields); detail returns detail DTOs; `?include=` is not used (keep it predictable). **Shared warning codes (review fix 02/Oct):** `previous_month_pnl { date }` (a write dated in an earlier month's P&L — Parts 6 and 7, one name) · `payroll_finalized_period { run_id, period: { start, end } }` (Part 7 day reopen inside a finalized payroll period — allowed, cash corrections may still be needed) · `pending_leaves { count }` (Part 5 finalize — PENDING leaves inside the period) · `reopened_not_recalculated` (Part 5 — a reopened payroll run until its next Calculate; no context).

**API-DATA-11 · Reasons.** 🔒 (AD-RSN-02 table) Every action that requires a reason takes it in the body per the reason source (master list id / preset code / free text) and the API enforces "note required" (`requires_note`, OTHER). Missing → 400 `error.reason_required`. **v1.6 (owner S8):** the **field names are the ones the endpoint's part and OpenAPI document define** — a master-list reason as its id, a preset as its code, a free-text reason as the endpoint's own text field (Part 4: `reason`, `added_reason`, `override_reason`, …). `{ reason_id?, reason_code?, note? }` is the generic result of the shared reason dialog (AD-RSN-02); the calling screen maps it to the endpoint's fields. No endpoint changed.

## 5. Errors

**API-ERR-01 · Format.** ⚠️ RFC 9457 problem details, `Content-Type: application/problem+json`:
```json
{
  "type": "https://point.example/errors/slot_taken",
  "title": "Slot taken",
  "status": 409,
  "code": "slot_taken",
  "detail": "This time was just booked.",
  "errors": [ { "field": "starts_at", "code": "slot_taken", "params": { "next_free": ["2026-10-07T10:30:00+06:30"] } } ],
  "request_id": "0199a3f2-7c1e-7b3a-9d4e-2f6a8c1b5e70"
}
```
- `code` = the key under `error.*` in the language files (AD-FORM-04, FE-BK-11); `detail` is an English developer string, **never shown to users**.
- `errors[]` = field-level items for 400 / 422, each with `field` (JSON pointer-ish dotted path, e.g. `items[1].quantity`), `code` and `params` for message interpolation.
- `request_id` = a **server-generated UUIDv7**, one per request (review fix 02/Oct — R3-2). A client `X-Request-Id` is used instead **only when it parses as a UUID**; any other value is ignored (never an error). The id is returned in the `X-Request-Id` response header, written to logs and set as `app.request_id` for the transaction — `audit_events.request_id` is a `uuid` column and the DB audit trigger casts the setting without a guard (DB Part 8 constraints), so a non-UUID value must never reach it.
- **`context`** (v1.4 — RFC 9457 extension member, optional object) carries machine data a code needs, e.g. `price_changed` → the new quote, `already_exists` → the existing id (Part 3 §9).

## 6. Idempotency and concurrency

**API-IDEM-01 · Row-creating money endpoints require `Idempotency-Key`; state-based actions need none.** 🔒 D-VIS-10 + ⚠️ (AD-NET-01) + **v1.5 wording** (cross-part contract 15 — owner one-sheet G: the new `client_request_id` columns). The header value is the client's `client_request_id` (UUID v4/v7, one per logical submit), stored in the created row. **Required on** the endpoints whose main purpose is to create a money / stock row the client asked for, each storing the key in that row's `client_request_id` — the **final list** (v1.5, checked against the Part 4–8 OpenAPI documents; rows written as a side effect of a state change — e.g. stock movements at FINISH, the purchase expense at post — carry no client key; where such a row's table requires `client_request_id` — the automatic over-transfer change refund at FINISH, `refunds.client_request_id` NOT NULL UNIQUE — the server generates a UUIDv7 and a FINISH replay creates no second row: Part 4 P4-RULE-10, review fix 02/Oct — R3-12): Part 4 — `POST /v1/visits` (START), `POST /v1/sales` (product-only sale), `POST /v1/sales/{id}/difference-sale`, `POST /v1/sales/{id}/payments`, `POST /v1/refunds` · Part 5 — `POST /v1/receivables`, `POST /v1/receivables/{id}/repayments` · Part 6 — `POST /v1/stock-usages`, `POST /v1/stock-adjustments` · Part 7 — `POST /v1/cash-outs`, `POST /v1/cash-outs/{id}/returns` (cash return), `POST /v1/expenses`, `POST /v1/manual-incomes` · Part 8 — none (no money rows). Missing header → 400 `error.idempotency_key_required`. **State-based actions are safe to repeat without a key:** FINISH (`POST /v1/sales/{id}/finish` — removed from the v1.4 list), COMPLETE / INCOMPLETE, purchase post, count post, transfer send / receive, day close (a day **reopen** is the listed exception — a repeat answers 409 `invalid_transition`, Part 7 P7-RULE-07), payroll finalize / publish / mark paid / reopen, approve / reject, verify / unverify, cancel and delete — the row is locked `FOR UPDATE`; a repeat answers **200 with the current state**, a state that moved on answers 409 `invalid_transition` (API-IDEM-02). Drafts (purchase, transfer, count start) and POS line adds carry no key either: a duplicate is visible and removed with a reason (AD-NET-01).

**API-IDEM-02 · Replay semantics.** ⚠️ The key is stored in the row's `client_request_id` (unique index — Parts 4 / 5 / 6 / 7; START stores the same key on the visit **and** its sale; `stock_movements` uses a partial unique index — DB Part 6 v1.2). A retry with the same key: if the first request finished → **200 with the same resource** (not 201) and header `Idempotent-Replayed: true`; if it is still running (unique-index wait / advisory lock on the key) → 409 `idempotency_in_progress` (client waits and retries); if the key was used with a request whose **identifying fields differ** from the stored row (e.g. a payment with the same key but a different `amount` or `sale_id`) → 422 `idempotency_mismatch` (same code for the booking token — API-IDEM-03). There is no generic `idempotency_keys` table and no stored request hash (D-DB-12) — the rows themselves are the record, so mismatch detection compares the identifying fields each part lists, not the whole body. Only row-creating endpoints are idempotent this way; actions on existing rows (finish, close, post, finalize …) are naturally idempotent by state check (second call → 200 current state, or 409 `invalid_transition` where the state moved on — the list in API-IDEM-01). **Natural-key replays (v1.5)** where a table has no `client_request_id`: a Part 4 sale adjustment whose target already has the requested effective value → 200, no new row (P4-RULE-15); a Part 5 clock-in / clock-out repeated within 120 s → 200 with the same record (P5-RULE-13); a Part 8 internal backup-run report with the same sidecar `id` → 200 (P8-RULE-09). "Was it saved?" = `GET /v1/me/requests/{client_request_id}` (Part 4 P4.REQ.01 — AD-NET-02).

**API-IDEM-03 · Booking create.** 🔒 **Option A — ADR-004 (owner asked "which is better" 01/Oct 11:54; accepted 01/Oct 21:20).** `bookings` has no `client_request_id` (D-VIS-10 scope). Option A: the client generates the **manage token** (32 random bytes from `crypto.getRandomValues`, base64url, validated server-side for length / alphabet) and sends it as `manage_token`; the server stores `sha256(token)` in `manage_token_hash` (already unique). A retry with the same token returns the existing booking (200 + `Idempotent-Replayed: true`) — **including `manage_url`, which the API builds from the raw token it received, on the first response and on every replay** — instead of hitting `slot_taken` / `active_booking_exists`; the same token with different identifying fields (branch, barber, start time, phone) → 422 `idempotency_mismatch`. Option B (new column `bookings.client_request_id`, server-generated token) is idempotent too, but on a replay the server can only return the *hash* it stored, so the customer's one-time link is lost exactly in the case idempotency exists for (a lost reply). That is why A is recommended: one mechanism solves both problems and the DB stays at Part 3 v3. The token is shown once (FE-CONF-02, AD-BKG-02) and never logged.

**API-IDEM-04 · Optimistic concurrency on edits.** ⚠️ Mutable master records (employee, service, role, settings, bookings before start) carry `updated_at`; `PATCH` may send `If-Unmodified-Since` / body `expected_updated_at`; a mismatch → 409 `conflict` so the UI can show "Updated by Ko Min just now — Reload" (AD-RT-02). Not required for POS actions (state machine protects them).

**API-IDEM-05 · DB does the final word.** 🔒 §5.4 patterns. Slot exclusion (D-BKG-08), gapless receipt numbers (D-PAY-06, row lock), one open count per branch, unique KBZPay reference — the API maps the DB error to the matching `code` (e.g. exclusion violation → 409 `slot_taken` + nearest free times, AD-CAL-05).

**API-IDEM-06 · Cross-part transaction contracts — lock order, isolation, `PayrollLock`.** ⚠️ (review fix 02/Oct/2026 — R1-1 / R1-8 / R1-9, R2-1; binding for Parts 2 and 4–8, system design §3.6, ADR-015).
- **One lock order in every part.** A transaction takes only the locks it needs, but never out of this order: **(1) day lock** — Part 7 `DayLock`, a transaction-scoped advisory lock per (branch, business date): **shared** for writers (`assertOpen` → 422 `day_closed`), **exclusive for day close and reopen, taken as the first statement of the transaction** → **(2) payroll lock** — Part 5 `PayrollLock`, a transaction-scoped advisory lock per company payroll: shared for writers, exclusive for finalize / reopen → **(3) row locks** (`SELECT … FOR UPDATE`): **sale → visit → booking → payments → receipt counter → cash-out / closing rows → stock-level rows last** (Part 6 locks them sorted by (`branch_id`, `product_id`)). Rows a single part adds keep the position that part states, inside this order: Part 4 — discount code → customer after the booking, and the KBZPay-reference advisory lock with the payments (P4-RULE-09 / 10); Part 7 — cash-return, expense and income rows with the cash-out / closing rows (P7-RULE-02 / 18); Part 6 — the purchase / transfer / count header just before the stock-level rows (P6-RULE-02) — always after the two advisory locks and before the stock-level rows. Each part numbers the steps of its transactions so that the text order **is** the lock order.
- **Isolation.** Every transaction that writes money, stock or pay data — **day close and reopen included** — runs **READ COMMITTED**, takes its locks first (order above) and makes **every check after the locks**, so each check sees everything committed before the lock was granted. **`REPEATABLE READ READ ONLY` is for previews, reports, exports and dashboards only** (ADR-015) — never for a transaction that takes a lock or writes: PostgreSQL fixes a REPEATABLE READ snapshot at the transaction's first statement, which would be the advisory-lock call itself — before the wait — so a payment committed while a close waited for the lock would be invisible to its checks.
- **`PayrollLock.assertNotFinalized(tx, { employee_ids?, dates })`** (Part 5 P5-RULE-10) takes the **shared** payroll advisory lock and then answers **423 `payroll_finalized { employee_id, run_id, period: { start, end }, status }`** when a date lies inside the period of a FINALIZED / PUBLISHED / PAID run (for the listed employees; every employee when the list is omitted). **Finalize and reopen take the same lock exclusive**, so no correction can commit between finalize's checks and its commit. Callers: **Part 2** — shift writes (P2.SHF.03 / 04 / 05 / 08) and leave create / edit / approve / reject / cancel touching such dates · **Part 4** — late-entry START, FINISH of any sale with SERVICE lines whose business date is in such a period (the correction is a manual payroll line — owner B9) and the PERFORMER adjustment · **Part 5** — attendance writes, salary and plan rows. `AttendanceDetector.redetect` skips dates in finalized periods. A Part 7 day **reopen** is allowed inside a finalized period and answers with the warning `payroll_finalized_period { run_id, period }`; finalize adds the run warning `pending_leaves { count }`.

## 7. Audit and request context

**API-AUD-01 · Automatic.** 🔒 D-AUD-01 / 02 + ⚠️ (review §5.5). Each request runs in a transaction with `SET LOCAL app.user_id`, `app.session_id`, `app.request_id` so the Part 8 DB triggers attribute money-table changes (`source = 2 DB_TRIGGER`). An interceptor additionally writes one `audit_events` row with `source = 1 APP` for every **action endpoint** (`action` = the permission code or `<entity>.<verb>`, e.g. `booking.cancel`), including `reason` and `branch_id`, plus login success / failure (D-AUTH). **`branch_id` of an app row — one rule for every part (review fix 02/Oct — R3-5):** the interceptor writes the **single branch the request acted on** — the one branch the guard resolved from the endpoint's `{ branch: … }` path, or the `branch_id` of the loaded / created entity when there is exactly one (a transfer = the acting side; a purchase = its lines' branch when they all share one). **Employee-targeted actions (reconcile 02/Oct — 🔒 D-AUD-01 "manager = assigned branch"):** an action whose target is an employee — employee update / status, role assign / revoke, rating, invites, sessions, leave, attendance, shift, pattern — writes the branch the request acted on when the endpoint has one (a shift, or an attendance record / exception → that shift's or record's branch; a branch assignment → the assignment's branch), otherwise the employee's **primary branch** (the active assignment with the earliest `effective_from` — the definition Part 5 P5-RULE-04 uses for payroll allocation, = `/me.assigned_branch_ids[0]`); an employee with **no active assignment → NULL**. In **every other case it is NULL** — company-master, private and shared targets (roles, company settings, customers, pay data), requests touching several branches, logins, jobs without a branch. Rows with a NULL `branch_id` are read at company scope only — except by their own author: an `audit.view` holder always sees the rows they authored themselves (Part 8 P8-RULE-06, owner F10; private rows keep their own rule). DB-trigger rows take the row's own `branch_id` column when the table has one (DB Part 8 trigger). Reads are not audited — **except** (v1.5 — Part 8) signed URLs of staff documents (`employee.document_view`, owner F11); every export, synchronous or not, is an audited action (`export.run { kind, key, format, query, row_count }` — D-DAT-02). Jobs write `source = 3 SYSTEM_JOB` rows. Secrets never reach `audit_events` (token / code hashes, attendance QR tokens, `manage_token` / `captcha_token` — Part 3 P3-RULE-10, Part 5 P5-RULE-17, Part 8 P8-RULE-06).

## 8. Realtime (Socket.IO)

**API-RT-01 · One socket, cookie auth.** 🔒 D-NTF-01 + ADR-008 (accepted 01/Oct 21:20). Engine.IO **path `/rt`** (default namespace — a Socket.IO *namespace* would keep the HTTP path at `/socket.io/`, which Caddy routes to Next.js; v1.2 fix), authenticated with the same session cookie + `Origin` check (no custom header on a WebSocket upgrade; the client also sends `auth: { client: 'point-app' }`); handshake rejected 401 if invalid; a revoked session is disconnected within seconds by the revoke handler. Rooms are joined server-side: `user:<user_id>`, `branch:<branch_id>` for each branch in the caller's **read scope** (P1-RULE-05 v1.3 — assignments ∪ grants, so a barber with no code still receives their branches' events), `company` for users with any company-scope grant. Clients never choose rooms. **Targeted user rooms (v1.5):** when data must not reach every staff member of a branch, a part emits to the `user:` rooms of a computed recipient set instead of (or besides) the branch room — attendance (the employee + `attendance.view` / `attendance.resolve` holders covering the branch) and pay data (company-scope `payroll.*` holders — never the `company` room, private) in Part 5, SALARY-category expenses in Part 7, discount-request approvers in Part 4, low-stock recipients and transfer receivers in Part 6 (API-RT-03).

**API-RT-02 · Event envelope.** ⚠️ `{ "event": "booking.updated", "at": "…+06:30", "branch_id": "…", "entity_type": "bookings", "entity_id": "…", "actor_user_id": "…" | null, "data": { …minimal fields… } }`. Payloads are small; the client refetches the resource (TanStack Query invalidation — AD-PERF-03). **No event carries an amount** — every event of every part (Parts 1–8) sends ids + status only, never a money field (`*_amount`, money totals or balances — counts such as `total_rows` are fine); the client refetches the authorised resource (ADR-008 Consequences "ids only, then an authorised refetch"; reconciled 02/Oct — Part 4 §10, Part 5 §15, Part 6 §11 payloads made ids-only; P5-RULE-19, P7-RULE-19). Events are emitted **after commit** from the same interceptor that audits (no outbox table — D-DB-12; the emit is best-effort and the 5-minute / focus refetch is the safety net).

## 10. Rate limits, captcha, size limits

**API-LIM-01 · Public.** 🔒 D-BKG-21 + owner 01/Oct 21:20 (§12 #3, #5). Booking create: invisible captcha **Cloudflare Turnstile** (no Google account needed, free) verified server-side, plus **10 bookings / hour / IP** (setting `booking.public_rate_limit_per_hour`, default 10 — the owner may change it later in Settings, FE-SEC-03) and **3 / hour / phone number**. Availability: 120 requests / minute / IP. **Public media (P8.PUB.05): its own limit of 600 requests / minute / IP** (review fix 02/Oct — R3-8: browsers fetch every image of a page directly, so the JSON limit would break a branch page). Everything else public: 60 / minute / IP. 429 includes `retry_after`. **A request that carries a valid staff session is not IP-limited** on these paths (several staff phones share one shop Wi-Fi address — the per-session cap of API-LIM-03 applies instead). **SSR exemption (v1.5 — Part 8 P8-RULE-13):** server-side requests from the web container (`http://api:3001` over the Docker network, header `X-Internal-Key` = **`INTERNAL_SSR_KEY`** — API-SHAPE-02) are exempt from the per-IP limits — otherwise every server render shares one IP and the site would throttle itself; browsers never hold the key, and this key opens nothing under `/v1/internal/*`.

**API-LIM-02 · Auth.** 🔒 D-AUTH-04. OTP request: 1 per 60 s per email, 10 per hour per IP; OTP verify: 5 consecutive failures → lock 20 minutes (`login_locked_until`). **v1.6 (owner S9):** OTP verify also has a per-IP cap — **10 verify attempts per hour per IP → 429 `rate_limited` (`retry_after`)**, counted **before** any look-up, failure-counter change or audit write: the 10th attempt in the hour is processed, the 11th is refused and writes no `login.failed` row (otherwise one unauthenticated machine could lock every known staff address every 20 minutes and write unlimited audit rows). P1.AUTH.06 (hand-off) is limited the same way.

**API-LIM-03 · Staff API.** ⚠️ No per-user throttling in V1 beyond a global 600 / minute / session safety cap; uploads ≤ setting `system.upload_max_mb` (default 10 MB; Caddy caps the body at the limit + 1 MB); list `limit` ≤ 100. **v1.5 (Part 8, owner F3 / H):** upload types are checked by **file signature** (magic bytes), never by the extension (422 `file_type_not_allowed`); CSV has no signature — it passes a text test instead (valid UTF-8 / UTF-16, no NUL byte — Part 8 P8-RULE-03, review fix 02/Oct). **Fixed limits (code, not settings):** exports ≤ 50,000 rows (CSV / XLSX), synchronous ≤ 5,000 rows, PDF = summary + the first 1,000 detail rows; import ≤ 10,000 rows; report and audit ranges ≤ 366 days (closings list ≤ 92 days, P&L trend ≤ 12 months); report statement timeout 15 s; staff documents ≤ 20 per employee; signed URLs 5 minutes; staging uploads and background export files 24 h.
