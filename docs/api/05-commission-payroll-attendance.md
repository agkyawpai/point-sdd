## 1. Rules specific to this part

**P5-RULE-01 · Pay data is private (company scope only).** 🔒 owner **C1** + cross-part contract 1 (ADR-012 amendment), D-ROLE-07. Level **`private`** = read **and** write need the code through a **company-scope** assignment; a branch-scope grant of a private code reaches **nothing** — not even read-only, unlike company master (API-PERM-03 v1.4) — and is answered **403 `company_scope_required`** on lists too (a private list is not scope-filtered: there is no branch slice of it). Private here: every `commission.*`, `payroll.*`, `payroll_category.*` endpoint, salary history, branch-allocation shares, receivables — reads, balances **and the writes of `receivable.issue`** (review R1-6: owner C1 "advances = Admin only") —, the payroll outstanding list, admin payslips, report ⑦ (Part 8 `report_commission_payroll.view`) and audit rows of these tables (owner F10 — Part 8). Decorator `@Can(code, { level: 'private' })` / `@CanView(module, { level: 'private' })` (Part 0 amendment). The UI shows *Payroll* / *Commission plans* / *Payroll categories* only with a company-scope grant (AD-PERM-07 level hint *Private*). Own data stays open without a code (API-PERM-04 — P5-RULE-18).

**P5-RULE-02 · One commission engine.** 🔒 D-COM-01..04, F-P5-02/10, owner **C5 / C6 / C12**, contract 9. One module computes every figure (checkout estimate, *My earnings*, preview, payroll) from the same inputs:
- **Base** (🔒 D-COM-02/03): SERVICE lines of **FINISHED** sales (`line_total_amount` = net of discount — the transport-fee line never counts) whose **effective performer** (Part 4 `EffectiveSale` — latest PERFORMER adjustment) is the employee, sale `business_date` inside the window; refund items existing at calculation time (for a payroll run: of refunds recorded up to its `calculated_at`) reduce the line: **net base = `line_total_amount` − Σ those refund items, and a line whose net base ≤ 0 produces no EARN line** — a 100 % discount, a price override to 0, a 0-priced service or a fully refunded line (DB CHECK: an EARN line needs `base_amount > 0`; review R1-5). Difference sales count for the original barber (Part 4 P4-RULE-12).
- **Assignments** (🔒 D-COM-01, F-P5-01): `branch_id` null = sales of every branch added together; a branch row = that branch's sales only. Window = the assignment's days inside the period — **a plan that starts on 15/Oct counts sales from 15/Oct; thresholds are never prorated** (owner C5). No assignment = no commission (basic only). One result per (run, assignment) (F-P5-10).
- **Tiers** progressive: `commission = Σ_tier (min(base, to) − from)⁺ × rate`, rounded half-up to whole kyat per tier, `tier_breakdown` snapshot `[{ tier_order, from_amount, to_amount, rate_percent, base_amount, commission_amount }]`; `effective_rate_percent = commission ÷ base` (4 decimals — F-P5-02), **0 when the base is 0** (a REVERSAL-only result); EARN line commission = `base × effective rate` with **largest-remainder** rounding so Σ lines = the result (P5-RULE-20).
- **Estimate** — `Commission.estimate(employee_id, business_date, base_amount, branch_id, before?)` (Part 4 checkout, P5.CMS.02; review R1-18 / R1-29). **Window = the payroll period that contains `business_date`**: MONTHLY (🔒 D-PAYR-01 default) = the calendar month; for another `payroll.period_type` = the run covering the date, else the period that follows the latest run (`period_end + 1`, same length), else the calendar month. **Assignment** = the one active **on `business_date`** that covers `branch_id`. **PTD** (period-to-date base) = the employee's commissionable base in that window from sales with `finished_at < before`; `before` omitted = everything finished so far (an OPEN sale). Result: **marginal** = `tiers(PTD + base) − tiers(PTD)`. Example (owner C12): PTD 2,240,000 + a 30,000 cut → 10,000 × 15 % + 20,000 × 20 % = **5,500**; because every sale's PTD stops at its own `finished_at`, a finished sale's estimate never drifts and the estimates of a period add up to the final figure when nothing is refunded. Never stored (DB Part 4 note). Shown only to the performer whose **effective own-earnings flag** is ON (P1-RULE-06, 🔒 D-DSH-03 / D-COM-04).
- **Refund after finalize** (🔒 D-COM-04 v5.1, OPEN-26): a `refund_items` row whose sale line has an EARN line in a **FINALIZED+** run, and whose refund was recorded after that run's `calculated_at`, becomes a **REVERSAL** line in the run whose period contains the refund's business date: `base = −refund amount`, `rate = the original line's rate`, linked by `original_line_id`; the old payslip never changes; the payslip label is "28/Oct Hair dye refund — 6,000". If the employee has no assignment in that period the REVERSAL hangs on a result keyed by the **original** assignment (commissionable 0, rate 0). A refund recorded **before the sale's period is finalized** just reduces the base: it changes the run's inputs, so a CALCULATED run turns stale and is recalculated (P5-RULE-09 c).
- **Carry** (owner C6; review R1-2): `reversal_outstanding(employee) = max(0, Σ |REVERSAL commission| in FINALIZED+ runs − Σ amount of the **AUTO** COMMISSION_REVERSAL payroll lines in FINALIZED+ runs)` — AUTO = `source` 1 of the system category COMMISSION_REVERSAL (one per entry; `commission_result_id` set whenever the run has REVERSAL lines of its own). **MANUAL lines never count** — a B9 correction line (P5.RUN.07) is not a collection of this debt. Each run's AUTO line = this run's REVERSALs + the carry, limited by the cap (P5-RULE-08); what the cap — or a **downward override** of that AUTO line (`amount < auto_amount`, with its reason) — leaves uncollected **stays outstanding** and returns in the next run (deferred, not forgiven); an upward override can never push the figure below 0.

**P5-RULE-03 · Plans and assignments are effective-dated history.** 🔒 D-COM-01, AD-PAY-04, F-P5-01, contract 3.
- **Plan tiers:** `tier_order` 1..n contiguous — first `from_amount = 0`, each `from = previous to`, last `to = null`, rates 0–100 with ≤ 2 decimals (else 422 `tiers_invalid { reason }`). A plan referenced by any assignment is **in use**: its tiers never change (409 `plan_in_use` → P5.COM.05 *Create a new version* copies it with new tiers, name suffixed "v2" unless given); name / description / status stay editable. Archive is refused while an assignment is open or future (409 `plan_in_use`). INACTIVE / archived plans can't be newly assigned (422 `plan_inactive`). Seed: "Point ပုံမှန်" 0 → 2,250,000 = 15 %, 2,250,000 → ∞ = 20 % (D-COM-01 — go-live data).
- **Assignment writes** (per key = employee + scope) follow the P2-RULE-04 algorithm: same `effective_from` → update in place; otherwise the row effective on the new date is closed at `new − 1` and the new row runs to the next later row − 1 (or open). Unlike Part 2, **`effective_from` may be in the past** (an employee who qualified on 15/Oct is entered on 20/Oct — owner C5) but never on or before the **end of the last finalized period** (`PayrollLock` → 423 `payroll_finalized`). The DB EXCLUDE refuses the same scope twice (409 `assignment_overlap`); an all-branch row and a branch row on the same days → 409 `assignment_scope_conflict` (app — F-P5-01); a branch row needs the employee assigned to that branch on `effective_from` (422 `not_assigned_to_branch`). Ending = PATCH `effective_to` (≥ the last finalized period end).
- **Withdraw** (P5.CPA.04 — a wrong row): only when the row is **unused** — not referenced by a `commission_results` row of a **FINALIZED / PUBLISHED / PAID** run (the result of a DRAFT / CALCULATED working run does not count: that run turns stale and is recalculated — review R1-3) — and starts after the last finalized period (else 409 `assignment_in_use` / 423 `payroll_finalized`). Effect: the row no longer applies and the previous row's `effective_to` is re-linked. **Mechanism = archive (🔒 owner 02/Oct/2026 — OPEN-40 OK, (b) = B):** DB Part 5 **v1.2** gives `employee_commission_plans` and `employee_salaries` `archived_at` + `archived_by_user_id` + `archive_reason`, and their overlap EXCLUDE constraints ignore archived rows (`WHERE archived_at IS NULL` — the pattern the owner approved for DB Part 2 v1.3): the row is **archived** (at = now, by = the actor, reason = the request's `reason`), **never deleted** — 🔒 D-DAT-05 / API-PERM-06 #3 hold. Order inside the transaction: **archive first, then re-link** the previous row's `effective_to` (or insert the corrected row) — the EXCLUDE is checked per statement, so the reverse order is refused by the database (DB Part 5 v1.2 tests). An archived row is left out of every list, picker and calculation; it stays readable through the audit log (showing archived rows on the Pay tab would need a list filter — not part of v1.1, review OPEN-41). The API surface (endpoint, body, response, codes) is unchanged. Neither table has a DB audit trigger — the interceptor audit row (`commission.assignment_withdraw` / `payroll.salary_withdraw`) carries the before-image and the reason.

**P5-RULE-04 · Salaries, proration, allocation shares.** 🔒 D-PAYR-02, F-P5-12, owner **C5**, gap E7 / E8 (accepted).
- `employee_salaries` = one monthly amount per day per employee (EXCLUDE), written with the P5-RULE-03 algorithm (past dates allowed back to the day after the last finalized period; 423 `payroll_finalized` otherwise); withdraw of a wrong row (P5.EPY.04) = the P5-RULE-03 withdraw rule and mechanism — the row is **archived** (DB Part 5 v1.2 — owner 02/Oct/2026, OPEN-40 OK) (no result row references a salary row, so "unused" = it starts after the last finalized period; audit `payroll.salary_withdraw` with the before-image). Salary changes are audited by the interceptor with before / after (D-AUD-01).
- **Proration by calendar days** (owner C5): basic for a run = Σ over the salary rows overlapping the period of `amount × overlapping days ÷ days in that calendar month`, each segment rounded half-up. Examples: joins 16/Oct at 300,000 → 300,000 × 16/31 = **154,839**; raise 300,000 → 350,000 from 15/Oct → 135,484 + 191,935 = **327,419**; a full month = the amount exactly. The same per-day rule prorates WEEKLY / BIWEEKLY / CUSTOM runs (F-P5-12). Joining and leaving are expressed by the salary rows (start / `effective_to`); no salary row = basic 0 (commission-only staff).
- **Allocation shares** (D-PAYR-08 basis 3 MANUAL_PERCENT): stored in the company JSON setting **`payroll.manual_allocation`** = `{ "<employee_id>": { "<branch_id>": percent, … } }` (gap E7 — the settings store has no employee scope, D-PLT-16), written only through P5.EPY.05 (Σ = 100, each branch an active assignment of the employee — 422 `shares_invalid`). **Primary branch** (D-PAYR-08 fallback) = the employee's active assignment with the earliest `effective_from` (gap E8 — same order as Part 1 `/me.assigned_branch_ids[0]`).

**P5-RULE-05 · Payroll run state machine.** 🔒 D-PAYR-01/06, F-P5-04/09, AD-PAY-01, owner **C4 / C7**, contract 15. Statuses on the wire = DB: **0 CANCELLED · 1 DRAFT · 2 CALCULATED (= Review) · 3 FINALIZED · 4 PUBLISHED · 5 PAID**.

| From | Action (endpoint, code) | To | Guard |
| --- | --- | --- | --- |
| – | create (P5.RUN.02, `payroll.create`) | 1 | period valid for its type (MONTHLY = a calendar month; WEEKLY 7 days; BIWEEKLY 14; CUSTOM 1–31) else 422 `period_invalid`; overlap with a non-cancelled run → 409 `period_overlap { run_id }` (DB EXCLUDE — also the natural replay guard) |
| 1, 2 | calculate (P5.RUN.04, `payroll.update`) | 2 | P5-RULE-06; `rules_snapshot` written (CHECK); no earlier run still DRAFT / CALCULATED (409 `earlier_run_open`) |

**Finalize and reopen first take the exclusive payroll lock** (P5-RULE-10); then every transition locks the run row (`FOR UPDATE`), runs **READ COMMITTED** with its checks made after the locks (review R2-1 — REPEATABLE READ READ ONLY is for the commission preview and reports only, ADR-015) and is **idempotent by state** (a repeat → 200 current state; a wrong order → 409 `invalid_transition { status }` — contract 15, no `Idempotency-Key`). Review writes (lines, items) need status 2 (status 1 → 409 `invalid_transition` "calculate first"; 3–5 → **423 `locked`** with `correction_path: "reopen"` — AD-DET-03). PAID is final (🔒 D-PAYR-06 — no reopen). Status changes emit `payroll.run_updated` and are audited (`payroll.run_create / calculate / finalize / publish / pay / reopen / cancel`).

**P5-RULE-06 · Calculate.** 🔒 D-PAYR-02/03/05/08, D-COM-01..04, F-P5-04/05, owner C5 / C6 / C8 / C9. Synchronous in one transaction (about 15 employees — research D1), run row locked; refused with **409 `earlier_run_open { run_id }`** while a non-cancelled run of an earlier period is still DRAFT or CALCULATED (review R1-10 — a receivable balance or a reversal carry is then never deducted by two working runs at once):
1. **Snapshot** the rules into `rules_snapshot` (every `payroll.*` key below, `leave_types.is_paid` per type, the allocation basis, the period type) — later setting changes never alter this run (🔒 D-PAYR-05 v5.1) — and, in the same JSON, the **`inputs_fingerprint`** of this calculation (P5-RULE-09 c).
2. **Who gets an entry:** every employee with a salary row or a commission assignment overlapping the period, attendance in the period, commissionable sales or REVERSALs in the period, or (status ACTIVE) an outstanding receivable / reversal. Employees with none (e.g. the owner) get no entry.
3. **Rebuild derived rows** — AUTO lines, attendance items, commission results / lines — after saving the existing **MANUAL lines and overrides** of a CALCULATED run **or of a reopened run** (the working rows a reopen leaves in place — P5-RULE-09); they are re-applied by key (employee + category + source reference: exception id, leave id, receivable id, the **assignment** of a commission result — result ids are rebuilt); an override whose target disappeared → `warnings[] override_dropped`, whose auto amount changed → `override_stale` (shown on the entry — AD-PAY-02).
4. **Earnings:** BASIC (P5-RULE-04 proration; `payroll_entries.basic_salary_amount`) · COMMISSION one AUTO line per result (P5-RULE-02) · MANUAL earnings.
5. **Deductions:** attendance items and lines (P5-RULE-07) · UNPAID_LEAVE · COMMISSION_REVERSAL — one AUTO line per entry (this run's REVERSALs + the carry — P5-RULE-02) · ADVANCE_REPAYMENT / LOAN_REPAYMENT one AUTO line per receivable (P5-RULE-11) · MANUAL deductions — capped by P5-RULE-08.
6. **Totals:** `gross = Σ EARNING`, `deduction = Σ DEDUCTION`, `net = gross − deduction` (DB CHECK), attendance summary columns (`late_count`, `late_minutes`, `absent_days`, `unpaid_leave_days`, `scheduled_days`); an allocation **preview** per entry (stored only at finalize).
7. **Warnings** on the run: `open_exceptions { count }` (OPEN exceptions in the period — they **are** deducted, 🔒 F-P5-05; the banner says so — AD-PAY-02), `closings_open { items }` (C7 — finalize will refuse), `period_not_ended`, `no_salary { employees }`, `capped { employees }`, `employees_left { employees }` (resigned with outstanding amounts — gap E10), **`pending_leaves { count }`** (PENDING leaves inside the period — an unpaid leave that is still pending deducts nothing, so decide them before finalizing; review R1-9), `reopened_not_recalculated` (a reopened run before its next Calculate).
Calculation is allowed before the period ends (preview); results are working rows until finalize.

**P5-RULE-07 · Attendance and leave deductions.** 🔒 D-PAYR-05 (OPEN-06 A), F-P5-05, owner **C8 / C9**. Inputs = `attendance_exceptions` with status **OPEN or CONFIRMED** and `business_date` in the period (EXCUSED / LEAVE / VOID never deduct; INCOMPLETE is never deducted — it has no item type) + APPROVED unpaid leaves. Daily rate (basis snapshot `payroll.absent_daily_rate_basis`): 1 = monthly basic ÷ 30 · 2 = ÷ 26 · 3 = ÷ the employee's scheduled days of that month; basic = the amount effective on the item date; each item rounded half-up.
- **LATE** (type 1, minutes = the exception's raw minutes): `payroll.late_deduction_mode` 0 OFF · 1 FIXED per occurrence (`late_deduction_amount`) · 2 PER_MINUTE (`late_deduction_amount × minutes`). The grace (`payroll.late_grace_minutes`) is a **threshold**: lateness within it never becomes an exception (owner C8, P5-RULE-14), lateness beyond it counts in full minutes.
- **LATE_TO_ABSENT** (type 5): when `payroll.late_count_to_absent` = N > 0, every N counted lates in the period → one item, `day_portion` 1, at the daily rate; the N lates converted carry `auto_deduction_amount` 0 (no double penalty).
- **EARLY_LEAVE** (type 2): recorded on the payslip; deducted only when `payroll.early_leave_deduction_mode` ≠ 0 (same modes as late, `early_leave_deduction_amount`) — default 0 OFF (owner C9 "recorded only — switch it on to deduct").
- **ABSENT** (type 3, `payroll.absent_deduction_enabled`): **one item per date**, linked to the first counted ABSENT exception of that date; `day_portion` = **0.5 when the employee attended another shift that day or has a half-day leave that day, else 1** (owner C9 — one of two shifts missed = half a day). Lateness and early leave are never measured inside an ABSENT shift (P5-RULE-14), so a missed segment costs its half day only.
- **UNPAID_LEAVE** (type 4, `payroll.unpaid_leave_deduction_enabled`): APPROVED leaves whose type was unpaid at calculation, per date in the period that has an active shift; FULL = 1, MORNING / AFTERNOON = 0.5.
- Per type the items' Σ `deduction_amount` becomes one AUTO line (LATE · ABSENT · UNPAID_LEAVE system categories; EARLY_LEAVE and LATE_TO_ABSENT fold into LATE and ABSENT with the description "Early leave × 2" / "Late × 6 → 1 day"). Item overrides need a reason (DB CHECK, AD-RSN-02 F).

**P5-RULE-08 · Net pay never goes below zero — the one deduction order.** Owner **C6** + 🔒 D-PAYR-04, D-COM-04. Per entry the deductions are applied **in this order** against the remaining gross (the only place the order is defined — review R1-22): (1) **attendance + unpaid-leave deductions** — capped at the gross; the excess is **not carried** (a penalty of this period — there is no balance that could hold it); (2) **MANUAL deductions** — never capped: a write that would make net < 0 → 422 `net_negative { employee_id, net_amount }`; (3) **COMMISSION_REVERSAL** (this run + carried) — capped, the remainder **carries** (P5-RULE-02); (4) **advances**, oldest first; (5) **loans**, oldest first — capped, the remainder stays on the balance and **carries**. Owner C6 "the rest goes to next month" therefore means repayments and commission reversals. The capped figure **is** the AUTO amount (`auto_amount` = the amount after the cap; the description says "capped — 20,000 next month"), so no override reason is needed; a lower amount chosen by the admin is an override with a reason. **Example — owner C6 (the sheet's case):** gross 180,000, advance 200,000 with no instalment → advance line **180,000**, net **0**, **20,000** stays on the balance for the next run. **Example — with an absence (a separate case):** gross 180,000, absent deduction 40,000, the same advance → absent 40,000, advance line 140,000, net 0, 60,000 stays on the balance. Any review write re-runs (3)–(5) for that entry. Finalize refuses a negative net (422 `net_negative`).

**P5-RULE-09 · Finalize, publish, mark paid, reopen, cancel.** 🔒 D-PAYR-06/08, D-FIN-04, F-P5-09/11, owner **C4 / C7**, G, contracts 2 / 3 / 15.
- **Finalize** (`{ expected_calculated_at }` — the review the admin saw; another recalculation since → 409 `run_stale`) — first statement: the **exclusive payroll lock** (P5-RULE-10 — in-flight corrections finish first, later ones wait and then meet 423), then the run row; every check below runs after both: (a) `period_end < today` (MMT) else 422 `period_not_ended`; (b) **every branch-day of the period is CLOSED** — `DailyClosings.openDays(null /* every branch */, period_start, period_end)` (Part 7 P7-RULE-03 — §13 note 2: open days from each branch's first active date, closure / closed-weekday days only when they had money activity) → 409 **`closings_open { items: [{ branch_id, dates[] }] }`** (owner C7, contract 3); (c) **not stale** (review R1-10) — Calculate stores `rules_snapshot.inputs_fingerprint` = `{ <group>: sha256 }` over the canonical, id-ordered inputs of the calculation, one hash per group: `sales` (every commissionable SERVICE line of the period: `sale_item_id`, effective performer, `line_total_amount`) · `refunds` (the refund items on those lines, and the refund items dated in the period on lines earned in FINALIZED+ runs) · `attendance` (exceptions of the period: id, status, minutes, leave; non-voided records: id, branch, in, out) · `leaves` (PENDING / APPROVED leaves overlapping the period: id, status, type, `is_paid`, portion, dates) · `shifts` (active shifts of the period: id, employee, branch, times) · `salaries` · `assignments` (rows overlapping the period, with the tiers of their plans) · `receivables` (ACTIVE receivables: id, balance, instalment, start date; the reversal carry per employee) · `settings` (the `payroll.*` keys incl. `payroll.manual_allocation`) · `runs` (the ids of the other runs that are FINALIZED / PUBLISHED / PAID — the set moves when "another run was finalized or reopened since"). Finalize recomputes it under the lock and compares: any difference → 409 `run_stale { changed[], calculated_at }` (`changed` = the names of the groups that differ). A withdrawn row simply leaves its group, and tables without `updated_at` need no timestamp (`payments` are not an input; refunds are compared by id + amount). No DB change — the fingerprint is one more key of the existing jsonb snapshot; (d) every `net ≥ 0` (422 `net_negative`); (e) **no earlier run open** — a non-cancelled run of an earlier period still DRAFT or CALCULATED → 409 `earlier_run_open { run_id }` (the same guard as on Calculate — P5-RULE-06). The response repeats the run warning `pending_leaves { count }` when PENDING leaves remain in the period. Then: **allocation snapshot** (next bullet), **`Expenses.postPayroll(run, actor)`** (Part 7 P7-RULE-15 — one APPROVED expense, source 3 PAYROLL, category SALARY, per allocation row, `amount = allocated_gross_amount`, `expense_date = period_end` — 🔒 D-FIN-04 Gross), status 3, `finalized_*`. OPEN exceptions left in the period stay OPEN and are deducted (🔒 F-P5-05) — the confirm dialog repeats the count (AD-PAY-06).
- **Allocation** (🔒 D-PAYR-08, F-P5-11): per entry, the COMMISSION earning lines (as finally set in review) are split across branches in proportion to the EARN line commission by sale branch (D-COM-01 "commission by branch sales"); the rest of the gross (basic + other earnings) is split by the snapshot basis — 1 ATTENDANCE_HOURS (non-voided record minutes per branch) · 2 SCHEDULED_HOURS (active shift minutes) · 3 MANUAL_PERCENT (`payroll.manual_allocation`) · fallback 4 PRIMARY_BRANCH when the basis gives nothing. `allocated_gross_amount` by largest remainder (Σ = gross); `ratio = allocated ÷ gross` (4 decimals, last row absorbs the rounding so Σ = 1); `basis` = the basis used for the non-commission part; entries with gross 0 get no rows.
- **Publish:** status 4, notification `payslip.published` (**mandatory** — D-NTF-03) + realtime `payslip.published` to every employee with an entry; P5.PSL shows the payslip from now on.
- **Mark paid** (`{ paid_at?, paid_note? }`, default now, `published_at ≤ paid_at ≤ now`): **one paid date for the run** (owner C4 — anyone paid later is noted in `paid_note`); writes one `employee_receivable_repayments` row per ADVANCE / LOAN line with amount > 0 (`payroll_line_id` — unique, so a repeat is a no-op) and sets a receivable **SETTLED** (`settled_at`) when its balance reaches 0 (G — repayments at Mark paid, so reopen never deletes money rows). Salaries paid from a branch drawer = a Part 7 Cash Out with the CASH_MOVEMENT reason **"Salary payment — recorded in Payroll"** (contract 6 — no second expense, D-FIN-04).
- **Reopen** (`{ reason }`, FINALIZED or PUBLISHED — PAID → 409 `invalid_transition`; first statement: the exclusive payroll lock): only the **latest** finalized run, and only while every later run is CANCELLED or a DRAFT that **holds no commission result lines** (never calculated — a later run that was itself reopened still holds REVERSAL lines pointing at this run's EARN lines and must be cancelled first) → otherwise 409 `later_run_exists { run_id }` (verification 02/Oct: the FK `commission_result_lines.original_line_id` has no ON DELETE action, and the next Calculate rebuilds this run's EARN lines). In one transaction: **`Expenses.removePayroll(run, actor, reason)`** (Part 7 P7-RULE-15 — takes this run's source-3 salary expenses out of the books; **🔒 owner 02/Oct/2026 — OPEN-40 OK, (a) = B**): the expenses are **soft-deleted** (`deleted_at`, `deleted_by` = the actor, `deletion_reason` = "Payroll reopened — <reason>") and the allocations can then be deleted because DB Part 7 **v1.2** makes `expenses.payroll_entry_branch_allocation_id` `ON DELETE SET NULL` and lets `expenses_source_refs_chk` accept a NULL allocation on source 3 only when `deleted_at IS NOT NULL`; the next finalize posts fresh rows (`expenses_one_per_allocation … WHERE deleted_at IS NULL` allows it) — no hard delete, 🔒 D-DAT-05 holds (§13 note 1). The API surface (endpoint, body, response, codes) is unchanged. Then (review R1-11): the **allocations are deleted**; **`calculated_at`, `finalized_at` and `published_at` are cleared** (DB `payroll_runs_status_fields_chk` — status 1 allows none of them; `paid_at` is already NULL) together with `calculated_by_user_id`, `finalized_by_user_id`, `published_by_user_id` and `rules_snapshot`; status 1, `reopen_count + 1`, `last_reopened_*` (DB CHECK). **The entries, lines, attendance items and commission results / lines stay in place as the working rows of the reopened DRAFT run**: the next Calculate deletes and recomputes them (🔒 F-P5-09 "results deleted and recomputed" — DB note: once the run is DRAFT again) after saving the **MANUAL lines and the overrides**, which it re-applies exactly as a recalculation does (P5-RULE-06 #3) — B9 correction lines and review decisions survive a reopen. Until then the run carries `warnings[] reopened_not_recalculated`, its payslips are hidden and its rows count in no balance (pending deductions and the reversal carry read FINALIZED+ runs only). **Audit:** the DB triggers record the changes of `payroll_runs`, `payroll_entries`, `payroll_lines` and `commission_results` (🔒 D-AUD-02); `commission_result_lines`, `payroll_attendance_items` and `payroll_entry_branch_allocations` have **no** DB trigger — they are covered by the one interceptor audit row **`payroll.reopen`**, which stores the run's full before-image as JSON (entries, lines, attendance items, results, result lines, allocations) with the reason. A run that was PUBLISHED sends **`payslip.revised`** (mandatory) and hides its payslips until the next publish.
- **Cancel** (`{ reason }`, DRAFT / CALCULATED): derived rows removed, status 0 (the period is free again — the EXCLUDE ignores cancelled runs).

**P5-RULE-10 · `PayrollLock` — finalized periods are frozen.** Contract 3 (owned here) + owner B9; review R1-1 / R1-9.
- **`PayrollLock.assertNotFinalized(tx, { employee_ids?, dates })`** = `pg_advisory_xact_lock_shared(payrollKey)` with `payrollKey = hashtextextended('payroll:' || company_id, 0)` (one key per company — runs are company-wide, every employee is frozen for a finalized period), then a read of the runs covering `dates`: a date inside a run with status 3 / 4 / 5 → **423 `payroll_finalized { employee_id, run_id, period: { start, end }, status }`** (`employee_id` = the first of `employee_ids`, null when none was passed). The shared lock is held to commit, so a finalize cannot slip in between the check and the write.
- **Finalize and reopen** take `pg_advisory_xact_lock(payrollKey)` (**exclusive**) as their first statement: they wait for in-flight writers, and every later writer sees the new status. In the one lock order of the system the payroll lock comes **second** — day lock → payroll lock → row locks (Part 4 P4-RULE-10).
- **Callers:** **Part 4** — late-entry START, FINISH of every sale with SERVICE lines (a business date inside such a period: no later run would pay the commission — the correction is a MANUAL payroll line in the next run, owner B9) and the PERFORMER adjustment · **Part 2** — shift writes and leave **create / edit / approve / reject / cancel** touching such dates (v1.4 amendment) · **Part 5** — attendance manual entry, manual clock-out, correction, void and exception resolution, salary rows and plan assignments whose dates reach the period.
- **Detection:** `AttendanceDetector.redetect` and the detection job **skip dates inside finalized periods** — nothing is created, voided or flipped there (an exception already deducted never changes afterwards). The automatic close of a stale open record at the employee's next clock-in (P5-RULE-13) is the one write allowed on such a date; it creates no exception.
- **Not callers:** Part 7 day **reopen** — allowed inside a finalized period (cash corrections may still be needed) but answered with the warning `payroll_finalized_period { run_id, period }` (Part 7 P7-RULE-07) · refunds (they become REVERSAL lines of a later run — P5-RULE-02) · own clock-in / clock-out (always today).
- **Read-only lookups** (no lock taken, nothing refused): **`PayrollLock.finalizedRunFor(date)`** → `{ run_id, period: { start, end }, status } | null` — the FINALIZED / PUBLISHED / PAID run whose period contains `date`; Part 7 P7-RULE-07 uses it for the reopen warning `payroll_finalized_period { run_id, period }` (reconcile 02/Oct — named here as owned). `PayrollLock.lastFinalizedEnd()` gives the earliest date still open (UI date pickers; Part 2 P2.LV.03 look-back).

**P5-RULE-11 · Advances and loans (receivables).** 🔒 D-PAYR-04, D-FIN-02/07/08, REC-15, owner **C2 / C3 / C6**, G (b), contract 5.
- **Issue** = `Receivables.issue({ employee_id, kind, principal_amount, installment_amount?, repayment_start_date?, reason?, cash_out_id?, client_request_id?, actor })` — the only writer. Two paths: (a) **from a drawer** — Part 7 Cash Out with an EMPLOYEE_BALANCE reason (P7-RULE-09 — `kind` = the reason's `receivable_kind`, `principal_amount` = the cash-out amount, `reason` = the cash-out note); the caller needs **`cashout.create` + `receivable.issue`** (private — company scope); the receivable is created in the cash out's transaction with `cash_out_id` (the cash out's `client_request_id` covers replays; `employee_receivables.client_request_id` stays NULL); (b) **not from a drawer** (bank / owner's pocket) — P5.RCV.03 with `Idempotency-Key` (= `employee_receivables.client_request_id`; identifying fields `employee_id`, `kind`, `principal_amount`). Both: `employee_id` = the caller's **own** employee → **422 `self_issue`** (owner C2 — never to oneself); employee ACTIVE (422 `employee_inactive`); `0 < installment ≤ principal` (DB CHECK); kind 1 SALARY_ADVANCE · 2 STAFF_LOAN keep separate balances.
- **Deduction:** an ACTIVE receivable with `repayment_start_date` null or ≤ period end gets one AUTO line per run (ADVANCE_REPAYMENT / LOAN_REPAYMENT, `employee_receivable_id`): `installment_amount`, or **the whole balance when no instalment is set** (owner C2 — "next payroll in full"), never more than the balance, capped by P5-RULE-08.
- **Balance** = principal − Σ repayments − **pending** (Σ ADVANCE / LOAN lines in FINALIZED / PUBLISHED runs not yet paid). Repayment rows for payroll deductions are written at **Mark paid** (G).
- **Cash repayment** (P5.RCV.05, `Idempotency-Key` = `employee_receivable_repayments.client_request_id`): money handed to **the owner / admin outside the drawer** (owner C3 — `received_at` + `received_by_user_id` = the caller; no closing effect — gap E1, Part 7 P7-RULE-04); `amount ≤ balance` (422 `repayment_exceeds_balance { balance_amount }`); balance 0 → SETTLED.
- **Change / cancel:** instalment and start date editable while ACTIVE (future runs only). Cancel only while nothing was repaid or is pending (409 `receivable_in_use`); a drawer-issued receivable is cancelled with its cash out — Part 7 P7.CSO.06 calls **`Receivables.cancelForCashOut(cash_out_id, actor, reason)`** in the cash out's transaction (same 409 `receivable_in_use` rule; status 0 CANCELLED, audit `receivable.cancel`, realtime `receivable.changed`) — while P5.RCV.06 answers 409 `cash_out_linked { cash_out_id }`. Part 7 edit and cancel of an EMPLOYEE_BALANCE cash out (P7.CSO.05 / 06) therefore also require `receivable.issue` (review R2-3), and an edited cash-out note is copied to the receivable's `reason` by **`Receivables.updateForCashOut(cash_out_id, { reason }, actor)`** in the cash out's transaction (the P5.RCV.04 rule — receivable ACTIVE, else 409 `invalid_transition`; audit `receivable.update`, realtime `receivable.changed`).
- **Leavers** (gap E10): settled in the regular monthly run (company-wide periods allow no off-cycle run); what the cap leaves **stays listed** in P5.RCV.07 *Outstanding* (advance / loan balances, reversal remainder) — the admin's "to collect" record (🔒 D-COM-04). Money a leaver hands over for an advance / loan is recorded as a **cash repayment** (P5.RCV.05). **There is no write-off / settle action in V1 (⏭ — review R1-16):** an uncollectable balance, and any commission-reversal remainder (which has no repayment endpoint), simply stays in the list; a partly repaid receivable cannot be cancelled (409 `receivable_in_use`). The admin's decision is taken outside the system until a later version adds the action.

**P5-RULE-12 · Payslips.** 🔒 D-PAYR-07, D-COM-04, D-NTF-03, ADR-007 (in-app only), contract 10, research D2. A payslip = one entry of a **PUBLISHED / PAID** run (self — P5.PSL; reopened runs hide it); the admin copy (P5.RUN.16) is available from CALCULATED with a "Not final" watermark until FINALIZED. Content: employee, period, earnings (basic with the proration note, commission with the tier breakdown, manual), REVERSAL lines with their refund label, attendance items per date, deductions, advance / loan repayments and the remaining balances, net, paid date. Files are **rendered on demand** from the stored snapshot — PDF through the `DocumentRenderer` (HTML → headless Chromium, self-hosted Pyidaungsu / Inter — Myanmar text shaped correctly), Excel through exceljs (opens in Google Sheets — D-PAYR-07); never stored; `Content-Disposition: attachment; filename="payslip-<employee_code>-<YYYY-MM>.pdf|.xlsx"`. Language = `?lang=` else the **employee's** `users.ui_language` (else the system default); bilingual master names follow D-DB-04 fallback.

**P5-RULE-13 · Own clock-in and clock-out.** 🔒 D-ATT-01/02/06, F-P5-07/08, owner **C10**, research D3 / D4.
- **Clock in** (P5.ATT.02, self): body `{ qr_token, latitude, longitude, accuracy_meters }`. Checks in order: `attendance.qr_required = false` → 422 `manual_only_mode` (a manager records attendance — AD-ATT-02); the token (the `t` value of the poster URL `https://<app host>/clock?t=<token>`) must exist (422 `qr_invalid`) and be active (422 `qr_revoked` — "this code was replaced"); the employee ACTIVE and assigned to the token's branch today (422 `not_assigned_to_branch`); location is **always** required (DB CHECK `attendance_records_method_fields_chk` — a QR_GPS row needs latitude, longitude **and** distance; 🔒 D-ATT-01): a device that gives **no position** cannot self clock in — the request is refused (400 `validation`), nothing is stored, and a manager records the attendance manually (method 2 MANUAL — P5.ATR.03); **the branch must have coordinates for every self clock-in → 422 `branch_location_missing`, whatever `attendance.gps_required` says** (review R1-19 — without them no distance could be stored); the haversine distance is always computed and stored (`clock_in_distance_meters`) and the reported `accuracy_meters` is kept in the interceptor audit row `attendance.clock_in` (DB Part 5 has no accuracy column); **only when `attendance.gps_required` is on** are the two limits enforced — `accuracy_meters > attendance.max_gps_accuracy_meters` (100) → 422 `gps_inaccurate`, and a distance > `branches.location_radius_meters` (else `attendance.default_radius_meters`) → 422 `too_far { distance_meters, radius_meters, branch_id }` (AD-ATT-01 "You're 240 m from Branch 3.0"). **With the setting off, distance and accuracy are recorded but neither the radius nor the accuracy limit is enforced** (🔒 D-ATT-01 "GPS not needed = the radius check switched off" — the accuracy limit only serves that check; reconcile 02/Oct). The session user must be the employee — nobody clocks in for a colleague (🔒 D-ATT-06; the endpoint has no employee field).
- **Open record:** at the **same** branch → 409 `already_clocked_in { record_id }`, except a repeat within 120 s → 200 with that record (`Idempotent-Replayed: true` — natural replay, no `client_request_id` column); at **another** branch → that record is closed first (owner C10 *auto switch*): at the end of its matched work block if that already passed (`clock_out_source` 3 AUTO_SHIFT_END), otherwise now (1 SELF, no clock-out coordinates); from an **earlier business date** → closed at its block end (else 23:59 of its date, source 3) with an INCOMPLETE exception (P5-RULE-14); `warnings[] previous_record_closed { record_id, clock_out_at }`.
- **Clock out** (P5.ATT.03, self): **button + GPS, no QR** (owner C10) — `{ latitude, longitude, accuracy_meters }`, the same accuracy and radius checks against the record's branch — **both only when `attendance.gps_required` is on** (off: position, distance and accuracy are recorded, nothing is refused) — a branch that lost its coordinates since the clock-in does not block the clock-out: the position is stored with `clock_out_distance_meters` NULL (the DB CHECK constrains the clock-in columns only); no open record → 409 `not_clocked_in`; a repeat within 120 s of the close → 200. A barber who left without clocking out is closed by a manager (P5.ATR.04) or the automatic rule (P5-RULE-14).
- **Stored:** method 1 QR_GPS, `qr_token_id`, coordinates + distance (in and out), `clock_in_device_label` from the session (D-AUTH-05), `business_date` = MMT date of `clock_in_at` (DB CHECK), the matched shift and raw `late_minutes` / `early_leave_minutes`. **GPS privacy** (research D4): location is captured only at these two moments (never tracked); lists show the distance only; raw coordinates appear in the record detail for the employee and for holders of `attendance.update` covering the branch.

**P5-RULE-14 · Shift matching and exception detection — `AttendanceDetector`.** 🔒 D-ATT-03/04, F-P5-05/08, owner **C8 / C9**, ADR-002.
- **Work block** = the employee's active shifts at one branch on one date, touching segments merged (9–13 + 13–20 at the same branch = one block; Part 2 allows touching same-branch segments). A record matches the block at its branch whose span (from 120 minutes before its start to its end) contains `clock_in_at` (first unmatched block); none → `schedule_shift_id` null (`warnings[] no_shift_today` — no late / early detection). `schedule_shift_id` = the **first shift of the block that the record attends** — the first one with `ends_at > clock_in_at`; a shift of the block that ended before the clock-in is wholly missed.
- **LATE** at clock-in (or when a manual entry / correction is saved): `late_minutes = ⌊clock_in − start of the first attended shift⌋⁺` — **minutes are never counted inside a wholly missed shift** (review R1-14: segments 9–13 + 13–20, clock-in 13:05 → LATE **5** minutes on the second shift and ABSENT for the first = half a day, owner C9 — not LATE 245 plus ABSENT); an exception (OPEN, on that shift) only when `late_minutes > payroll.late_grace_minutes` (owner C8 — 9:04 with grace 10 is not on the board; the raw minutes stay on the record). **EARLY_LEAVE** at clock-out the same way against the end of the **last attended shift** of the block (the last one with `starts_at < clock_out_at` — the exception is recorded on that shift); later shifts of the block are wholly missed. **ABSENT** — job: a shift (non-archived, employee ACTIVE) that ended with no non-voided record at its branch overlapping it, no PENDING / APPROVED leave covering its time (half days by `leave.half_day_cutoff_time` — D-LV-05) and no branch closure that date → one exception per shift — so a wholly missed shift is ABSENT and nothing else (0.5 day when another shift that day was worked — P5-RULE-07). **INCOMPLETE** — job at end of day: records of today still open, or closed by the automatic rule.
- **Automatic clock-out** (🔒 D-ATT-04): when `attendance.auto_clock_out_after_shift_minutes` = M > 0, an open record whose block ended more than M minutes ago is closed at the block end (source 3) — and still flagged INCOMPLETE so the manager sees it (never deducted).
- **Job `attendance.detect_exceptions`** (ADR-002 canonical list): every 15 minutes (ABSENT, automatic clock-out) and at 23:55 MMT (INCOMPLETE); idempotent (DB partial uniques: one exception per shift and type, one INCOMPLETE per record); skips periods already finalized.
- **Re-detection** (`AttendanceDetector.redetect(employee_id, dates[], actor)` — in the caller's transaction): after a manual entry, correction or void (Part 5), a past-date shift write (Part 2 P2.SHF.03/04/05/08) or a leave create, edit, decision or cancellation whose dates include today or a past date (Part 2 P2.LV.03 / 05 / 06 / 07 / 08 — P2-RULE-09). OPEN exceptions that no longer hold become **VOID** with `resolution_reason` "Schedule / attendance changed" and `resolved_by` = the actor; minutes of OPEN exceptions are refreshed; resolved exceptions keep their status (the board flags `changed_after_resolution`); new ones are created. Dates inside a finalized payroll period are skipped (P5-RULE-10), and Part 2 refuses a shift write — and a pattern save — that changes the caller's **own** shifts on a date ≤ today (422 `self_action` — owner C11), so re-detection never lets a manager void their own lateness (review R1-15). A LEAVE-resolved exception whose leave is later REJECTED / CANCELLED returns to OPEN; an APPROVED leave covering an OPEN ABSENT exception resolves it to LEAVE (`leave_id`). The job (no actor) never voids — it only creates.

**P5-RULE-15 · Manual attendance, correction, void.** 🔒 D-ATT-04/05/06, owner **C11**, G (a), contract 3.
- **Manual entry** (P5.ATR.03, `attendance.create`, branch of `branch_id`): `{ employee_id, branch_id, clock_in_at, clock_out_at?, manual_reason: 1 PHONE_UNAVAILABLE | 9 OTHER, manual_note? }` (OTHER → note required — DB CHECK); method 2 MANUAL, `entered_by_user_id` = caller; employee assigned to the branch on that date; times ≤ now, out ≥ in (422 `clock_time_invalid`); overlapping record → 409 `attendance_overlap`, another open record → 409 `already_clocked_in`. The screen shows that day's visits as evidence (P5.ATR.07 — 🔒 D-ATT-06); the monthly manual count per employee is in P5.ATR.08.
- **Manual clock-out** (P5.ATR.04, `attendance.create`): closes an open record `{ clock_out_at, reason }` → `clock_out_source` 2 MANUAL + `corrected_*` (the reason travels in `correction_reason` — DB CHECK all-or-none).
- **Correction** (P5.ATR.05, `attendance.update`): `{ clock_in_at?, clock_out_at?, correction_reason }` — times only (employee and branch never change: wrong person / branch = void + new manual entry); `corrected_*` set; `business_date` follows `clock_in_at`; before → after in the audit diff (AD-ATT-04).
- **Void** (P5.ATR.06, `attendance.update`, G a): `{ void_reason }` → `voided_at / _by / void_reason` (all-or-none, reason non-empty); a voided record no longer blocks a new record (v1.1 partial indexes), never counts in hours / allocation, its LATE / EARLY / INCOMPLETE exceptions become VOID and ABSENT is re-detected (P5-RULE-14).
- **Common:** **not on one's own record** — the record's employee = the caller's own employee → 422 **`self_action`** (owner C11 — another manager or the admin does it; also P5-RULE-16); `PayrollLock.assertNotFinalized(tx, { employee_ids: [the record's employee], dates: [business_date] })` (423); every write re-runs detection and sends `attendance.record_changed` to the employee.

**P5-RULE-16 · Exception resolution.** 🔒 D-ATT-03/05, F-P5-05, AD-ATT-03, owner **C11**. P5.EXC.02 (`attendance.resolve`, branch of the exception): `status` 2 EXCUSED (reason required) · 3 CONFIRMED (reason optional) · 4 LEAVE (`leave_id` of a PENDING / APPROVED leave of that employee covering the date — 422 `leave_not_covering` — or `create_leave: { leave_type_id, day_portion }`, which calls the Part 2 leave create on behalf and needs `leave.create` too) · 0 VOID (reason required) · 1 OPEN (undo — clears the resolution). The employee's own exception → 422 `self_action` (C11); `PayrollLock` (423); a resolution in a CALCULATED run's period makes it stale (P5-RULE-09). OPEN + CONFIRMED are deducted, the others not — the response carries `payroll_effect`. Resolve on the day where possible (F-P5-05); the approvals inbox counts OPEN exceptions for their holders (AD-NTF-04).

**P5-RULE-17 · Branch attendance QR.** 🔒 D-ATT-01, F-P5-07, AD-QR-02, research D3. One active token per branch (DB partial unique): 32 random bytes, base64url (43 characters); the poster encodes **`https://<app host>/clock?t=<token>`** so the in-app scanner and a phone camera both open the clock-in screen; the path and the `qr_token` body field are redacted in Caddy / API / Sentry logs and in the audit interceptor (as P3-RULE-10). **Issue / regenerate** (`attendance_qr.create`) revokes the active token in the same transaction (history kept) — old posters stop working at once (422 `qr_revoked`). **Revoke** without replacement (`attendance_qr.delete`) leaves the branch with manual attendance only. No timed rotation (🔒 D-ATT-01 *static* QR). The printable poster (AD-QR-02 template) is the Part 8 export kind **`attendance_qr_poster`** (P8.EXP.01 `{ kind: "attendance_qr_poster", branch_id, size }` — needs `attendance_qr.view⁺` for the branch, not `data.export`; PDF → **202**, job `export.run`, realtime `export.ready`, file kept 24 h — P8-RULE-08, contract 10).

**P5-RULE-18 · Permissions — levels, own data, operational reads.** 🔒 ADR-011, ADR-012 (+ `private`), D-ROLE-07/09, owner C1 / C2 / C11.
- **Levels:** commission, payroll, payroll categories, salaries, receivables — reads **and `receivable.issue`** — = **private** (P5-RULE-01; review R1-6: owner C1 "advances = Admin only" + C2 seed Admin — a branch-scope grant of `receivable.issue` reaches nothing, 403 `company_scope_required`) · attendance records / exceptions / QR = **branch data** (the record's / exception's / token's branch; a manual entry = `body.branch_id`).

- **Self-action guard** (C11 / C2): attendance writes and resolutions on one's own employee → 422 `self_action`; issuing to oneself → 422 `self_issue`.

**P5-RULE-19 · Notifications, realtime, audit.** 🔒 D-NTF-01..03, D-AUD-01/02, contract 14, research D5. In-app only. Attendance events go to the **user rooms** of the employee and of the holders of `attendance.view` / `attendance.resolve` covering the branch — **not** the whole `branch:` room (barbers don't see colleagues' lateness — Part 0 amendment); payroll events go to the user rooms of company-scope holders of a `payroll.*` code (not the `company` room — private). **Notes on cross-part calls used above.**
1. **Reopen and the salary expenses — soft delete (🔒 owner 02/Oct/2026 — OPEN-40 OK, (a) = B).** Part 7 creates one source-3 expense per allocation at finalize (`Expenses.postPayroll(run, actor)`). 🔒 F-P5-09 says reopen deletes the payroll results and recomputes; up to DB Part 7 v1.1 `expenses_source_refs_chk` required every source-3 expense to keep its FK to `payroll_entry_branch_allocations` (a soft-deleted row kept it, so the allocations could not be deleted); 🔒 D-DAT-05 says transactional rows are never hard-deleted. **Locked:** DB Part 7 **v1.2** — FK `expenses.payroll_entry_branch_allocation_id` `ON DELETE SET NULL` and `expenses_source_refs_chk` lets source 3 have a NULL allocation only when `deleted_at IS NOT NULL`; `Expenses.removePayroll(run, actor, reason)` **soft-deletes** the run's salary expenses (reason "Payroll reopened — <reason>", by = the actor), then the allocations are deleted; the next finalize posts fresh rows (the partial unique index `expenses_one_per_allocation … WHERE deleted_at IS NULL` allows this) — no hard delete, 🔒 D-DAT-05 holds. The API surface (P5.RUN.14 endpoint, body, response, error codes) is **unchanged** — only this internal step was decided.
2. `DailyClosings.openDays(branch_ids?, from, to)` (Part 7 **P7-RULE-03** — called here with every branch and the run period) = the branch-dates that **need closing** and have **no CLOSED** `daily_closings` row. "Needs closing" is defined **only** in Part 7 P7-RULE-03 (first active date … today; open per the opening-hours rows — each weekday row counting from its `updated_at` date — and no closure, **or** money activity, **or** an existing `daily_closings` row) — so a sale recorded on a closure day still needs that day closed before finalize.
3. **Withdrawing a wrong salary row / plan assignment — archive (🔒 owner 02/Oct/2026 — OPEN-40 OK, (b) = B).** Up to DB Part 5 v1.1 `employee_salaries` and `employee_commission_plans` had no `archived_at`, and 🔒 D-DAT-05 / API-PERM-06 #3 say nothing is hard-deleted. **Locked:** DB Part 5 **v1.2** — `archived_at` + `archived_by_user_id` + `archive_reason` on both tables, and their overlap EXCLUDE constraints ignore archived rows (`WHERE archived_at IS NULL` — the DB Part 2 v1.3 pattern); withdraw **archives** the row, it is never deleted. "Unused" = not referenced by a FINALIZED / PUBLISHED / PAID run. P5.CPA.04 / P5.EPY.04 (endpoint, body, response, codes) are unchanged.
