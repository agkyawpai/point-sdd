## 1. Rules specific to this part

**P2-RULE-01 · Company master, branch sale.** 🔒 D-SVC-01/02. `service_categories` and `services` are company-level (one company in V1 — D-ORG-03). A service is sold at a branch only through a `branch_services` row (`status = 1`) with that branch's `duration_minutes`. Lists for a branch (`?branch_id=`) return only services sold there; staff pickers (POS, booking) never see services that are not sold at the current branch. **Data levels (v1.3 — ADR-012):** categories and the service master (create, details, pricing mode, buffer, website fields, options, order, status / archive) are **company master** → `service.create` / `service.update` / `service.delete` through a **company-scope** assignment (a branch-scope holder reads them, 403 `company_scope_required` on write); **whether a branch sells a service and its duration there** (`branch_services` — P2.SVC.06) is **branch data** → `service.update` covering **each item's branch** (company scope covers all). So the admin creates the service once, and each branch Manager switches it on or off for their own branch (D-SVC-02, D-ROLE-07).

**P2-RULE-02 · Options → variants are generated, never typed.** 🔒 D-SVC-05, D-DB-06. An OPTIONS service has 1–2 option groups (🔒 the API enforces **≤ 2** in V1 to match the grid editor AD-CMP-13 — owner 01/Oct 21:20, §16 #5 ✅; the DB allows more), each with ≥ 1 values. On every options write the server (re)generates `service_variants` = the Cartesian product of the active values, with `variant_key` = the sorted value ids joined by `|`; variants whose values were archived are archived too (and their price rows closed as of today). Clients never create variants directly; they reference them by id (price cells, booking items, sale lines). A SIMPLE service has no groups / variants. **SIMPLE → OPTIONS happens through `PUT /v1/services/{id}/options`** (the write flips `pricing_mode` to 2 in the same transaction and closes the service's variant-null price rows and barber-override rows as of today — returned in `warnings[]`); `PATCH … pricing_mode: 2` is refused (422 `use_options_endpoint`). OPTIONS → SIMPLE (`PATCH pricing_mode: 1`) is refused while any variant has a price row effective today or later (422 `has_variant_prices`). Regeneration **reuses** variants whose `variant_key` is unchanged (same id, prices untouched): adding or archiving a *value* touches only the variants that contain it; **changing the number of groups** changes every key, so it is refused while any variant has a current or future price row (422 `has_variant_prices` — the admin withdraws / closes prices first).

**P2-RULE-03 · One price store, resolved in a fixed order.** 🔒 D-SVC-03/05/06/08. A price row = `(branch, service, variant | null, location 1 BRANCH / 2 HOME, employee | null, effective_from … effective_to)`. Resolution for a service date `d` (booking = appointment date, walk-in = today — D-PLT-15): take rows effective on `d` for the branch + service + variant; prefer the barber override (`employee_id` = the barber) over the branch row (`employee_id` null); for HOME, take the HOME row if present else the **branch-level BRANCH row (`employee_id IS NULL`) — barber overrides never apply to HOME** (D-SVC-06; `price_source` 4); **no row at all = not sold** at that branch for that variant (D-SVC-05 — for SIMPLE services the BRANCH-location row must exist for the service to be bookable). Duration = the row's `duration_minutes` if set, else `branch_services.duration_minutes`; buffer = `services.buffer_minutes` (D-SVC-07). Barber overrides exist in V1 only for SIMPLE services at location BRANCH (D-SVC-05) — the API rejects an override cell on an OPTIONS service or HOME location (422 `override_not_allowed`).

**P2-RULE-04 · Effective-dated writes (prices, eligibility, patterns).** 🔒 D-SVC-08, D-EMP-05, D-SCH-01. Dates are inclusive on both ends (DB `daterange(effective_from, effective_to, '[]')`; `effective_to = null` = open). A write names `effective_from` ≥ today (422 `effective_date_past`; history is never edited). **Algorithm per key** (price cell · eligibility (employee, branch, service) · pattern set), inside one transaction with the key's non-archived rows locked `FOR UPDATE`:
1. If a row with `effective_from = new.effective_from` exists → **update it in place** (editing a scheduled grid / set).
2. Else: the row effective on `new.effective_from` (if any, and only if its `effective_from < new.effective_from`) gets `effective_to = new.effective_from − 1`; the new row gets `effective_to = (next later row).effective_from − 1`, or null when there is none.
3. A price cell sent as `null` (not sold / inherit): if a row with the same `effective_from` exists → per-cell withdraw (archive it and re-link the previous row's `effective_to` as in step 4); else step 2 without inserting. A cell is a no-op only when an **explicit** row for that key with the same value is already effective on `effective_from` (a HOME cell sent equal to the inherited shop price still creates an explicit HOME row). Step 1 always recomputes `effective_to` (a row closed at `today` by step 5 and rewritten today is re-opened to the next later row or null).
4. **Withdraw** (P2.PRC.05, scheduled only): archive the rows with that `effective_from` and set the previous row's `effective_to` to the next later row's `effective_from − 1` (or null).
5. **Close as of today** (un-sell a branch, archive a service / variant / value; eligibility un-tick; pattern segment removal): rows with `effective_from > today` → `archived_at`; the row effective today with `effective_from < today` → `effective_to = today`; a row with `effective_from = today` (same-day change) **cannot** be closed (date CHECK) → `archived_at` — which is why `employee_service_eligibilities` and `schedule_patterns` have `archived_at` in DB Part 2 **v1.3** (🔒 D-DB-06 v1.3 — §16 #10 ✅; verified in PostgreSQL 16: the same-day close fails `eligibility_dates_chk`, the archive path passes and the partial unique `eligibility_one_open` now ignores archived rows). Archived rows are history only; `schedule_shifts.schedule_pattern_id` keeps pointing at archived pattern rows (no hard delete — D-DAT-05).
The DB EXCLUDE / date CHECKs are the last line (409 `price_overlap` / `shift_overlap` if two writers race). Every grid write is audited as `price.set` with the diff and raises `catalogue.changed` + `site.content_changed { tags: ['services', 'branch:<code>'] }` (website prices — D-WEB-01).

**P2-RULE-05 · Price quote is the only price calculator.** 🔒 D-SVC-04, D-SVC-06, D-BKG-12. `POST /v1/prices/quote` returns, for a branch / location / date / optional barber and a list of items `{ service_id, service_variant_id? }`, each item's `unit_price_amount`, `duration_minutes`, `buffer_minutes`, `price_source` (1 BRANCH · 2 BARBER_OVERRIDE · 3 HOME · 4 HOME_FALLBACK_BRANCH) and `sold` (false → the whole quote is `complete: false` and the caller must not proceed), plus `transport_fee_amount` for HOME (branch setting `home_service.transport_fee_amount`, 0 = shop pays) and totals. Part 3 (booking create / reschedule — including the D-BKG-12 "which items are repriced" rules) and Part 4 (checkout lines, option change at checkout) call this function in-process; the HTTP endpoint exists for screens that preview prices (AD-BKG-01 step 5, AD-POS). Nobody types a price into a booking or sale line (D-SVC-04); adjustments are Part 4 actions with a reason.

**P2-RULE-06 · Eligibility is per employee × branch × service, effective-dated.** 🔒 D-EMP-05, D-SVC-06. An eligibility row exists only for a branch the employee is assigned to (`employee_branches` active on `effective_from` — 422 `not_assigned_to_branch`) and a service sold there (composite FK). `home_allowed` is a flag on the same row (D-BKG-22). Writes follow P2-RULE-04 (close / open per key); an item whose resolved state is unchanged is a no-op; `home_allowed` omitted = keep the current value (false for a new row); the partial unique index allows one open row per (employee, branch, service). `GET /v1/employees/pickable` (P1.EMP.09) gains its Part 2 filters here: repeatable `service_id` (all must be eligible on `date`), `home=true` (all must have `home_allowed`), `date` (default today) — Part 1 §13 #5 closed; applied in Part 1 v1.3 (P1.EMP.09 — repeatable `service_id`).

**P2-RULE-07 · Patterns are the plan, shifts are the truth.** 🔒 D-SCH-01/02, D-DB-06. A pattern set for an employee = for each weekday, 0..n segments `{ branch_id, start_time, end_time }` (MMT), valid from `effective_from` (to `effective_to`). A set is saved by P2-RULE-04 (same `effective_from` = edit in place; otherwise the previous set is closed at `effective_from − 1`), `effective_from ≥ today`; when a set has an `effective_to`, no pattern applies after it (days off until a new set starts). The write validates: segments of one day don't overlap; a segment lies inside the employee's active branch assignment (422 `not_assigned_to_branch`); **branch change within a day needs ≥ `schedule.cross_branch_gap_minutes`** (default 60) between the end of one segment and the start of the next — same-branch segments may touch (422 `cross_branch_gap { needed, actual, after_segment }`). **Manual day rule:** an (employee, date) is a *manual day* when it has any shift with `source = 2` — active **or archived** (the archived MANUAL row is the marker). P2.SHF.03 / 04 / 05 make the day manual: in the same transaction every other active PATTERN shift of that day is converted to MANUAL, so a manual day's hours are exactly what the roster shows. **Generation never touches manual days.** `POST /v1/schedule/days/reset` (P2.SHF.08) returns a manual day to the pattern: it archives the day's active shifts and sets `source = 1` on **every** archived `source = 2` row of that day (the markers become plain history), after which the day is non-manual again and is regenerated in the same request. `shifts.generate` (ADR-002, nightly 00:30 MMT; also P2.SHF.06 and every pattern write) runs for `[max(effective_from, today), today + booking.advance_window_days + 7]` and is **diff-based**: for each non-manual date it computes the shifts the pattern set effective on that date produces — only if the employee is ACTIVE and assigned (`employee_branches`) to the segment's branch on that date — then keeps every active PATTERN shift whose `(branch_id, starts_at, ends_at, schedule_pattern_id)` is unchanged (same id — nightly runs change nothing), archives active PATTERN shifts the pattern no longer produces, and inserts the new ones. A PATTERN shift referenced by an attendance row (`attendance_records` / `attendance_exceptions.schedule_shift_id` — Part 5) is **never archived by generation**: if the pattern no longer produces it, it is converted to MANUAL (the day becomes manual) and reported in `warnings[]` (`shift_kept_attendance`). Past dates are never regenerated (attendance / payroll read them). The DB EXCLUDE (no overlapping shifts per employee, any branch) is the last line (409 `shift_overlap`). **v1.4 (Part 5 — contract 3, P5-RULE-10 / 14):** a shift write (P2.SHF.03 / 04 / 05 / 08) whose date falls inside a FINALIZED / PUBLISHED / PAID payroll period is refused with **423 `payroll_finalized`** (`PayrollLock.assertNotFinalized(tx, { employee_ids: [employee_id], dates: [date] })` — the shared payroll advisory lock, taken before the shift rows: Part 0 API-IDEM-06); a write touching **today or a past date** calls **`AttendanceDetector.redetect(employee_id, dates[], actor)`** in the same transaction, so ABSENT / LATE / EARLY_LEAVE exceptions follow the corrected roster (re-detection itself skips dates in finalized periods). **Own shifts (review fix 02/Oct — R1-15, owner C11; reconcile 02/Oct — 422, the same status Part 5 uses):** a shift write (P2.SHF.03 / 04 / 05 / 08) for a **date ≤ today** whose `employee_id` is the **caller's own employee** → **422 `self_action`** — re-detection would void or change the caller's own lateness / absence, and nobody excuses their own attendance; another `schedule.*` holder (or the admin) makes the change. The same guard covers a **pattern save (P2.PAT.02) on the caller's own employee**: when the regeneration it triggers would archive, insert or convert one of the caller's own shifts on a date ≤ today (only possible with `effective_from` = today on a non-manual day whose segments differ from today's shifts) → 422 `self_action`, nothing is saved; an own pattern set starting tomorrow or later, and one that leaves today's shifts unchanged, are allowed with the code. Own shifts for future dates stay allowed with the code.

**P2-RULE-08 · Roster edits never touch bookings.** 🔒 D-BKG-19, D-SCH-02. Creating, moving, shortening or deleting a shift (or regenerating from a pattern) checks the employee's BOOKED bookings whose block falls outside the shifts that remain for that day; they are returned as `warnings[]` (`code: "bookings_outside_shift"`, with booking ids and times — AD-SCH-02) and **never cancelled or moved**. The same cross-branch gap rule applies to manual shifts on one day.

**P2-RULE-09 · Leave.** 🔒 D-LV-01..05. A leave is employee-level (all branches). Half-day (`day_portion` 2 MORNING / 3 AFTERNOON) only when `start_date = end_date` (DB CHECK → 422 `half_day_single_date`); the split time is `leave.half_day_cutoff_time` (default 13:00 MMT — D-LV-05). Overlap with another PENDING / APPROVED leave of the same employee → 409 `leave_overlap` (DB EXCLUDE on half-day units). Anyone may request for themselves; on someone's behalf (branch scope — the employee must be in scope) `leave.create` requests, `leave.update` edits and `leave.delete` cancels (PENDING only — "delete" in the matrix = cancel, the row is kept, ADR-011 #3). **While PENDING** the requester (or `leave.update` / `leave.delete`) may edit or cancel. Approve / reject = `leave.approve` with the employee in scope (P1-RULE-11 target set); 🔒 a user cannot decide a leave whose `employee_id` is their own employee (422 `self_approval` — owner 01/Oct 21:20, §16 #4 ✅; a manager who requested on behalf may still approve). The employee of the leave may edit / cancel it while PENDING even if someone else requested it. An APPROVED leave can be cancelled only by `leave.approve` (🔒 §16 #3 ✅ — the employee asks their manager). **Create, edit, approve, reject and cancel** are refused with 423 `payroll_finalized` when any date of the leave (on an edit: the old or the new dates) lies inside a FINALIZED / PUBLISHED / PAID payroll period — the check is Part 5 **`PayrollLock.assertNotFinalized(tx, { employee_ids: [employee_id], dates })`**, the shared payroll advisory lock of Part 0 API-IDEM-06, taken before the leave row is locked (contract 3; v1.4 covered edit / cancel — create and the two decisions added by the review fix of 02/Oct, R1-9: each of them calls `redetect` and would flip an exception that payroll has already deducted). A PENDING leave still inside the period shows as the run warning `pending_leaves { count }` before finalize (Part 5), so it is decided first; after finalize it can only be decided once the run is reopened. `start_date ≥ today − 7` for create and edit (⚠️ back-dated sick leave before payroll); **v1.4:** when the create comes from Part 5 **P5.EXC.02 `create_leave`** (an attendance exception resolved as leave), `start_date` may go back to the **start of the oldest non-finalized payroll period** (`PayrollLock.lastFinalizedEnd()` + 1 day) instead. **v1.4 (P5-RULE-14):** a create, edit, decision or cancellation whose dates include today or a past date calls `AttendanceDetector.redetect(employee_id, dates[], actor)` in the same transaction (P2.LV.03 / 05 / 06 / 07 / 08 — an APPROVED leave resolves a covered OPEN ABSENT exception to LEAVE; a LEAVE-resolved exception whose leave is rejected or cancelled returns to OPEN). PENDING and APPROVED both block availability (D-LV-04); REJECTED / CANCELLED free it. Every request, decision and cancellation raises the realtime event `leave.requested` / `leave.decided` / `leave.cancelled` (§13), and a request / decision the **notification types** `leave.requested` / `leave.decided` / `leave.cancelled` (§13 — catalogue Part 8 §15; realtime + notification as locked in v1.3 — D-LV-02, D-NTF-01) and returns `affected_bookings[]` = BOOKED bookings of the employee inside the leave interval (AD-LV-02; never deleted — D-BKG-19).

**P2-RULE-10 · Availability — one function.** 🔒 D-BKG-04/05/06/07/08/23, D-SCH-03, D-SVC-07, D-LV-04/05, D-WEB-04 (§6.4b A-2). For `(branch, location, items, date range, employee | any, exclude_booking_id?)`:
0. **Items are validated first** exactly as the quote does (`service_inactive`, `category_inactive`, `not_sold_here`, `variant_required` → 422 with `errors[]`), and the date range must lie inside the window (422 `outside_window`).
1. **Candidates** = employees ACTIVE, assigned to the branch on the date, eligible for **every** item on the date (HOME → `home_allowed`), or the single requested employee if it qualifies (else `[]`). No candidate at all → every date `full` and `no_eligible_employee: true` in the response (FE shows "no barber does this here" instead of "fully booked").
2. **Block length** = `travel_before + Σ duration_i + Σ buffer_i + travel_after` where `travel_* = home_service.travel_minutes` (branch setting) for HOME and 0 for BRANCH (D-SCH-03). `ends_at = starts_at + Σ duration_i` is what the customer sees; the block is what the barber is busy for (🔒 buffers are **summed** per item — owner 01/Oct 21:20, §16 #1 ✅: cut 5 + colour 10 = 15 minutes of clean-up).
3. **Free time per candidate and date** = union of that employee's shifts **at this branch** on the date (adjacent shifts merged) **minus**: blocks of their BOOKED / STARTED bookings at any branch (`block_starts_at … block_ends_at`, excluding `exclude_booking_id`), leave intervals (PENDING / APPROVED; FULL = whole day, MORNING = day start → cutoff, AFTERNOON = cutoff → day end), in-progress visits (STARTED, no `completed_at`, **`visits.is_late_entry = false`** — v1.4: a late entry records the past and must not block the barber's current slots; **each** in-progress visit counts — a barber may have several at once, owner B1 / Part 4 P4-RULE-02): busy `[started_at, max(now, estimated_end)]` where `estimated_end` = `started_at` + Σ (duration + buffer) of the visit's planned items — the `booking_items` snapshot for a booking-origin visit, or the quote of the sale's active SERVICE lines on `visits.business_date` for a walk-in, or `now + slot_interval` when the sale has no service line yet (🔒 §16 #6 ✅); and everything up to and including now — the first offered start is the **slot boundary strictly after now** (D-BKG-23 — at 10:00:00 with a 15-minute grid the first slot is 10:15; MMT).
4. **Dates** = `today … today + booking.advance_window_days` inclusive — the furthest bookable date is today + 14, so the strip has 15 chips (Part 3 / the public modal use the same definition; FE-BK-08 "14 days" = 14 days ahead) (D-BKG-06, public **and** staff); a date in `branch_closures` is `closed` (🔒 for staff bookings too — §16 #2 ✅); the date strip state is `available` / `full` / `closed`.
5. **Slots** = start times on the slot grid (`booking.slot_interval_minutes`, default 15, aligned to midnight MMT) whose whole block fits inside one free interval — including the buffer and, for HOME, the travel parts (a last slot whose clean-up would run past the shift end is not offered — 🔒 §16 #8 ✅). `employee = any` → the union of candidates' slots with the list of free employees per slot (D-BKG-05 — the client lets the customer pick one; no auto-assignment).
6. The function is called in-process by Part 3 (booking create / reschedule re-check inside the transaction, before the DB EXCLUDE — D-BKG-08 first-success-wins) and by the public endpoints (`/v1/public/booking/availability` — Part 3), and over HTTP by the staff screens (§11). Results are never cached (`Cache-Control: no-store`).

**P2-RULE-11 · Operational reads for staff, management reads and writes by code.** 🔒 (v1.2 — owner 01/Oct 21:20, ADR-011 #4 / #5). **Read scope** of a caller = branches of their active `employee_branches` assignments ∪ branches covered by any permission grant (P1-RULE-05 v1.3) — so a barber with no permission code still reads their own branches.
- **Operational reads — any staff in read scope, no code** (POS, booking, calendar and pickers need them; unticking a `view` code never breaks checkout): P2.CAT.01 (active), P2.SVC.01 (services sold at a branch), P2.SVC.03, P2.OPT.01, P2.OPT.03, P2.PRC.06 (quote), P2.SHF.01 (roster / calendar shifts, leave blocks, closures), P2.LVT.01 (active types for the request form), P2.AVL.01–03, plus P1.EMP.09 (picker).
- **Own data — session, no code:** P2.SHF.02, P2.LV.02, and P2.ELG.03 / P2.PAT.01 / P2.LV.04 / P2.LV.09 when the employee is the caller.
- **Filters:** `status` (active / inactive) on the operational lists is open; only **archived** rows (`include_archived=true`) and the `sold=all` view are management reads. `sold=all` (v1.3) needs `branch_id`, which must be covered by the caller's `service.*` grant (company scope = any branch) — otherwise the page is empty (API-PERM-03).
- **Management reads — `<module>.view⁺`** (= the view code or any other code of the same module, API-PERM-06): `include_archived=true` on P2.CAT.01 / P2.SVC.01 / P2.LVT.01 and `sold=all` on P2.SVC.01 (`service.view⁺` / `leave_type.view⁺`) · price grid with scheduled grids and price history P2.PRC.01 / 03 (`price.view⁺`) · eligibility matrix and an employee's eligibility rows P2.ELG.01 / 03 (`eligibility.view⁺`) · someone else's pattern P2.PAT.01 and the conflicts list P2.SHF.07 (`schedule.view⁺`) · other employees' leave P2.LV.01 / 04 / 09 (`leave.view⁺`, which includes `leave.approve`).
- **Writes** need the codes in §12 at the **data level of the target** (v1.3 — ADR-012, API-PERM-07): company master (categories, service master, options, order, archive, leave types) = company scope; branch data (P2.SVC.06 per item, prices, eligibility, patterns / shifts, leave) = the branch(es) in scope. For actions whose target is an **employee** (eligibility, pattern, shifts, leave on behalf / approve) the branch set is the P1-RULE-11 target set (the employee's active assignments; for a pattern write the union of the old and new segment branches). Out-of-scope single reads → 404 (API-PERM-03).

**P2-RULE-12 · Audit actions in this part.** 🔒 D-AUD-01. `category.create / update / archive / reorder`, `service.create / update / archive / reorder / branches_set / options_set`, `price.set / copy / withdraw`, `eligibility.set`, `schedule.pattern_set`, `shift.create / update / archive`, `schedule.day_reset`, `schedule.generate`, `leave_type.create / update / archive`, `leave.request / update / cancel / approve / reject`. Price and schedule writes store the before / after diff (`audit_events.changes`). **`branch_id` of these rows follows API-AUD-01** (review fix 02/Oct): the per-branch sale switch (one row per branch written), prices, eligibility and single-shift writes = their branch; a pattern set = its segments' branch when they all share one, else the employee's primary branch; leave actions and other employee-targeted writes = the employee's **primary branch** (earliest active assignment — Part 5 P5-RULE-04; NULL without an active assignment — reconcile 02/Oct); otherwise — and for categories, the service master, options and leave types — NULL (read at company scope only — Part 8 P8-RULE-06).
