**P8-RULE-02 · Notifications — catalogue, emit, recipients, bell.** 🔒 D-NTF-01..03, D-PLT-03, F-P8-03/04 + owner F12 + research E11 / E12 + contract 14 + ADR-007.
- **Catalogue** = `notifications.json` in the repo (D-ROLE-08 pattern): per type `{ code, category (1 BOOKING · 2 STAFF · 3 MONEY · 4 STOCK · 5 PAYROLL · 6 SECURITY), mandatory, recipient_rule (1 ADMINS · 2 BRANCH_MANAGERS · 3 TARGET_USER · 4 BRANCH_STAFF), related_code?, exclude_actor (default true), template_key, link_pattern, toast (AD-NTF-03) }`; `sync.code_tables` (deploy) upserts one `notification_types` row per company (new → `enabled = true`; removed from the file → `archived_at`; `is_mandatory` and `category` follow the file; `enabled` is kept, mandatory forces true — DB CHECK `notification_types_mandatory_chk`). The full catalogue of all parts is §15.
- **Enable / disable (company level only — research E12):** P8.NTT.02 (`notification.update`, company scope). A disabled type creates no rows. A mandatory type → 409 `notification_mandatory`. **No per-user mute** in V1 (the Part 8 constraints-file comment "mandatory type = user ပိတ် ✖" means "cannot be disabled", nothing more).
- **`Notifications.emit(code, { branch_id?, entity_type?, entity_id?, payload, link_params, recipients?, actor_user_id? })`** — owned here, called by every part **after commit** (API-RT-02; best effort, like realtime — ADR-002 event rule). Recipients:
  - **1 ADMINS** = active users holding the type's `related_code` through a **company-scope** assignment; none → the company admins (P1-RULE-12) — owner **F12**.
  - **2 BRANCH_MANAGERS** = holders of the `related_code` through a branch-scope assignment that lists the branch **+** company-scope holders who are assigned to that branch (`employee_branches` open on today) — contract 14; a part that computes its own list (no-show alarm, discount requests, low stock, `expense.pending` …) passes `recipients` explicitly and documents it.
  - **3 TARGET_USER** = `recipients` given by the emitter — also the stored rule of a type whose recipients the emitter computes case by case and that fits no other rule (`leave.cancelled` — §15): `notification_types.default_recipient_rule` is NOT NULL with CHECK 1–4, so every catalogue row carries one of the four numbers (review fix 02/Oct — R3-15). **4 BRANCH_STAFF** = active staff with an open assignment to the branch (or the emitter's explicit receiver).
  - Always: only users who can sign in (`users.status` 1 ACTIVE or 2 INVITED and `employees.status` 1 ACTIVE — D-DB-03), minus the actor when `exclude_actor`; the one exception is **`account.deactivated`**, stored for the deactivated user **and** sent to the company admins (research E11 — the user may never open the bell again).
- One row per recipient: `template_key` + `payload` (no text in the DB — the client renders in the viewer's language, D-PLT-03), `link_path` from `link_pattern` (AD-NAV-06), `entity_type` / `entity_id`, `branch_id`. Then realtime `notification.created { notification_id, type_code, category, unread_count, toast }` to `user:<id>`.
- **Bell** (AD-NTF-01): list newest first (P8.NTF.01), exact unread count (P8.NTF.02 — the UI caps at 99+), mark one / all read (idempotent), delete own = soft `deleted_at` (D-NTF-02). Multi-device sync: `notification.updated` / `notification.read_all`.
