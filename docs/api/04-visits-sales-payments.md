## မြန်မာ အတိုချုပ် (Owner အတွက်)

- ဒီ part = **ဆိုင်ထဲမှာ customer တစ်ယောက် ဝင်လာကနေ ငွေရှင်းပြီး receipt ထွက်တဲ့အထိ** — START (walk-in / booking / ကိုယ်စားမှတ် / အိမ် / နောက်မှသွင်း) → service · product ထည့် → "Service ပြီး" → ငွေယူ (Cash / KBZPay / ခွဲပေး) → **FINISH** (receipt နံပါတ်) → refund / ပြင်ဆင်ချက်။ Endpoint **၅၅ ခု**, permission code **၂၂ ခု** (§9)။ DB = Part 4 **v1.2** — FINISH ပြီးသား sale ကို DB trigger နဲ့ပါ ကာ (G)။
- **Barber တစ်ယောက် customer ၂ ယောက် တပြိုင်နက် ရ** (ဆိုးဆေး စောင့်တုန်း walk-in ညှပ်) — "ငွေမရှင်းရသေး" visit ရှိမှပဲ နောက်တစ်ယောက် START ပိတ် (B1)။ Ko Aung အိမ်ပြန်သွားပြီး visit ကျန်ခဲ့ရင် **Manager / Admin** က reason နဲ့ ကိုယ်စား ငွေလက်ခံ / FINISH / Incomplete (B2)။ "ငွေလက်ခံသူ" ရွေးစာရင်း = ဒီ branch ဝန်ထမ်း အကုန် (clock-in ထားသူ အပေါ်ဆုံး) (B3)။
- **ဈေး = system က တွက်** (Part 2 price quote — barber ဈေးမရိုက်)။ Booking မှာ Ko Aung (8,000) နဲ့ ချိန်းပြီး တကယ်လုပ်တာ Ko Min (6,000) ဆို = **နည်းတဲ့ဈေး 6,000** (B4)။ ဈေးပြောင်း = Admin / Manager (`sale.override_price`) + reason — barber ✖။
- **Discount:** code (**Admin ပဲ** ဖန်တီး) ဒါမှမဟုတ် app ထဲ "လျှော့ခွင့် တောင်း" → ဒီ branch မှာ approve ခွင့်ရှိသူ **အကုန်ဆီ** noti → **ကိုယ့် request ကိုယ် approve ✖** → approve ပြီးမှ service ထပ်ထည့်လည်း discount **မတိုး** — approve လုပ်ချိန်က ရှိပြီးသား line တွေပေါ်မှာပဲ တွက် (B7) · approve ပြီးသား discount ကို ငွေမရှင်းခင် ပြန်ဖြုတ်လို့ ရ။ % discount = **၁၀၀ ပြည့်** — 6,500 ရဲ့ 15% = 975 → **1,000** (စုစုပေါင်း 5,500) (B6 — အနီးဆုံး ၁၀၀: 945 ဆို 900)။
- **ငွေ:** KBZPay = reference မဖြစ်မနေ + နံပါတ်တူ ၂ ခါ ✖ (ငွေပေးပုံ ပြင်ထားတဲ့ payment ပါ စစ်)။ ဈေး 7,000 ကို KBZPay **10,000** လွှဲပြီး **3,000 cash ပြန်အမ်း** = FINISH မှာ system က "ပိုငွေ ပြန်အမ်း" (RF receipt) auto မှတ် — ဝင်ငွေ / commission မထိ၊ စာရင်းပိတ်မှာ cash ရော KBZPay ရော ကိုက် (B5)။ KBZPay ✔ = စာရင်းပိတ်ပြီး မနက်မှ စစ်လည်း ရ (E3)။
- **FINISH** = receipt နံပါတ် `B3-2026-OCT-00125` (branch + လ အလိုက် ဆက်တိုက်၊ မကျော်) → ပြင်မရ။ Receipt = English · **PDF / Share = ဖုန်းတိုင်း** · Print = Android + Bluetooth · reprint = server က ထုတ်ပြီး **သိမ်းထားတဲ့ ဖိုင်တူ** (H)။ iPhone သုံးတဲ့ barber ရဲ့ receipt ကို Android colleague က "ဒီနေ့ receipt စာရင်း" (ငွေပမာဏ မပါ) ဒါမှမဟုတ် နံပါတ်နဲ့ ရှာပြီး print ရ။
- **FINISH ပြီးမှ ပြင်:** refund = **Admin ပဲ** (B12) · sale လုပ်ခဲ့တဲ့ branch မှာပဲ · product = "စင်ပေါ် ပြန်တင် / ပျက်စီး" ရွေး · KBZPay နဲ့ ဝယ်တာ cash နဲ့ ပြန်ပေးရ (B8)။ ငွေပေးပုံ / barber / ငွေလက်ခံသူ ပြောင်း = Admin (`sale.adjust`) — **စာရင်းပိတ်ပြီးတဲ့ရက် ✖** (admin reopen) · **payroll finalize ပြီး barber ပြောင်း ✖** (manual payroll line) (B9)။ KBZPay ref စာလုံးမှား / customer မှား = reason နဲ့ တိုက်ရိုက်ပြင် · ဈေးနည်းယူမိ (7,000 → 10,000) = မူလ barber အတွက် "**ကွာငွေ sale**" 3,000 (B10) — **customer က ကွာငွေ လာပေးတဲ့အချိန်မှ ဖွင့်** · အဲ့နေ့ စာရင်းမပိတ်ခင် FINISH (သို့) cancel (E2)။ Refund (ပစ္စည်း / service ပြန်အမ်း — kind 1) စုစုပေါင်း = **sale total ထက် မပို** (line တစ်ခုချင်း = အဲ့ line ရဲ့ net ထက် မပို) · ပိုလွှဲငွေ ပြန်ပေး (kind 2): FINISH မှာ အလိုအလျောက် အမ်းငွေ = ပေးငွေ − total (code မလို) · payment အဖြစ် မမှတ်ထားတဲ့ ၂ ခါလွှဲငွေ ပြန်ပေး = `sale.refund` + reason + reference၊ တစ်ခါချင်း ≤ sale total နဲ့ cash မဟုတ်တဲ့ payment စုစုပေါင်း ထဲက ကြီးတာ — kind 2 က kind 1 ရဲ့ အကန့်အသတ်ကို မစားဘူး (🔒 D-PAY-05)။
- **နောက်မှ သွင်း (late entry):** စက္ကူ / မေ့သွား → **စာရင်းမပိတ်ရသေးတဲ့ ရက်မဆို** (B11) · ဈေး = အဲ့ရက်ဈေး · ဝင်ငွေ + cash = အဲ့ရက် စာရင်းထဲ · **စချိန် / ပြီးချိန် / ငွေယူချိန် / FINISH ချိန် ၄ ခုလုံး မဖြစ်မနေ ရိုက်** · payroll finalize ပြီးသား လထဲက ရက် ✖ (admin က manual payroll line နဲ့ ပြင်) · barber role default ✔ · တစ်ယောက်ကို ပိတ်ချင်ရင် "late entry မပါတဲ့ Barber role" ပေး (B12)။

## 1. Rules specific to this part

**P4-RULE-01 · Visit ≠ Sale — one state machine, guarded by the DB.** 🔒 D-VIS-01/07/08/09, F-P4-01/12/13, owner G (f).
- `visits` = the service (START / COMPLETE / INCOMPLETE); `sales` = the money document (lines, discount, payments, receipt). A service visit has exactly one sale (`sales.visit_id` unique); a **visit-less sale** is either a **product-only sale** (🔒 D-PAY-03) or a **difference sale** (owner B10 — P4-RULE-12). Service lines live in `sale_items` (no visit-items table).
- Transitions (any other → 409 `invalid_transition` with `context.status`):

  | Object | Transition | Endpoint |
  | --- | --- | --- |
  | visit | — → 1 STARTED (+ sale 1 OPEN) | P4.VIS.03 START |
  | visit | 1 → 2 COMPLETED ("Awaiting payment") | P4.VIS.05 |
  | visit + sale | 2 → 3 FINISHED + sale 1 → 2 FINISHED | P4.SAL.10 FINISH |
  | visit + sale | 1 / 2 → 0 INCOMPLETE + sale 1 → 0 CANCELLED | P4.VIS.06 |
  | visit-less sale | 1 → 2 FINISHED · 1 → 0 CANCELLED | P4.SAL.10 · P4.SAL.11 |
  | booking (Part 3 row) | 1 BOOKED → 2 STARTED (START) → 3 COMPLETED (FINISH **or** INCOMPLETE) | P3-RULE-09 |

- **Business dates** (🔒 D-PLT-15): visit = MMT date of `started_at`; sale = MMT date of `finished_at` (the revenue day — F-P4-12); refund = MMT date of `refunded_at`.
- **Immutability** (🔒 D-VIS-08 + owner G): DB Part 4 v1.2 triggers — `sales_finished_guard` (a FINISHED / CANCELLED sale may change only `customer_id` + `updated_at` — owner B10), `sale_items_finished_guard` (no UPDATE / DELETE once the sale is FINISHED / CANCELLED), `payments_finished_guard` (on a FINISHED sale only `verified_at`, `verified_by_user_id`, `external_reference` — B10 / E3), `visits_final_guard` (FINISHED / INCOMPLETE visit: only `updated_at`). **The services check the state first: every direct write on a FINISHED / CANCELLED sale — lines, price, discount, payment add / void, collector change — answers 409 `invalid_transition { status, correction_path }`** with `correction_path` = `adjustment` (method / performer / collector) · `refund` (overcharge, void) · `difference_sale` (undercharge) — one rule for all of them, never 423 `locked` (review R1-25). **v1.1 (owner S17):** `correction_path` is sent only where this rule names a correction. It is **omitted** for a **payment add on a FINISHED sale** and for **every write on a CANCELLED sale** — those answer 409 `invalid_transition { status }` without the member (nothing corrects them; the member is optional in `Problem.context`). Every other case stays as written here. The triggers are the second wall, not the message source: a violation raises SQLSTATE `P0001` `finished_immutable`, which Part 0 maps to 423 `locked`; because every writer locks the sale row before its state check (P4-RULE-10), no endpoint reaches it by design.

**P4-RULE-02 · START — walk-in, booking, proxy, home, late entry.** 🔒 D-VIS-01..04, 10..13, D-AUTH-07, D-SVC-06, P3-RULE-09 + owner B1 / B4 / B9 / B11. `POST /v1/visits` (P4.VIS.03) with `Idempotency-Key` (stored as `client_request_id` on **both** the visit and its sale — same value, each table has its own unique index; identifying fields for `idempotency_mismatch` = `branch_id`, `booking_id`, `performed_by_employee_id`). Steps, in one transaction:
1. **Branch** in the caller's read scope (P1-RULE-05); else 403 `out_of_scope`.
2. **Performer** = `performed_by_employee_id`, default the booked barber (booking) or the caller's employee (walk-in — D-AUTH-07). Must be ACTIVE and assigned to the branch on the visit date (422 `not_assigned_to_branch`). **Performer ≠ caller** → `proxy_reason` required (1 PHONE_UNAVAILABLE · 2 OTHER — 400 `reason_required`); performer = caller → `proxy_reason` must be null. No note field (🔒 §10.6 #16, AD-POS-03).
3. **Late entry** (`late_entry` present — P4-RULE-13): needs `sale.late_entry` for the branch; `late_entry.started_at` is **required** (400 `validation`) and becomes `visits.started_at`; a normal START has no start-time field and uses `now()`. Visit business date = MMT date of `started_at`.
4. **Day lock** — `DayLock.assertOpen(branch, visit business date)` for **every** START (owner B9: a closed day takes no new sale; refused at START rather than at FINISH) → 422 `day_closed` (`context.correction_path = "reopen"`). **Late entry only — then the payroll lock:** `PayrollLock.assertNotFinalized(tx, { employee_ids: [performer], dates: [visit business date] })` (Part 5 P5-RULE-10) → **423 `payroll_finalized`**: a service day inside a FINALIZED / PUBLISHED / PAID payroll period takes no new sale, because no later run would pay its commission (🔒 D-COM-01/04) — the correction is a MANUAL payroll line (owner B9). Both advisory locks are taken before any row lock (P4-RULE-10 lock order).
5. **Unpaid block** (🔒 D-VIS-07 + owner B1): if the performer has a **non-late-entry** visit in 2 COMPLETED whose sale is still OPEN → 422 `unpaid_visit_open { visit_id }` ("Finish payment for your previous customer first" — AD-POS-04). Any number of STARTED visits per performer is allowed (dye processing + a walk-in cut). Late-entry STARTs are not blocked and late-entry visits block nobody (a backlog must not stop the chair).
6. **From a booking** (`booking_id`): `SELECT … FOR UPDATE` on the booking (P3-RULE-09 — after the advisory locks of step 4); must be **1 BOOKED** (2 STARTED → 409 `invalid_transition { status, visit_id }`; 0 CANCELLED → 409 — a no-show-cancelled customer is started as a walk-in, P4-RULE-13); same branch (422 `booking_other_branch`); `bookings.business_date` = the visit business date (422 `booking_not_today`). Performer ≠ booked barber → `performer_change_reason` required (🔒 D-VIS-04). Location, `home_address` and transport fee come from the booking; `sales.customer_id` = the booking customer. Each `booking_items` row becomes a SERVICE line (`booking_item_id` set, description snapshot — F-P4-11), priced by P4-RULE-05 (owner B4). Booking → 2 STARTED; the no-show jobs become no-ops (P3-RULE-08).
7. **Walk-in:** no customer questions (🔒 D-VIS-02). `location_type` default 1; HOME → `home_address` required (422 `home_address_required`). Optional `items[]` = first services (no reason — D-VIS-02 v5.1), each added as P4-RULE-04.
8. **Insert** visit (1 STARTED, `started_by_user_id` = caller = "Recorded by", late-entry fields) + sale (1 OPEN, `branch_id` = visit branch) + lines; HOME → exactly one TRANSPORT_FEE line (list = booking snapshot or branch setting `home_service.transport_fee_amount`; 0 = the shop pays — 🔒 D-SVC-06). Totals per P4-RULE-06.
9. **After commit:** realtime `visit.started` (+ `booking.started`), audit `visit.start`. Response **201** `Visit` (with its `sale` and `warnings[]`), replay **200**.

**P4-RULE-03 · Who may act on a visit or sale — "self" sets and the codes for everyone else.** 🔒 D-VIS-04/06/12, D-ROLE-07 ("own work needs no code"), ADR-011 + owner B2. All checks use the **branch of the visit / sale** (branch data — ADR-012).

| Action | Self — no code | Anyone else needs |
| --- | --- | --- |
| Read the visit / sale | performer (of the visit or a line), recorder (`started_by`), finisher, creator of a visit-less sale | `visit.view⁺` / `sale.view⁺` |
| Lines (add, option, quantity, remove) and COMPLETE — "line actors" | performer, recorder (proxy 1 **or** 2), creator | `visit.update` (the one code for someone else's open lines — also the lines of someone else's OPEN product-only sale; there is no `sale.update`) |
| Discount code / request, payments (add, void, collected by), FINISH — "checkout actors" | performer, recorder of a **PHONE_UNAVAILABLE** (1) proxy visit (🔒 D-VIS-12 — that visit only), creator of a visit-less sale; for a **difference sale** also the original line's effective performer (P4-RULE-12) | **`sale.finish_override`** + `override_reason` on FINISH (🔒 D-VIS-06 "override + reason"; seed Admin + Manager — owner B2) |
| INCOMPLETE | performer, PHONE_UNAVAILABLE recorder | `visit.delete` (cancel — record kept) |
| Cancel an OPEN visit-less sale | creator | `sale.delete` |
| Price override | — | `sale.override_price` |
| Late entry | — | `sale.late_entry` (and then the self rules above) |
| Refund · adjustment · difference sale · change a sale's customer | attach a customer to a sale that has none: performer / finisher on the sale's business date | `sale.refund` · `sale.adjust` |

"Creator" of a visit-less sale = the `actor_user_id` of the **DB-trigger audit row of that sale's INSERT** — `audit_events` with `source = 2` (DB_TRIGGER), `action = 'INSERT'`, `entity_type = 'sales'`, `entity_id` = the sale id, written by the `audit_sales` trigger inside the creating transaction from `app.user_id` (D-AUD-02; there is no DB column). It is read through the index `(entity_type, entity_id, occurred_at)` — the oldest row — and never changes, so the sale loader may cache it for the request (review R1-28). A help-record proxy (2 OTHER) never takes payment: checkout stays with the performer (🔒 D-VIS-04). Decorators: `@Can(code, { branch: 'entity.branch_id', orSelf: '<resolver>' })` with the named resolvers `visit.lineActors`, `sale.checkoutActors`, `visit.incompleteActors`, `sale.readers` (Part 0 amendment — API-PERM-02 `orSelf` may name an actor-set resolver). Denials → 403 `forbidden` with `context.required` (the code that would allow it). There is no performer change on an OPEN visit (AD-POS-11): a wrong performer is fixed by INCOMPLETE ("recorded for the wrong barber") + a new START, or after FINISH by a PERFORMER adjustment.

**P4-RULE-04 · Lines.** 🔒 D-VIS-02/05, D-SVC-05/06, D-PAY-03, F-P4-02/11 + owner B10.
- **Only while the sale is OPEN** (FINISHED → 409 `invalid_transition` with `correction_path`; CANCELLED → 409 `invalid_transition` without it — P4-RULE-01 v1.1). SERVICE lines need a visit; the single line of a **difference sale** is written only by P4.SAL.13 — P4.SAL.04 / 05 / 06 on a difference sale answer 422 `difference_line_type` (a wrong amount = cancel it and create it again — P4-RULE-12); `performed_by_employee_id` = the visit performer (V1 — F-P4-02). `quantity` = 1 for SERVICE / TRANSPORT_FEE.
- **Add service** (P4.SAL.04): item checks as the Part 2 quote (`service_inactive`, `category_inactive`, `not_sold_here`, `variant_required` → 422). HOME visit → the performer must be `home_allowed` for the service (422 `not_eligible` — 🔒 D-SVC-06); BRANCH visit → an ineligible service is **recorded with** `warnings[] not_eligible` (the real-time record beats the matrix — RISK-01). `added_reason` required (400 `reason_required`) for a service not in the booking (booking-origin visit — 🔒 D-VIS-05) and for any service added **after COMPLETE**; walk-in services added before COMPLETE need none (🔒 D-VIS-02 v5.1, AD-POS-04).
- **Add product:** `is_sellable`, ACTIVE, not archived (422 `product_not_sellable`); list price = `products.sell_price_amount` at add time; quantity ≥ 1; stock shown, never blocking (owner D5 — the movement is posted at FINISH, P4-RULE-10).
- **Change option** (P4.SAL.05 `service_variant_id`): re-priced by the quote (P4-RULE-05); an override on that line is cleared; a booking-origin line needs `reason` (kept in the audit row — DB has no column; AD-POS-04). **Quantity** = PRODUCT only.
- **Remove** (P4.SAL.06): `removed_at` + `removed_by_user_id` + `removed_reason` (row kept — D-DAT-05, DB CHECK). The TRANSPORT_FEE line cannot be added or removed by hand (422 `transport_line_locked` — reduce it with a price override, 🔒 D-SVC-06). Removing the last SERVICE line of a COMPLETED visit → 422 `service_required`.
- Every line change recomputes the totals (P4-RULE-06) under the sale row lock and emits `sale.updated`.

**P4-RULE-05 · Prices — one source, the lower price when the barber changes.** 🔒 D-SVC-03/04/05/06/08, P2-RULE-05, API-DATA-07 + owner B4 / B11.
- Every SERVICE / TRANSPORT price comes from the **Part 2 quote in-process** for (branch, location, **performer**, variant, **visit business date**) — walk-in = today, late entry = the service date (Part 2 v1.4 window = any not-closed date — owner B11). The client never sends a service price.
- **Booking-origin lines:** list price = the booking item snapshot (🔒 D-SVC-04) when the performer is the booked barber. When the **performer ≠ booked barber** (owner B4): list price = **min(booking snapshot, quote for the actual performer on the appointment date)** (`bookings.business_date` = the visit business date — the day of the service, not the day the booking was made) — the customer never pays more than quoted nor a senior's price for a junior's work; `warnings[]` `booked_price_kept` / `performer_price_lower { booked_amount, performer_amount }` per line. A not-sold quote for the performer keeps the booking price.
- **Option change** = the quote price for the new variant (not the snapshot — the item changed).
- **Product** = company sell price; **transport fee** = booking snapshot / branch setting at START.
- **Override** (P4.SAL.07, `sale.override_price` — admin / manager; barbers never — 🔒 D-SVC-04, F-P4-03): sets `unit_price_amount` ≠ `list_price_amount` with `price_override_reason` + `price_override_by_user_id` (DB CHECK); sending the list price back **resets** the override. Up or down. Discount and override may both apply (the discount splits over the charged prices). There is no self rule: a holder may override the price of a line they performed themselves, with the code and the reason — it is a recorded price decision (🔒 D-SVC-04), not a discount approval, so owner B7 b does not apply (review R1-30).

**P4-RULE-06 · Totals, discount split and rounding.** 🔒 D-PAY-04 v5.1 + OPEN-36, D-PAY-08, API-DATA-02 + owner B6 / B7 d. Computed by the server on every change while OPEN (never sent by the client), frozen at FINISH:
- `subtotal` = Σ active lines (`unit × qty`); `eligible` = Σ active **non-transport** lines.
- **Code:** PERCENT → `round_to(eligible × p / 100, R)` with **R = setting `sales.discount_round_to_amount` (100 — owner B6: 15 % of 6,500 = 975 → 1,000)**; `round_to` = to the **nearest** R, half up (6,300 → 945 → 900) — the default reading of B6 "၁၀၀ ပြည့်", whose only example (975 → 1,000) fits both "nearest" and "up"; AMOUNT → the value. Capped at `eligible`.
- **Approved request** (owner B7 d — review R1-17): the discount applies only to the **lines that existed at approval** — the active non-transport lines with `sale_items.created_at ≤ discount_requests.decided_at` ("approved lines"). For a request, `eligible` = Σ approved lines still active; PERCENT → `round_to(eligible × p / 100, R)`, AMOUNT → `min(value, eligible)`. A line added after the approval gets `line_discount_amount = 0` and never enters the base (a new service does not grow the discount); removing an approved line lowers it; removing a line and adding it again creates a **new row**, which is not an approved line. Nothing is compared with an earlier amount — the figure is always recomputed from the approved lines, so it cannot ratchet. An option change or a price override on an approved line keeps it an approved line at its new price.
- **Split** (`line_discount_amount`): proportional to each eligible line's `unit × qty` (a request: the approved lines only), whole kyats by largest remainder (ties → lower `sort_order`), Σ = discount; TRANSPORT_FEE = 0 (DB CHECK). Commission base = net SERVICE lines (🔒 D-COM-02 — Part 5).
- **Service charge / tax** (only when `sales.service_charge_enabled` / `sales.tax_enabled` — default OFF, 🔒 D-PAY-08): SC = round-half-up(rate × (subtotal − discount)); tax = round-half-up(rate × (subtotal − discount + SC)); exclusive (added on top). Rates are snapshotted on the sale. ⚠️ The order is Claude's default; the owner confirms it when switching either on (D-PAY-08 🟡 — no API change, settings only).
- `total = subtotal − discount + SC + tax` (DB CHECK); `paid` = Σ non-voided payments; `remaining = max(total − paid, 0)`; `change_due = max(paid − total, 0)` (P4-RULE-09).

**P4-RULE-07 · Discount codes — master and apply.** 🔒 D-PAY-04 v5.1, F-P4-05 + owner B7 a.
- **Master = company** (ADR-012 company master — owner B7 a: Admin only): `code` uppercase `^[A-Z0-9_-]{2,40}$`, unique per company **including archived** (never reused — 409 `already_exists`); PERCENT 1–100 or AMOUNT > 0 (DB CHECK); `is_public`; `once_per_customer`; `max_uses`; `scope_type` 1 ALL / 2 BRANCHES (+ `branch_ids`, ≥ 1 — 422 `branches_required`); `valid_from` / `valid_to` (MMT); status. The code text is immutable once used (409 `code_in_use`); value, validity, branches and limits apply to future sales only. Service-restricted codes and website codes ⏭ (🔒 D-PAY-04).
- **Checkout list** (P4.DSC.02, operational): ACTIVE, non-archived, **internal** (`is_public = false`) codes valid today (or the late-entry date) at the branch and not exhausted. Public codes are never listed (the customer mentions them — AD-POS-09).
- **Apply** (P4.SAL.08, checkout actors): one discount source per sale (code **XOR** request — DB CHECK; a PENDING request, or an APPROVED one still applied to the sale → 422 `discount_source_exists` — cancel / remove it first, P4-RULE-08). Checks → 422 `discount_code_invalid { reason }`: `not_found` · `inactive` (or archived) · `not_started` · `expired` (on the sale business date) · `not_valid_here` (branch) · `exhausted` (`used_count` = FINISHED sales with the code ≥ `max_uses`); `once_per_customer` with a known customer who already used it → 422 `once_per_customer`. Everything is **re-checked at FINISH under the code row lock** (P4-RULE-10). A once-per-customer code makes the phone required at FINISH (422 `customer_required`).

**P4-RULE-08 · Discount requests — in-app approval.** 🔒 D-PAY-04 v5.1, F-P4-05, D-NTF-01/03 + owner B7 b / c / d.
- **Create** (P4.DRQ.02, checkout actors — the barber at the chair): OPEN sale, no code applied (422 `discount_source_exists`), `discount_type` + value + `reason` (required). One PENDING per sale (DB partial unique → 409 `discount_request_pending`).
- **Recipients** (owner B7 c): every holder of `discount.approve` whose grant **covers the sale branch** — branch-scope assignments listing the branch **and** company-scope holders — except the requester: notification `discount.requested` (toast — AD-NTF-03) + realtime to their user rooms; it also sits in the approvals inbox (P4.DRQ.01 — AD-NTF-04).
- **Approve / reject** (P4.DRQ.05/06, `discount.approve` for the branch): PENDING and sale OPEN (else 409 `invalid_transition`); **no self-approval** (owner B7 b → 422 `self_approval` when `requested_by_user_id` = caller). Approve → `sales.discount_request_id` = the request, discount computed on the lines existing at the decision (`decided_at` — P4-RULE-06) and applied at once (realtime `discount_request.decided` + `sale.updated`; notification `discount.decided` to the requester). It never grows afterwards (owner B7 d).
- **Cancel / remove** (P4.DRQ.04, requester or checkout actors, sale OPEN — else 409 `invalid_transition`): a **PENDING** request → 0 CANCELLED. An **APPROVED** request that is applied to the sale is **removed from the sale**: `sales.discount_request_id` = NULL and the discount / line discounts recomputed to 0 (allowed by `sales_discount_source_chk` while OPEN); the request row **stays 2 APPROVED** with its decision — DB `discount_requests_decision_chk` lets status 0 exist only with `decided_by` / `decided_at` NULL, so the decision record is not rewritten (review R1-17); the removal is the audit row `discount_request.remove`, the DTO shows `applied: false` (derived: `sales.discount_request_id` = the request), realtime `sale.updated` (`change: discount`). Afterwards a code or a new request may be used. A repeat → 200 current state. FINISH while PENDING cancels it automatically (`warnings[] pending_request_cancelled`) — "no answer → finish at full price, admin refunds later" (🔒 D-PAY-04; the later correction is a **refund**, F-P4-07).

**P4-RULE-09 · Payments.** 🔒 D-PAY-01/02, D-VIS-06/07/10/12, F-P4-08/10 + owner B3 / B5.
- **Add** (P4.PAY.02, checkout actors, `Idempotency-Key`; identifying fields `sale_id`, `payment_method_id`, `amount`): OPEN sale; ACTIVE method; `amount > 0`. **Reference:** required when the method `requires_reference` (422 `reference_required`); spaces trimmed; must match `payment_methods.reference_regex` when set (422 `reference_format` — OPEN-24; the dropped setting `sales.kbzpay_reference_regex` is not used); unique per **effective** method among non-voided payments (🔒 D-PAY-02; review R1-7): the app takes `pg_advisory_xact_lock` on (method id, reference) — after the sale row lock, one per transaction — and looks for another non-voided payment with that reference whose **effective** method (P4-RULE-15) is this method, so a CASH row adjusted to KBZPay with reference X blocks a later KBZPay payment X; the DB partial unique index `payments_reference_unique` (stored method) stays the second wall. Either → 409 `duplicate_reference { receipt_number }` (AD-FORM-12).
- **Amount cap:** a **cash** payment may not exceed `remaining` (422 `amount_exceeds_remaining` — record what is kept; the "customer gave" change helper is not stored — AD-POS-08). A **non-cash** payment may exceed it (owner B5 — "KBZPay 10,000 for a 7,000 haircut, 3,000 cash back"): the excess is `change_due_amount`, returned in cash at FINISH as an automatic OVERPAYMENT_RETURN (P4-RULE-10 #15).
- **Collected by** (🔒 D-VIS-06 + owner B3): default = performer; for a PHONE_UNAVAILABLE proxy visit = the recorder's employee (🔒 D-VIS-12); may be any **ACTIVE employee assigned to the sale branch** on the sale date (422 `not_assigned_to_branch`) — P4.SAL.14 lists them, **clocked in at that branch now first** (Part 5 `Attendance.openRecordsAt(branch_id)` — P5-RULE-18, in-process, no code). Changed before FINISH with P4.PAY.04; after FINISH only by a COLLECTED_BY adjustment (P4-RULE-15). No code is needed to pick another collector (`payment.collect_override` dropped — owner B3).
- `received_at` = now; on a **late-entry visit** the body's `received_at` is **required** (400 `validation`) = the entered time (≥ `completed_at`, ≤ now — 422 `late_entry_time`). `recorded_by_user_id` = caller.
- **Void** (P4.PAY.03): OPEN sale only (FINISHED → 409 `invalid_transition`, `correction_path: "refund"`; CANCELLED → 409 `invalid_transition` without `correction_path` — P4-RULE-01 v1.1), reason required, row kept struck through (D-DAT-05). Collector change (P4.PAY.04) the same (`correction_path: "adjustment"` — type 3).
- **Day lock:** add, void and collector change call `DayLock.assertOpen(branch, the sale's prospective business date)` (today, or the late-entry payment date) → 422 `day_closed` (owner B9) — **first, before the sale row lock** (P4-RULE-10 lock order).
- **Closing:** an OPEN sale that holds a non-voided payment **received on an earlier day** blocks the closing of that day (409 `open_sales_exist` — Part 7 P7-RULE-06 #4 ii; the money already sits in that day's drawer / KBZPay): finish the sale, void the payment, or mark the visit Incomplete / cancel the sale (reconcile 02/Oct).
- **Verification** — P4-RULE-17. **Reference correction** — P4-RULE-16.

**P4-RULE-10 · FINISH — one short transaction, fixed lock order.** 🔒 D-VIS-02/06/07/08, D-PAY-04/06, D-CUS-03, D-COM-04, F-P4-04/05/12/13 + owner B5 / B9 / B10. `POST /v1/sales/{id}/finish` (P4.SAL.10) — **idempotent by state** (contract: no `Idempotency-Key`; already FINISHED → **200** current state):
1. **Read** the sale without a lock (branch, kind, late-entry flag — none of them changes after creation). A sale that is already FINISHED → **200** current state, CANCELLED → 409 `invalid_transition` — answered here, before any lock (both states are final, so a repeat never meets `day_closed`). `finished_at` = now; on a **late-entry visit** the body's `finished_at` is **required** (400 `validation`; ≥ `completed_at` and ≥ the latest `received_at`, ≤ now — 422 `late_entry_time`, checked again under the lock) so the money lands on the service day (P4-RULE-13). Business date = MMT date of `finished_at`.
2. **Day lock** — `DayLock.assertOpen(branch, business date)` (shared advisory lock — Part 7 P7-RULE-02) → 422 `day_closed` (owner B9 / E2).
3. **Payroll lock** — for a sale with a visit and for a difference sale with a SERVICE line: `PayrollLock.assertNotFinalized(tx, { employee_ids: the performers of its SERVICE lines, dates: [business date] })` (shared advisory lock — Part 5 P5-RULE-10) → **423 `payroll_finalized`** (reachable only by a late entry or on a reopened day inside a finalized period; correction = a MANUAL payroll line — owner B9).
4. Lock the **sale** `FOR UPDATE` and re-check its status (a concurrent FINISH that won → **200** current state; CANCELLED → 409 `invalid_transition`).
5. Lock the **visit** and, for a booking-origin visit, the **booking** `FOR UPDATE` (P3-RULE-09).
6. Actor (P4-RULE-03): a checkout actor, or `sale.finish_override` + `override_reason` (400 `reason_required`; stored in the audit row — no DB column).
7. Service sale → visit must be 2 COMPLETED (422 `visit_not_completed`); visit-less sale → ≥ 1 active line (422 `no_lines`).
8. A PENDING discount request → 0 CANCELLED (`warnings[] pending_request_cancelled`).
9. Applied **discount code** `FOR UPDATE` → re-check P4-RULE-07 on the business date (422 `discount_code_invalid`).
10. **Customer:** body `customer { phone, name? }` → `matchOrCreateCustomer` (P3-RULE-01 — no `customer.create` code needed; a new phone needs `name` — 400 `validation`, AD-POS-12 / §10.6 #11); omitted / null → keep the booking customer, or none (Skip — 🔒 D-VIS-02). A once-per-customer code → customer required (422 `customer_required`) + INSERT `discount_code_customer_uses` (unique → 422 `once_per_customer`).
11. Recompute totals (P4-RULE-06); `expected_total_amount` ≠ total → 409 `total_changed { total_amount }` (another device changed the sale; AD-PERF-04).
12. **Money check:** `paid < total` → 422 `amount_mismatch { remaining_amount }` (🔒 D-VIS-07); `paid > total` is allowed only when the excess ≤ Σ non-cash payments (else 422 `amount_mismatch`).
13. **Receipt number** (🔒 D-PAY-06 v5.1, F-P4-04): `INSERT … ON CONFLICT (branch_id, kind 1, year, month) DO UPDATE SET last_seq = last_seq + 1 RETURNING last_seq` on `receipt_counters` → `<branches.code>-<YYYY>-<MMM>-<seq, 5+ digits>` (e.g. `B3-2026-OCT-00125`), year / month from the **business date**; parts stored separately (sort / search by parts). Never reused; the number is taken only here (INCOMPLETE never consumes one).
14. Update **sale** 2 FINISHED (`finished_at`, `finished_by_user_id`, `business_date`, receipt parts, frozen rates) · **visit** 3 FINISHED (`finished_at`) · **booking** 3 COMPLETED.
15. **Over-transfer change** (owner B5): `change_due > 0` → INSERT `refunds` kind 2 OVERPAYMENT_RETURN, method CASH, amount = change, reason "Change returned for over-transfer", `refunded_by` = caller, `refunded_at` = `finished_at`, RF number from counter kind 2, **`client_request_id` = a server-generated UUIDv7** (the column is NOT NULL UNIQUE and FINISH carries no key — review R3-12; a FINISH repeat stops at step 1 or 4, so no second row is ever written) — no `sale.refund` code needed (automatic), no revenue / commission effect (F-P4-06); it is exempt from the "≤ sale total" reading of a refund (7,000 sale, 20,000 transfer → 13,000 change — P4-RULE-14 caps); closing: cash −change, KBZPay +full transfer (REC-17).
16. **Stock:** `StockLedger.post(tx, actor_user_id, movements[])` (Part 6 P6-RULE-02 / 11) — one **SALE_OUT** `−quantity` per active PRODUCT line at the sale branch, `ref = sale_item_id`, `occurred_at = finished_at` (late entry: the entered time); negative allowed, `warnings[] negative_stock` (owner D5). Stock levels are locked last.
17. Enqueue **`receipt.render`** for the sale (and the change refund) **inside** the transaction (ADR-002 / ADR-013).
18. Commit → realtime `sale.finished`, `visit.finished`, `booking.updated` (status 3), `refund.created` (change); notification `sale.finished_for_you` to the performer when someone else finished it (proxy / override); audit `sale.finish` (+ `override_reason`).

**Lock order — one order in every part** (review R1-8; system design): **day lock (shared advisory `DayLock`, Part 7) → payroll lock (shared advisory `PayrollLock`, Part 5) → sale → visit → booking → discount code → customer → payments (+ the reference advisory lock of P4-RULE-09, one per transaction) → receipt counter(s) → cash-out / closing rows (Part 7) → stock level rows (Part 6) last.** The steps above are numbered in that order; START, payments, refunds and adjustments take the same prefix (advisory locks first, then the sale row). **Isolation** (review R2-1): every money write of this part runs **READ COMMITTED** with its locks taken first and every check made after them; REPEATABLE READ READ ONLY is for previews and reports only (ADR-015). Close-day takes the **exclusive** day lock as its first statement and only then reads sales (open-sale check — owner E2); payroll finalize / reopen take the exclusive payroll lock first — so FINISH never deadlocks with either: it waits, then checks against what they committed.

**P4-RULE-11 · COMPLETE and INCOMPLETE.** 🔒 D-VIS-02/03/09, F-P4-13.
- **COMPLETE** (P4.VIS.05, line actors): STARTED → 2 COMPLETED with ≥ 1 active SERVICE line (422 `service_required`); `completed_at` = now — on a **late-entry visit** the body's `completed_at` is **required** (400 `validation`; ≥ `started_at`, ≤ now — 422 `late_entry_time`); `completed_by_user_id` = caller (🔒 D-VIS-03). Repeat → 200 current state. The UI combines COMPLETE + open checkout in one tap ("Service done · Take payment" — AD-POS-04).
- **INCOMPLETE** (P4.VIS.06 — performer, PHONE_UNAVAILABLE recorder, or `visit.delete`): from 1 or 2 with an OPEN sale; reason required (🔒 D-VIS-09); **no non-voided payments** (422 `payments_exist` — void them first, so no money sits on a cancelled sale). Visit 0 INCOMPLETE, sale 0 CANCELLED (`cancelled_at`), pending discount request cancelled, booking 3 COMPLETED (F-P4-13). No receipt number, no revenue, no commission. No day lock (no money moves). Realtime `visit.incomplete`, `booking.updated`; audit `visit.incomplete`.

**P4-RULE-12 · Visit-less sales — product-only and difference sales.** 🔒 D-PAY-03, F-P4-09 + owner B10.
- **Product-only sale** (P4.SAL.03, `sale.create`, `Idempotency-Key`): OPEN sale with PRODUCT lines only; the creator works it like a visit (lines, payments, FINISH — P4-RULE-03); collector default = the creator's employee; late entry ⏭ (422 `late_entry_not_allowed` — F-P4-09); create calls `DayLock.assertOpen(branch, today)` (422 `day_closed` — owner B9, Part 7 P7-RULE-02 caller list). Cancel while OPEN (P4.SAL.11 — creator or `sale.delete`, reason in the audit row, 422 `payments_exist` first).
- **Difference sale** (P4.SAL.13, `sale.adjust`, `Idempotency-Key` = the new sale's `client_request_id`) — owner B10 for an undercharge ("haircut charged 7,000 instead of 10,000 → 3,000 more"). **It is created when the customer is paying the difference** (the same day or at a later visit) — never in advance: it is a normal OPEN visit-less sale and, like every OPEN sale, must be FINISHED or cancelled (P4.SAL.11) before the day closes (owner E2 — Part 7 P7-RULE-06 applies unchanged; a customer who has not paid yet has no difference sale). Create calls `DayLock.assertOpen(branch, today)` (422 `day_closed`).
  - **Original:** a FINISHED sale (409 `invalid_transition`) and one active **SERVICE or TRANSPORT_FEE** line of it (422 `difference_line_type`; PRODUCT ⏭ — an undercharged product is absorbed). A difference sale only corrects a price: **it never moves stock** (it cannot hold a PRODUCT line — P4-RULE-04 — so FINISH #16 posts nothing).
  - **New sale:** same branch and customer, exactly **one** line copied from the original with the **same `line_type`** — SERVICE: same `service_id` / `service_variant_id`, `performed_by_employee_id` = the original line's **effective** performer (P4-RULE-15); TRANSPORT_FEE: no service and **no performer** (DB CHECK `sale_items_type_refs_chk`) — `quantity` 1, `list_price_amount` = `unit_price_amount` = `amount`, `booking_item_id` NULL, description `"Difference for <receipt> — <line description>"`.
  - **Link to the original** — no column fits (`sales` / `sale_items` have no reference to another sale, and a type-9 `sale_adjustments` row may carry no `sale_item_id` — DB CHECK): one **type 9 OTHER `sale_adjustments` row on the ORIGINAL sale** whose `reason` starts with the fixed token **`difference_sale:<new sale id>:<original sale_item_id>`**, then ` — ` and the admin's reason, written in the same transaction. **This row is the link** in both directions (new → original: `reason LIKE 'difference_sale:<new sale id>:%'`); the DTO fields `Sale.difference_of { sale_id, sale_item_id, receipt_number }` (on the new sale) and `SaleAdjustment.difference_sale_id` (on the original) are parsed from it. A cancelled difference sale keeps its row (history).
  - **Idempotency:** the key is the new sale's `client_request_id` (unique) — a replay returns that sale with **200** and writes no second link row; identifying fields for `idempotency_mismatch` = the original sale, `sale_item_id` (both read back from the link row) and `amount`.
  - **Actors** (P4-RULE-03): the line is fixed (no line actors). **Checkout actors = the creator (the adjuster), the original line's effective performer** (TRANSPORT_FEE: the performer of the original visit) **and holders of `sale.finish_override`**; collector default = that performer.
  - Payment and FINISH follow the normal rules (P4-RULE-09 / 10 — incl. the payroll lock for a SERVICE line). It is not a visit (D-KPI-02 visit count unchanged); its SERVICE line is commissionable for the original barber in the period of the difference sale's own business date (D-COM-02/03). `Sale.kind` = `difference` (derived: no visit + a SERVICE / TRANSPORT_FEE line). The app rules "SERVICE line ⇒ visit" and "TRANSPORT_FEE line ⇒ HOME visit" (Part 4 SQL notes) get this one exception.

**P4-RULE-13 · Late entry.** 🔒 D-VIS-13, OPEN-01, REC-02 + owner B11 / B12.
- **Who:** `sale.late_entry` for the branch (Barber seed ✔ — 🔒 D-VIS-13); for oneself or a colleague (proxy rules apply — 🔒 D-VIS-04). To switch it off for one barber, give that person a **Barber role without `sale.late_entry`** (owner B12 — roles are grant-only, D-ROLE-04; no per-person flag, no DB change).
- **When:** any business date of the branch that is **not closed** (owner B11 — `DayLock.assertOpen`; no fixed look-back), never in the future, and **not inside a FINALIZED / PUBLISHED / PAID payroll period** (`PayrollLock` at START and at FINISH → 423 `payroll_finalized` — possible only after a day inside such a period was reopened, Part 7 P7-RULE-07 warning `payroll_finalized_period`; the barber's commission for that service is then a MANUAL payroll line, owner B9 — review R1-1). The Part 2 quote accepts that date (P2.PRC.06 v1.4).
- **What is entered:** `late_entry { reason, note?, started_at }` on START (reason preset 1–4 / 9; OTHER needs `note` — DB CHECK), `completed_at` on COMPLETE, `received_at` on each payment, `finished_at` on FINISH — **all four are required on a late-entry visit (400 `validation` when one is missing — a defaulted "now" would put the sale on today instead of the service day; review R1-12)** and ordered `started ≤ completed ≤ received ≤ finished ≤ now` (422 `late_entry_time`). `created_at` = recorded at (🔒 D-VIS-13 performed ≠ recorded). The sale's business date = the entered `finished_at` day, so revenue, cash and the receipt month land on the service day — the same day the lock checks.
- **Flags and reports:** `visits.is_late_entry` (+ sale flag `late_entry` in lists); monthly count per barber (Part 8 reports). Late-entry visits are excluded from the unpaid block (P4-RULE-02 #5) and from the in-progress busy time of availability (Part 2 P2-RULE-10 amendment).
- **Consequence noted:** during an internet outage the server's no-show timer still cancels a booking at +40 min (🔒 D-BKG-17); the late entry is then a walk-in (a CANCELLED booking never restarts — 🔒 D-BKG-16) and the no-show stays in history, which never restricts the customer (🔒 D-CUS-09).
- A late-entry sale left OPEN blocks closing like any OPEN sale (owner E2 — Part 7).

**P4-RULE-14 · Refunds.** 🔒 D-PAY-05, D-VIS-08, D-COM-04 v5.1, F-P4-06 + owner B8 / B12. `POST /v1/refunds` (P4.RFD.02 — `sale.refund`, Admin seed — owner B12; `Idempotency-Key`; identifying fields `sale_id`, `kind`, `amount`):
- Sale FINISHED (409 `invalid_transition`); **refund branch = the sale branch** (owner B8 b — the caller's scope must cover it; cash leaves that branch's drawer). Reason required.
- **Kind 1 SALE_REFUND:** `items[]` with `sale_item_id`, `quantity` (products), `amount`; per line `amount ≤ line_total − Σ earlier refund_items` and quantity ≤ remaining (422 `refund_exceeds_remaining { sale_item_id, remaining_amount }`); total = Σ items. Product lines: **`back_to_stock`** (owner B8 a, default true) → `StockLedger.post(tx, actor_user_id, movements[])` **SALE_RETURN_IN** `+quantity` (`ref = refund_item_id`); `false` (damaged) → SALE_RETURN_IN **and** **MANUAL_ADJUST** `−quantity` with `adjustment_reason_id` = setting `stock.refund_damaged_reason_id`, note = the RF number, recorded by the refunder — no `stock.adjust` code and no `stock.adjusted` notification (`sale.refunded` already reaches the admins) — Part 6 P6-RULE-07 / 11, contract 4. Commission: Part 5 reads `refund_items` (before the sale's period is finalized = smaller base; after = REVERSAL line at the original % in the run whose period contains the refund date — 🔒 D-COM-04 v5.1, P5-RULE-02; no payroll lock needed here).
- **Kind 2 OVERPAYMENT_RETURN** — no items, no revenue / commission effect (F-P4-06). Two forms (🔒 D-PAY-05): **(a) the automatic change** of P4-RULE-10 #15 — amount = `paid − total`, written by FINISH, **no code needed**; **(b) a manual return** through P4.RFD.02 — money the customer sent that was **never recorded as a payment** of the sale (e.g. a duplicate KBZPay transfer): needs **`sale.refund`**, `amount`, `reason` **and `external_reference`** (always required for a manual kind-2 return, whatever the method — 422 `reference_required`: the reference of the return transfer when it goes back through a reference method, otherwise the reference of the duplicate transfer being returned, so the money can be traced in the KBZPay statement).
- **Caps** (🔒 D-PAY-05 — coordinator decision at the reconcile 02/Oct; **replaces the review ruling R1-20**): **Kind 1** — Σ kind-1 refunds of the sale (this one included) ≤ the **sale total** (`sales.total_amount`); at line level each line's refunded amount ≤ its net (`line_total_amount` — the per-line cap above) → 422 `refund_exceeds_remaining { sale_item_id, remaining_amount }` (line), `{ sale_item_id: null, remaining_amount }` (sale level; `remaining_amount` = total − Σ earlier kind-1 refunds). **Kind 2** — the automatic change is by definition `paid − total` and is not tested; **each manual return ≤ the larger of the sale total and Σ non-voided non-cash payments of the sale** (a duplicate or stray transfer is about one sale's worth; a cash-paid sale can still return a stray transfer — 🔒 D-PAY-05) → 422 `refund_exceeds_remaining { sale_item_id: null, remaining_amount }` (`remaining_amount` = that limit). **Kind-2 returns do not consume the kind-1 cap** (they give back money that was never revenue), and kind-1 refunds do not lower the kind-2 limit.
- **Method** = any ACTIVE method (owner B8 c — a KBZPay sale may be refunded in cash); a reference method needs `external_reference` (422 `reference_required`; format as P4-RULE-09). Refund references are **not** checked for uniqueness — `refunds` has no such index and the RF number identifies the refund — so there is no `duplicate_reference` here.
- `refunded_at` = now, business date = today, `DayLock.assertOpen(branch, today)` first (422 `day_closed`), then the sale row `FOR UPDATE` and the checks; RF number from `receipt_counters` kind 2 → `<code>-RF-<YYYY>-<MMM>-<seq>` (🔒 D-PAY-06). `receipt.render` enqueued; realtime `refund.created`; notification `sale.refunded` to admins; audit `refund.create`. Customer statistics and reports count kind-1 refunds on the refund's business date (owner F6).

**P4-RULE-15 · Adjustments and the effective sale.** 🔒 D-VIS-06/08, F-P4-07, D-COM-03 + owner B9 / B10 + cross-part contract 8.
- `POST /v1/sales/{id}/adjustments` (P4.ADJ.01, `sale.adjust`, Admin seed) on a FINISHED sale; reason required; **amounts never change** (overcharge → refund, undercharge → difference sale).
- Types: **1 PAYMENT_METHOD** (`payment_id` + `new_payment_method_id`; to a reference method → `external_reference` required, validated like P4-RULE-09 — format and uniqueness on the **effective** method under the advisory lock — and **written on the payment row**; to a method **without** references → `payments.external_reference` is set **NULL**, so a stale reference never blocks a real payment (the DB-trigger audit row keeps the old value) — both allowed by `payments_finished_guard`, owner B10; review R1-7) · **2 PERFORMER** (`sale_item_id` of a SERVICE line + `new_employee_id` assigned to the branch on the sale date) · **3 COLLECTED_BY** (`payment_id` + `new_employee_id`, owner B3 list) · **9 OTHER** (note only).
- **Locks** (owner B9): types 1–3 → `DayLock.assertOpen(branch, sale business date)` (closed → 422 `day_closed`, admin reopens); type 2 → then `PayrollLock.assertNotFinalized(tx, { employee_ids: [old performer, new performer], dates: [sale business date] })` → 423 `payroll_finalized` (fix with a manual payroll line — Part 5). Type 9 → no lock. Order: day lock → payroll lock → sale row `FOR UPDATE` → checks (P4-RULE-10).
- **Natural-key replay** (no `client_request_id` on `sale_adjustments`): if the target's **effective** value already equals the requested one → 200, no new row. Type 9 (double-submit guard — review R1-28): when the sale's latest type-9 row was written by the caller with the same `reason` text → 200, no new row.
- **`EffectiveSale`** (owned here, used by Part 5 commission, Part 7 closing, Part 8 reports): loads a sale (or a filtered set) and applies the ledger — per payment the latest PAYMENT_METHOD and COLLECTED_BY rows (by `adjusted_at`), per SERVICE line the latest PERFORMER row. Responses show `effective_*` next to the stored values; KBZPay verification and closing totals use the **effective** method.

**P4-RULE-16 · The two in-place corrections after FINISH.** 🔒 D-VIS-08 (exception approved — owner B10), D-PAY-02, D-CUS-02/03.
- **Customer** (P4.SAL.12): attach / replace / detach (`phone: null`) the customer of a FINISHED sale with a reason — `sale.adjust`, or the performer / finisher **attaching** a customer to a sale that has none on the sale's business date (the "customer gave the phone after paying" case — D-VIS-02 phone capture). Phone → P3-RULE-01. A sale that used a **once-per-customer code** (review R1-13): replacing the customer moves the use row (`discount_code_customer_uses.customer_id`; the unique `(discount_code_id, customer_id)` refuses a customer who already used the code → **422 `once_per_customer`**); **detaching is refused → 422 `customer_required_for_discount`** (the use row's `customer_id` is NOT NULL and the code needs a customer). Audit `sale.customer_set` (before / after + reason). No day lock (no money moves).
- **KBZPay reference** (P4.PAY.07, `payment.verify` — the person reconciling at closing): new reference validated (format + effective-method uniqueness as P4-RULE-09), `verified_at` / `verified_by` cleared (verify again — allowed after close, owner E3); audit `payment.reference_correct` (old / new + reason). **No day lock, on purpose** (review R1-24): a reference correction is allowed after the day is closed (owner B10 — neither the amount nor the closing snapshot changes) and clearing the tick only asks for a new verification, which is itself allowed after close (owner E3); an **unverify alone** has no business reason on a closed day, so P4.PAY.06 stays tied to an open day (P4-RULE-17).
- Nothing else on a FINISHED sale changes in place (DB guard — P4-RULE-01).

**P4-RULE-17 · KBZPay verification.** 🔒 D-PAY-02 v5.1 (REC-11, C-1) + owner E3 + contract 7. `POST /v1/payments/{id}/verification` (P4.PAY.05) and `DELETE …/verification` (P4.PAY.06), `payment.verify` for the payment's branch. Only non-voided payments of FINISHED sales whose **effective** method `requires_verification` (422 `verification_not_required`). Verify sets `verified_at` / `verified_by_user_id` — **allowed after the day is closed** (owner E3: the closing snapshot doesn't change; no day lock). Unverify only while the sale's branch-day is open (422 `day_closed`). Verification never blocks FINISH. Realtime `payment.verified { verified }`. Part 7's closing screen lists and counts these (AD-CLS-04).

**P4-RULE-18 · Receipts — numbering, rendering, reprint, printing.** 🔒 D-PAY-06/07, OPEN-20/32, REC-37 ✅ + owner H + ADR-003 / ADR-013 / ADR-014.
- Number at FINISH / refund only (P4-RULE-10 #13, P4-RULE-14); gapless per branch + kind + MMT month; the month restarts at 00001; the branch prefix = `branches.code` (changing a code later changes only future prefixes — counters are keyed by `branch_id`).
- **Rendering** (ADR-013 `DocumentRenderer`): job `receipt.render { entity_type: 'sales' | 'refunds', entity_id }` renders the English receipt (AD-RCPT-01 — `*_en` snapshots with `*_mm` fallback, masked phone `09•••••123`) to **PDF** and a **1-bit PNG** at the branch's `receipt.printer_width_mm` (58 → 384 px, 80 → 576 px) and stores both as attachments (kind 1, entity `sales` / `refunds`, `uploaded_by` = the finisher / refunder). The stored files freeze the branch header, opening hours and thank-you text, so **a reprint is identical** (🔒 D-PAY-06). `GET …/receipt?format=pdf|png` returns the stored file, or renders on the fly (and stores) when the job has not run yet; another width renders on the fly. `format=json` returns the receipt data (`ReceiptView`).
- **Access:** any staff in read scope (operational — 🔒 D-PAY-07 "an Android colleague opens the sale and prints it", AD-POS-13): P4.RCP.03 finds a receipt by exact number; P4.RCP.04 lists the branch's receipts of a day (≤ 7 days back) **without amounts** (AD-PERM-05 — the amounts show only on the opened receipt).

A printer error never touches the sale. `receipt.auto_print` = OFF (REC-37 ✅ owner H).
- **Search group** (P1.SYS.04, API-DATA-09): `sales: [{ id, receipt_number, finished_at, branch_id, total_amount }]` for `sale.view⁺` holders (exact or prefix receipt number); barber-like callers don't get it (🔒 D-SRC-01) and use P4.RCP.03.

**P4-RULE-19 · Payment methods master.** 🔒 D-PAY-01/02, D-DB-04, OPEN-24, ADR-012 (company master).

**P4-RULE-20 · Permissions — levels, reads, data minimisation.** 🔒 D-ROLE-03/07, ADR-011, ADR-012, AD-PERM-05 + owner B2 / B3 / B7 / B12 + C1.
- **Levels:** visits, sales, sale lines, payments, refunds, adjustments, discount requests = **branch data** (the visit / sale branch) · discount codes, payment methods = **company master** (write = company scope; branch scope = read-only) · customers = **shared** (Part 3) · nothing in this part is `private`, except that the **commission estimate** is never shown to managers (commission data is private — owner C1).
- **Operational reads (any staff in read scope, no code):** P4.VIS.02 (own Today), P4.DSC.02 (checkout codes), P4.PMT.01 (active methods), P4.RCP.01..04 (receipts), plus Part 2 quote / Part 3 phone lookup. **Self reads:** own visits / sales (P4-RULE-03), own discount requests, P4.REQ.01. **Management reads:** `visit.view⁺`, `sale.view⁺` (sales, refunds), `payment.view⁺`, `discount.view⁺`, `payment_method.view⁺`.
- **Commission estimate** (🔒 D-COM-04, D-DSH-03 + owner C12): `Sale.commission_estimate` = `Commission.estimate(employee_id = performer, business_date = the sale's business date (an OPEN sale: today — a late-entry visit: its visit date), base_amount = this sale's net SERVICE lines of the performer, branch_id = the sale branch, before = the sale's finished_at (an OPEN sale: none))` (Part 5 P5-RULE-02; review R1-18 / R1-29): the window is the **payroll period containing that date** (MONTHLY = the calendar month — 🔒 D-PAYR-01); the assignment is the one **active on that date** that covers the sale branch (a branch-scope plan counts only that branch's sales); the period-to-date base = the performer's commissionable base from sales finished **before this sale's `finished_at`** in that period (an OPEN sale: everything finished so far) — so the estimate of a finished sale never drifts and the estimates of a period add up to the payroll figure (marginal tiers: 2,240,000 + a 30,000 cut → 5,500). It is returned **only when the caller is that performer and their effective own-earnings flag is ON**; `null` for everyone else (managers included). Never stored.
- Barbers never see colleagues' figures in lists (AD-PERM-05): P4.RCP.04 has no amounts; P4.VIS.01 / P4.SAL.01 need management codes.

**P4-RULE-21 · Notifications, realtime, audit.** 🔒 D-NTF-01..03, D-AUD-01/02, API-RT-02/03, API-AUD-01 + owner F12. Types and events in §10. Events are emitted after commit; `receipt.render` is enqueued inside the transaction. **P4-RULE-22 · Idempotency and concurrency.** 🔒 D-VIS-10, API-IDEM-01/02/05, AD-NET-01/02 + contract 15.
- **`Idempotency-Key` (stored `client_request_id`):** START (visit + sale), product-only sale, difference sale, payment add, refund. Replay → 200 + `Idempotent-Replayed: true`; in progress → 409 `idempotency_in_progress`; different identifying fields → 422 `idempotency_mismatch`; missing → 400 `idempotency_key_required`.

- **"Was it saved?"** — P4.REQ.01 looks up the caller's `client_request_id` in visits, sales, payments, refunds and **stock movements** (Part 6 usage / manual adjustment — `stock_movements.client_request_id`, DB Part 6 v1.2, owner G c) (AD-NET-02).
- Every mutation of an OPEN sale first takes the advisory locks its rule names (day lock, then payroll lock) and then locks the sale row — before any check (P4-RULE-10 lock order, READ COMMITTED); POS writes need no `expected_updated_at` (the state machine protects them — API-IDEM-04); FINISH carries `expected_total_amount` instead.
