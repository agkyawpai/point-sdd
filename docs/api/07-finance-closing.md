## 1. Rules specific to this part

**P7-RULE-01 · Data levels, reads and who may act.** 🔒 D-ROLE-03/07, D-DSH-02, ADR-011, ADR-012 + cross-part contract 1 (ADR-012 amendment) + owner E4 / E6 / C1.
- **Branch data** (the target branch must be covered — API-PERM-07): daily closings (`branch_id`), cash outs (the drawer's branch), cash returns (the **returning** drawer's branch), expenses / manual incomes **with** a `branch_id`, the branch P&L.
- **Company-wide money rows** (contract 1): expenses and manual incomes with `branch_id` NULL and the **company P&L** need the code through a **company-scope** assignment to **read and write**; a branch-scope grant reaches nothing — lists leave them out (no `company_wide` rows, filter ignored), a single read answers 404, a write 403 `company_scope_required`. This differs from company master data, which branch-scope holders may read (API-PERM-03 v1.4). Decorator: the optional branch path declares its empty value private — `@Can('expense.create', { branch: 'body.branch_id?', empty: 'private' })` (Part 0 amendment — §15).
- **Private salary rows** (contract 1, owner C1 / E6): expenses in the system **SALARY** category (`system_code` 1 — the payroll rows of source 3 and any manual salary entry) are listed and readable only by company-scope holders of **`payroll.view`** (private, Part 5); everyone else gets them excluded from P7.EXP.01 (404 on P7.EXP.02) and sees salary in the P&L as **one total line** (P7-RULE-17).
- **Staff advance taker — private (owner C1 + D-FIN-06, fix-up 02/Oct):** a cash out of accounting type **2 EMPLOYEE_BALANCE** stays a branch-data row — its `amount`, `reason`, `accounting_type`, dates, state and recorder are returned to every `cashout.view⁺` / `closing.view⁺` reader (the cash count needs the amount — 🔒 D-FIN-06), but **who took the advance** is pay data (C1 — "payroll / salary / advance = Admin only; a Manager can't see it even with branch scope"). `employee`, `receivable_id` and the `note` (= the receivable's reason — P5-RULE-11, private in Part 5) are returned only to company-scope holders of **`payroll.view` or `receivable.issue`** (both private, Admin seed — reconcile 02/Oct: the code that records, edits and cancels the advance must also show whose it is) and to that employee on a self read (own advance — like P5.RCV.08); everyone else gets `employee: null`, `receivable_id: null`, `note: null` and **`employee_hidden: true`** (UI label "Staff advance" — AD-FIN-01). One serializer for every `CashOut` / `CashOutListItem` response: P7.CSO.01 / 03 / 04 / 05 / 06, P7.CRT.02 / 03, the closing's `movements.cash_outs` (P7.CLS.02..05 — P7-RULE-04) and the exports of those lists (Part 8 P8-RULE-08); Part 8 report ⑤ and the audit viewer apply the same rule (P8-RULE-06 / 15). Without either code at company scope: the P7.CSO.01 `employee_id` filter → 403 `forbidden` (`context.required: "payroll.view"`), `q` never matches a hidden note. **Edit and cancel of an EMPLOYEE_BALANCE cash out (P7.CSO.05 / 06) need `receivable.issue`** as well (Part 5 — level **private**: a company-scope assignment; P7-RULE-10 — review R2-3) — whoever may edit or cancel the advance therefore always sees its taker and note. Totals (`cash_outs_amount`, per-type sums) are unchanged.

**P7-RULE-02 · `DayLock` — the one gate for a branch-day (owned here).** 🔒 D-FIN-06 ("closed = immutable"), D-VIS-13 + owner B9 / E2 / E3 + cross-part contract 2.
- `DayLock.assertOpen(tx, branch_id, business_date)` = `pg_advisory_xact_lock_shared(dayKey)` with `dayKey = hashtextextended('day:' || branch_id || ':' || business_date, 0)`, then `SELECT status FROM daily_closings WHERE (branch_id, business_date) = …`; **2 CLOSED → 422 `day_closed`** with `context { branch_id, business_date, closed_at, closed_by, correction_path: "reopen" }`; no row or 1 OPEN → passes. The shared lock is held to commit, so a close can't slip in between the check and the write.
- `DayLock.lockExclusive(tx, branch_id, business_date)` = `pg_advisory_xact_lock(dayKey)` — the **first statement** of the transaction of **close** (P7.CLS.04) and **reopen** (P7.CLS.05). A close therefore waits for in-flight writers of that day and every later writer sees CLOSED.
- **Isolation and lock order (independent review R2-1 / R1-8):** every write of this part — close and reopen included — runs **READ COMMITTED** with its locks taken first and **every check after them**. `REPEATABLE READ READ ONLY` is used only by previews and reports (P7.CLS.02, the P&L, Part 8 — ADR-015), never together with a lock or a write, so no serialization-failure (40001) retry path exists. Reason: a REPEATABLE READ snapshot is fixed by the transaction's first statement — the advisory-lock call itself, i.e. **before** the wait — so a FINISH, payment or cash out committing while the closer waits would be invisible to the open-sales check and to the figures, and would land on a CLOSED day outside its snapshot. One lock order in every part: **day lock (advisory) first → payroll lock (advisory, Part 5 `PayrollLock`) → sale → visit → booking → payments → receipt counter → cash-out / cash-return / expense / income / closing rows → stock level rows last**. A writer that must read its row to learn the branch-day (cash-out edit / cancel, cash-return cancel, cash-income edit / reject / delete) reads it **without a lock**, takes the day lock(s) — two branch-days in ascending (`branch_id`, `business_date`) order — then locks the row `FOR UPDATE` and re-reads it; a branch or date that changed in between → 409 `conflict` (the client retries).
- **Callers:** Part 4 (**every** START incl. late entry — owner B9, visit-less sale create (product-only P4.SAL.03 **and difference-sale create P4.SAL.13**), payment add / void / collector change, FINISH, adjustments types 1–3 PAYMENT_METHOD / PERFORMER / COLLECTED_BY, refunds on today's date, KBZPay **unverify** P4.PAY.06 — P4-RULE-02 / 09 / 10 / 12 / 14 / 15 / 17; the day lock is the **first** lock of each of them, before the sale row) and Part 7: cash out create / edit / cancel (the cash out's date **and** a new date), cash return create / cancel (the returning branch and the return date), **cash** manual income create / edit / reject / delete (branch + `income_date` — owner E7).
- **Late entry and payroll (owner B9 — shared rule, reviews R1-1 / R1-9):** a late-entry START and the FINISH of any sale with SERVICE lines also call Part 5 **`PayrollLock.assertNotFinalized`** right after the day lock — a business date inside a FINALIZED / PUBLISHED / PAID payroll period → 423 `payroll_finalized` (the correction is a manual payroll line). The two gates are independent: an open (or reopened) day is not thereby open for commissionable work (P7-RULE-07), and a late-entry visit is gated only by these two — it neither blocks nor is blocked by other visits (Part 4).
- **Exempt:** KBZPay **verify** (owner E3 — the closing snapshot never changes; **unverify** is gated — Part 4 P4-RULE-17), the two in-place corrections after FINISH — KBZPay reference (P4.PAY.07) and customer (P4.SAL.12) — and INCOMPLETE (P4.VIS.06) (no money moves — Part 4 P4-RULE-11 / 16), adjustment type 9 OTHER, expenses (never drawer money — D-FIN-07, AD-FIN-04), non-cash and company-wide manual incomes, approval of a cash income (P&L only), the month-end job (P7-RULE-12 — it moves no drawer money).
- A future `business_date` is refused before any lock: 422 `date_in_future`.

**P7-RULE-03 · Which days need closing — `DailyClosings.openDays`.** 🔒 D-FIN-06 + owner C7 (Part 5) / E2 + AD-CLS-07, AD-DSH-04.
- A branch-date **needs closing** when it lies between the branch's **first active date** and today (MMT) and **either** (a) the branch was **open** that day **or** (b) it has money activity (a FINISHED sale, a refund, a cash out / return, a cash manual income — a sale on a closure day still needs a closing) or already has a `daily_closings` row. **First active date** = the earliest business date with any of that activity or a `daily_closings` row at the branch — days before go-live never count.
- **Open** = no non-archived `branch_closures` range covers the date **and** the `branch_opening_hours` row of its ISO weekday does not say closed: no row for that weekday = open (no rows at all = open every day); a row counts **only for dates on or after its `updated_at` date (MMT)** — `is_closed = false` → open, `is_closed = true` → not open; **for an earlier date the row says nothing**, and that date needs closing only under (b) (independent review R3-3). The table keeps one row per weekday and no history, so an edit of the weekly hours must never re-decide past days: switching Monday from closed to open would otherwise make every past Monday block P7.CLS.04 (`previous_day_open`) and payroll finalize (`closings_open`), and the reverse would silently drop unclosed days. Consequence (a small narrowing of owner C7): a **zero-activity** day before the latest edit of its weekday's row is not required to be closed — nothing moved, and the next closing's opening check (P7-RULE-04) still compares the drawer with the last CLOSED count. Closures are stable for the past: Part 8 P8.WEB.08 archives a closure only while its **`start_date` ≥ today** (a closure created today by mistake can still be removed — no past day changes); a closure with `start_date` < today is ended through P8.WEB.07 (422 `closure_started`) — reconcile 02/Oct.
- `DailyClosings.openDays(branch_ids?, from, to)` = the dates that need closing and have **no CLOSED row** → Part 5 payroll finalize (409 `closings_open` — owner C7; Part 5 note 2 is this definition), P7.CLS.04 (409 `previous_day_open`), P7.CLS.01 (`needs_closing`), the Part 8 "days not closed" card (AD-DSH-04).

**P7-RULE-04 · The closing figures (preview and snapshot).** 🔒 D-FIN-06 (REC-17 formula — owner **E8**), D-PAY-02 v5.1, F-P7-06 + owner E1 / E3 / E7 / C3 + contract 8. One function `DailyClosings.components(branch_id, business_date)` computes them, with payment methods taken from Part 4 **`EffectiveSale`** (the latest PAYMENT_METHOD adjustment wins — contract 8). **Where it runs (independent review R2-1):** the preview (P7.CLS.02) and report ⑤ call it in one `REPEATABLE READ READ ONLY` transaction (ADR-015 — one consistent picture, nothing written); save (P7-RULE-05) and close (P7-RULE-06) call it **inside their READ COMMITTED write transaction, after their locks** — at close the exclusive day lock is already held, so no drawer writer of that branch-day can commit between the lock and the figures:

| Component | Source (branch B, business date D) |
| --- | --- |
| `opening_cash_amount` | the closer's value; **prefill** = setting `closing.opening_float_amount` (branch override → company default **0** — OPEN-05 A) |
| `cash_sales_amount` | Σ non-voided `payments` of **FINISHED** sales of B with `sales.business_date = D` whose **effective** method `is_cash` |
| `cash_refunds_amount` | Σ `refunds` of B with `business_date = D` paid with an `is_cash` method — kind 1 refunds and kind 2 overpayment returns: the automatic over-transfer change (owner B5) and manual returns (Part 4 P4-RULE-14) |
| `cash_outs_amount` | Σ `cash_outs` of B, `business_date = D`, **not cancelled** (DB v1.1) |
| `cash_returns_amount` | Σ `cash_returns` whose **returning** branch is B, `business_date = D`, not cancelled |
| `cash_manual_incomes_amount` | Σ `manual_incomes` of B, `income_date = D`, `is_cash` method, status **1 PENDING or 2 APPROVED**, not deleted — owner **E7** (the money is in the drawer once recorded; the P&L counts it only when approved) |
| `expected_cash_amount` | opening + sales − refunds − outs + returns + manual cash income (**DB CHECK** `daily_closings_expected_chk` — owner E8) |
| `noncash_expected_amount` · `noncash_verified_amount` · `unverified_payment_count` | non-voided payments of FINISHED sales of B with business date D whose effective method is **not** `is_cash` (Σ) · of those whose method `requires_verification`, Σ verified · count unverified (D-PAY-02 v5.1) |

- **Not in the formula** (by decision): advance / loan cash repayments (owner **C3** — they go to the owner / admin, outside the drawer, Part 5 P5.RCV.05), expenses (paid by bank / owner / other — AD-FIN-04), purchases (D1), salaries (C4 — a drawer payout is a Cash Out).
- **Opening check** (OPEN-05 A): `previous_closing` = the latest **CLOSED** closing of B before D (date + `counted_cash_amount`); opening ≠ that counted → `opening_difference_reason` required at close. With the takings handover recorded as a Cash Out before counting (owner E1) the two normally match.
- **Difference** = counted − expected (generated column); `difference_state` = `balanced` (0) · `within_tolerance` (|d| ≤ `closing.cash_difference_tolerance_amount`, company, default **0**) · `beyond_tolerance`.
- **Preview vs snapshot:** a date with no row or an OPEN row is shown **live** (`source: "live"`); a CLOSED row shows its **stored snapshot** (`source: "snapshot"` — F-P7-06) plus two live counters for E3: `verified_after_close_count` (verified at or after `closed_at`) and `unverified_now_count`.
- **Movements** (`movements.cash_outs` / `cash_returns` / `cash_incomes` / `cash_refunds`) list each line with its amount and reason (AD-CLS-01 #2); an EMPLOYEE_BALANCE cash out shows "Staff advance" without the employee unless the caller holds company-scope `payroll.view` **or** `receivable.issue` (P7-RULE-01 — owner C1 + D-FIN-06).
- **Checks** returned with the figures: `open_sales[]` (the P7-RULE-06 #4 set — incl. difference sales and, for a past date, OPEN sales holding earlier payments) and `previous_open_dates[]` (**blockers** — P7-RULE-06), `pending_discount_requests` (warning — AD-CLS-05), `pending_cash_incomes` (info — already counted, awaiting approval). The client adds the AD-CLS-05 reminder (paper-notebook cash outs, the takings handover — E1).

**P7-RULE-05 · Saving the count (draft).** 🔒 D-FIN-06 + AD-WIZ-01. `PUT /v1/daily-closings/{branch_id}/{business_date}` (P7.CLS.03, `closing.close`): READ COMMITTED, no day lock (a draft runs no business check and changes no drawer figure); date ≤ today (422 `date_in_future`); `INSERT … ON CONFLICT (branch_id, business_date) DO NOTHING` + `SELECT … FOR UPDATE` on the closing row; CLOSED → 423 `locked` (`correction_path: "reopen"`); writes `opening_cash_amount`, `counted_cash_amount`, the three reasons, `notes` **and** the recomputed components + `expected_cash_amount` (so the DB CHECK always holds); **`previous_closing_counted_amount` stays NULL until close** (a draft with a different opening and no reason yet must save — DB `daily_closings_opening_chk`); `expected_updated_at` mismatch → 409 `conflict`. No business check runs on a draft. Realtime `closing.updated`; audit `closing.save`.

**P7-RULE-06 · Close.** 🔒 D-FIN-06, D-PAY-02 v5.1, D-VIS-07 + owner **E2** / E3 / E8 + contracts 2 / 15. `POST …/close` (P7.CLS.04, `closing.close`) — **idempotent by state** (no `Idempotency-Key`; already CLOSED → **200** current state). One **READ COMMITTED** transaction — the locks first, every check after them (P7-RULE-02; independent review R2-1):
1. `business_date` ≤ today (MMT) else 422 `date_in_future` (no lock yet).
2. **First statement of the transaction:** `DayLock.lockExclusive(branch, date)` — it waits for the in-flight writers of that branch-day, and everything they committed is visible to every statement that follows. Then upsert + `FOR UPDATE` the closing row (P7-RULE-05); CLOSED → 200.
3. **Earlier days** — `DailyClosings.openDays(branch, first active date, date − 1)` non-empty → 409 **`previous_day_open { dates[] }`** (≤ 31 oldest) — the opening check needs yesterday's count.
4. **Open sales** (owner **E2** — "a sale that could still FINISH on this day"): sales of the branch in status 1 OPEN whose money belongs or could still belong to this business date — **date = today:** every OPEN sale of the branch: service, product-only **and difference sales** (Part 4 P4-RULE-12 — a difference sale is created when the customer pays the difference and is a normal OPEN visit-less sale; it is finished or cancelled before the day closes like any other — review R1-4); **date < today:** (i) OPEN **late-entry** visit sales whose visit business date ≤ the date (only a late-entry FINISH may carry a past `finished_at` — Part 4 P4-RULE-10 / 13) **and** (ii) any OPEN sale of the branch holding a **non-voided payment whose `received_at` (MMT date) ≤ the date** (independent review R2-8 — that money already sits in that day's drawer / KBZPay; without the guard it would be counted on the later finish date with nobody noticing) → 409 **`open_sales_exist { sales: [{ sale_id, visit_id, performer, started_at, is_late_entry, total_amount, paid_amount }] }`** — finish them, void the payment, or mark them Incomplete / cancel them (Part 4 P4.VIS.06 / P4.SAL.11 / P4.PAY.03). A sale of case (ii) finished today still counts its cash on the **finish** date (`cash_sales_amount` keys on `sales.business_date`): the earlier day's count then shows that amount as a difference, entered with `cash_difference_reason`.
5. Compute the components (P7-RULE-04) — now, under the exclusive lock. The body repeats what the closer saw — `expected_cash_amount` and `unverified_payment_count`; a difference → 409 **`closing_changed`** with the new figures in `context` (a payment or cash out landed meanwhile — AD-CONF-01).
6. **Reasons** (400 `reason_required`, `errors[].field`): `counted_cash_amount` required (400 `validation`); counted ≠ expected → `cash_difference_reason`; `unverified_payment_count > 0` → `unverified_reason` (D-PAY-02 — e.g. "KBZPay app not opening — owner checks in the morning", E3); opening ≠ previous counted → `opening_difference_reason`.
7. Write the snapshot (components, expected, `previous_closing_counted_amount`, noncash figures), `status` 2, `closed_at` = now, `closed_by_user_id` = caller (DB CHECK `daily_closings_status_fields_chk`).
8. After commit: realtime `closing.closed`; |difference| > tolerance → notification **`closing.difference`** (+ `warnings[] beyond_tolerance { difference_amount, tolerance_amount }`); audit `closing.close`. The person responsible for a shortfall is only recorded — no payroll deduction (🔒 D-FIN-06 (3), D-PAYR-03 manual).
From commit on, `DayLock.assertOpen` refuses every drawer write of that branch-day (422 `day_closed`) — Part 4 sales and payments, cash outs / returns, cash incomes.

**P7-RULE-07 · Reopen and correct.** 🔒 D-FIN-06 ("admin reopen / adjust + audit") + AD-CLS-06. `POST …/reopen` (P7.CLS.05, **`closing.reopen`** — Admin seed) `{ reason }` — READ COMMITTED; **first statement** `DayLock.lockExclusive`, then the closing row `FOR UPDATE`; **not CLOSED → 409 `invalid_transition { status }`**. Reopen is the **one exception** to "a repeat answers 200" (P7-RULE-18 — independent review R2-20): a second tap finds the row OPEN and gets 409 — `reopen_count` and `last_reopen_reason` must not be written twice, and an OPEN row can't tell whose reopen it was; the client treats that 409 after its own reopen as "already open" and refetches. Then `status` 1, `closed_at` / `closed_by_user_id` / `previous_closing_counted_amount` cleared, `reopen_count + 1`, `last_reopened_at` / `_by` / `_reason` (DB CHECK `daily_closings_reopen_chk`); counted, reasons and notes stay as the draft. **"Adjust" = reopen → correct the source records (cash out, cash return, refund, payment-method adjustment, a late entry …) → close again** — the snapshot is never edited in place (F-P7-06). **Finalized payroll (shared rule — reviews R1-1 / R1-9):** a day inside a FINALIZED / PUBLISHED / PAID payroll period **may** be reopened (cash corrections can still be needed); the response then carries `warnings[] payroll_finalized_period { run_id, period: { start, end } }` (a read-only lookup of that run through Part 5 `PayrollLock.finalizedRunFor(date)` — no payroll lock is taken and nothing is refused here). On such a day the drawer writes work again, but a late-entry START, the FINISH of a sale with SERVICE lines and a PERFORMER adjustment are still refused by Part 4 with 423 `payroll_finalized` — the commission correction is a manual payroll line (owner B9). Later CLOSED days of the branch keep their snapshots; the response carries `warnings[] later_closings { dates[] }` so the admin can reopen them too if their opening check changed. Realtime `closing.reopened`; notification **`closing.reopened`**; audit `closing.reopen` (reason).

**P7-RULE-08 · KBZPay verification at closing.** 🔒 D-PAY-02 v5.1 (REC-11, C-1) + owner **E3** + contract 7. **P7-RULE-10 · Correcting a cash out (owner E5).** 🔒 D-FIN-07, D-DAT-05, D-AUD-02 + G (d).

the editor holds `receivable.issue`, so the taker and the note are never hidden from them (P7-RULE-01). **MUST_RETURN:** not converted (409 `cash_out_converted { expense_id }`), `amount` ≥ Σ active returns (422 `amount_below_returned { returned_amount }`). **EXPENSE** (independent review R2-14): an APPROVED expense is never edited in place (P7-RULE-15) — when the amount, the reason's category, the business date or the note changes, the linked source-2 expense is **soft-deleted** (`deleted_by` = the editor, `deletion_reason` = "Cash out edited — <edit_reason>") and a **new** APPROVED source-2 row is inserted for the same `cash_out_id` (`requested_by` = `approved_by` = the editor) in the same transaction — the partial unique index `expenses_one_per_cash_out … WHERE deleted_at IS NULL` allows exactly that; `CashOut.expense_id` = the live row. **`edit_reason`** (required — 400 `reason_required`) has no column: it is stored in the interceptor audit row `cash_out.update` (`audit_events.reason`); the DB trigger rows keep the before / after of `cash_outs` and of both `expenses` rows (D-AUD-02 — a trigger row carries no reason).
- **Cancel** — `POST /v1/cash-outs/{id}/cancel` (P7.CSO.06, `cashout.delete`) `{ reason }`: locks as for edit (`DayLock.assertOpen` on the stored date, then the row `FOR UPDATE`); already cancelled → 200; active returns → 409 `cash_out_has_returns { count }` (cancel them first); converted → 409 `cash_out_converted { expense_id }`; **EMPLOYEE_BALANCE** → the caller also needs **`receivable.issue`** (403 `forbidden`, `context.required` — review R2-3: creating the advance needed it, Part 5 P5.RCV.06 cancel needs it, and a Manager holding only `cashout.delete` cannot even see whose advance it is — owner C1), then **`Receivables.cancelForCashOut(cash_out_id, actor, reason)`** (Part 5 P5-RULE-11 — receivable → 0 CANCELLED; 409 `receivable_in_use` once repaid or pending in a run); EXPENSE → the linked expense is soft-deleted (`deleted_by` = caller, `deletion_reason` = "Cash out cancelled — <reason>"); writes `cancelled_at` / `cancelled_by_user_id` / `cancel_reason` (all-or-none — DB v1.1). `actions.can_edit` / `can_cancel` are `false` for a caller who lacks one of the needed codes. Cancelled rows leave expected cash, outstanding and the month-end job. Notification `cash_out.cancelled`; audit `cash_out.cancel`.

**P7-RULE-11 · Cash return and its reversal.** 🔒 D-FIN-09 + OPEN-25 + G (d).
- `POST /v1/cash-outs/{id}/returns` (P7.CRT.02, `cashout.return` for the **returning** branch — `body.branch_id`, default the cash out's) + **`Idempotency-Key`** `{ branch_id?, amount, returned_at?, note? }`: `returned_at` ≤ now (422 `date_in_future`), `business_date` = its MMT date; `DayLock.assertOpen(returning branch, date)` — the first lock; then the cash out row `FOR UPDATE`; 4 MUST_RETURN only (422 `not_must_return`); cancelled → 409 `invalid_transition`; `amount` ≤ outstanding (amount − Σ active returns) → else 422 `return_exceeds_outstanding { outstanding_amount }`; partial returns allowed.
- **Response and scope (independent review R2-25):** the permission is checked on the **returning** branch only, so the cash can come back into another drawer. The full `CashOut` is returned only when the caller also holds `cashout.view⁺` for the **cash out's** branch (or is its recorder / taker); otherwise P7.CRT.02 / 03 answer with **`CashOutReduced { id, branch_id, accounting_type, state, outstanding_amount, reduced: true, returns: CashReturn[] }`** — `returns` = the returns of branches in the caller's scope; no amount, reason, note, taker or recorder of the original. (Such a caller gets the cash out id from the taker's own list — `mine=true` — or from an Admin; P7.CSO.02 lists only cash outs of branches in scope.)
- **Already converted** (P7-RULE-12): the same transaction inserts the **reversal** `expenses` row — source 6 CASH_RETURN_REVERSAL, **amount −x**, category = the conversion expense's, **branch = the conversion expense's branch** (the cash out's — so the two months net to 0 in that branch's P&L, D-FIN-09) even when the cash comes back to another drawer, `expense_date` = the return's business date, `original_expense_id`, `cash_return_id`, APPROVED by the receiver.
- Σ active returns = amount → `settled_at` = `returned_at`.
- Identifying fields `cash_out_id`, `amount`; replay 200. After commit: realtime `cash_return.created` + `cash_out.updated`; audit `cash_return.create`.
- **Cancel** — `POST /v1/cash-returns/{id}/cancel` (P7.CRT.03, `cashout.delete` for the return's branch) `{ reason }`: the return is read without a lock; `DayLock.assertOpen(return branch, return date)`; then the cash out row and the return row `FOR UPDATE`; already cancelled → 200. **The cash out is converted and this return has no reversal row** (it was dated on or before the converted month's end, so the conversion expense was computed with it) → **409 `cash_out_converted { expense_id }`** (independent review R2-5): cancelling it would raise the outstanding amount while the source-5 expense stays lower, and the months would no longer net to 0 (🔒 D-FIN-09 / OPEN-25); a return that was recorded there by mistake is put right with a new MUST_RETURN cash out for that amount. Otherwise: a return **with** a reversal row → that reversal expense is soft-deleted (`deletion_reason` = "Cash return cancelled — <reason>"); `settled_at` cleared when the cash out is outstanding again; writes the three cancel columns. Notification `cash_out.cancelled` (kind return); audit `cash_return.cancel`.

**P7-RULE-12 · Month-end conversion — job `closing.month_end_must_return`.** 🔒 D-FIN-09 ("not returned **until the month-end closing**") + OPEN-25 + ADR-002 (job named in the system design). Cron **daily at 01:00 MMT** (independent review R2-7 — a fixed run on the 1st would not wait for the month's last closing). Each run looks at every MUST_RETURN cash out that is not cancelled, not converted (`converted_expense_at IS NULL`), whose `business_date` lies in a month **M that has ended** (last day of M < today, MMT) and whose **outstanding at month end** (amount − Σ active returns with `business_date` ≤ the last day of M) is > 0 — and converts it **only when the month-end closing of its branch is done: `DailyClosings.openDays(the cash out's branch, first day of M, last day of M)` is empty** (every day of M that needs closing at that branch is CLOSED — P7-RULE-03). Otherwise the cash out is left alone and looked at again the next night; a return made on the 31st and entered the next morning (the day is still open) is therefore counted before anything is converted. Per cash out, one READ COMMITTED transaction: lock the cash out row `FOR UPDATE`; re-check (not cancelled, not converted, month still fully closed, outstanding at month end still > 0); INSERT `expenses` source 5 MUST_RETURN_AUTO (amount = that outstanding, category = the reason's expense category, branch = the cash out's, **`expense_date` = the last day of the cash out's own month M** — also when an older cash out is converted late; `cash_out_id`, APPROVED; **`requested_by` = `approved_by` = the cash out's recorder** — the DB needs a user and there is no system user; the audit row says `source = job`), set `converted_expense_at`; every active return dated **after** that month end gets its reversal row in the same transaction (P7-RULE-11). **"Processed" needs no table:** a converted cash out carries its source-5 expense (`expenses_one_per_cash_out`, `converted_expense_at`); an unconverted one is simply examined again every night — this also covers a MUST_RETURN cash out entered later with a date in an earlier month (possible only while that day is open, or after a reopen): once that month is fully closed again, the next run converts it. The job takes no day lock and moves no drawer money (P7-RULE-02). The obligation stays (D-FIN-09): the cash out shows `charged_to_expense` with its outstanding amount until returned. Idempotent (DB `expenses_one_per_cash_out`); 3 retries, dead letter → `job.failed` (Part 8). Notification **`cash_out.must_return_converted`** per cash out (admins + the taker when a user). The month's P&L shows the note (P7-RULE-17). The DB Part 7 DBML comment `finance.month_end_must_return_job` means **this job** — it is not a settings key (§13).

**P7-RULE-13 · Cash-out reasons and the seeds.** 🔒 D-FIN-08 + F-P7-07 + owner E1 / D1 / C4 + contract 6. **P7-RULE-14 · Expense and income categories.** 🔒 D-FIN-01/02, F-P7-01 + REC-15. One menu *Settings › Expense / income categories* = module **`finance_category`** (company master). **P7-RULE-15 · Expenses — one ledger, six sources.** 🔒 D-FIN-02/03/04/09, F-P7-04/05, REC-15/16 + owner **E4 / D3 / C1 / E6** + G (d).
- **Manual** (source 1 — P7.EXP.03, `expense.create`; branch row → the branch, `branch_id: null` → company-wide, company scope — P7-RULE-01) + **`Idempotency-Key`** (`client_request_id`, DB v1.1; identifying fields `branch_id`, `category_id`, `amount`, `expense_date`): `{ branch_id, category_id, amount > 0, expense_date ≤ today (422 date_in_future — no lower bound: a bill for last month is entered with last month's date), description_mm?, paid_via (1 BANK · 2 OWNER_PERSONAL · 3 OTHER — required; drawer cash is always a Cash Out — AD-FIN-04), attachment_ids? }`. An `expense_date` in an earlier month → `warnings[] previous_month_pnl { date }` (that month's P&L changes — the same warning as Part 6 purchases).
- **Approval (owner E4):** the entry is **APPROVED at once** (`approved_by` = the creator) only when the creator holds **`expense.approve` through a company-scope assignment**; otherwise **PENDING** → notification `expense.pending` to the approvers. **Nobody approves or rejects their own entry** (422 `self_approval`, like leave and discounts). Approve / reject (P7.EXP.05 / 06, `expense.approve` for the row's branch; company-wide → company scope) only from PENDING (already in the requested state → 200; otherwise 409 `invalid_transition`); reject needs `reason` and writes `status` 3, `rejection_reason` **and `approved_by_user_id` / `approved_at` = the rejecter and the time of the decision** (DB `expenses_status_fields_chk` requires both columns for status 3 — they mean "decided by / at"; the DTO fields `approved_by` / `approved_at` are labelled *Decided by* on a rejected row — independent review R2-4). - **Edit** (P7.EXP.04) only while **PENDING**, by the requester (self) or `expense.update` (D-FIN-03); APPROVED → 423 `locked` (`correction_path: "delete_and_recreate"`); REJECTED → 409 `invalid_transition` (final — enter a new one). Moving a row between branches / company-wide needs the code for both targets.
- **Delete** (P7.EXP.07 — soft, `{ reason }`, the word is "Delete", never "Void" — D-FIN-03): **manual** rows: the requester withdraws their own PENDING row (self), anyone else needs `expense.delete`; **source 4 PURCHASE** (owner **D3** — a wrong posted purchase): `expense.delete` through a **company scope** (the Admin posts purchases — Part 6 D2) → the replacement is a **manual** expense in category PRODUCT_PURCHASE; other automatic sources → 423 `locked` with `correction_path` = `cancel_cash_out` (2), `payroll_reopen` (3), `cash_return` (5 — the conversion stays; a return reverses it) or `cancel_cash_return` (6). Already deleted → 200. Deleted rows leave the P&L (DB index `expenses_pnl`).
- **Automatic rows** (status 2 APPROVED — DB CHECK; the **🔒 F-P7-04 carve-out** from owner E4 — P7-RULE-09: E4 governs manual entries, an automatic row records something that has already happened and is controlled at its source — the closing for cash outs, `purchase.post` for purchases, finalize for payroll) are written only through the functions this part owns: **`Expenses.createAuto({ source: 4, purchase_id, branch_id, amount, expense_date, actor })`** (Part 6 P6-RULE-08 post — one row per purchase × branch with subtotal > 0, `expenses_one_per_purchase_br`; this function sets category PRODUCT_PURCHASE, status APPROVED, requested / approved by = the actor and the description `"Purchase <invoice_reference> — <supplier>"`); **`Expenses.postPayroll(run, actor)`** (Part 5 P5-RULE-09 finalize — one row per `payroll_entry_branch_allocations` row, source 3, category SALARY, amount = `allocated_gross_amount` (Gross — 🔒 D-FIN-04 / REC-16), `expense_date` = period end); **`Expenses.removePayroll(run, actor, reason)`** (Part 5 P5-RULE-09 reopen — takes that run's source-3 rows out of the books; **🔒 owner 02/Oct/2026 — OPEN-40 OK, (a) = B**) = **soft delete** (`deleted_at`, `deleted_by_user_id` = actor, `deletion_reason` = "Payroll reopened — <reason>") with DB Part 7 **v1.2** making `expenses.payroll_entry_branch_allocation_id` `ON DELETE SET NULL` and `expenses_source_refs_chk` accept a NULL allocation on source 3 only when `deleted_at IS NOT NULL`, so Part 5 can then delete the allocations (🔒 F-P5-09) and the next finalize posts fresh rows (`expenses_one_per_allocation … WHERE deleted_at IS NULL`) — no hard delete, 🔒 D-DAT-05 holds. A row soft-deleted this way has lost its allocation link, so where it is still returned (P7.EXP.01 with `include_deleted=true`, P7.EXP.02) its `links.payroll_run_id` is `null` and the reopened run is named only in `deletion_reason` and the audit row; the database refuses to un-delete such a row and refuses to delete an allocation whose expense is still live (DB Part 7 v1.2 tests). The API surface is unchanged (Part 5 §13 note 1). The other automatic rows are written by this part's own rules: the cash-out rows (source 2 — P7-RULE-09 / 10), the month-end rows (source 5 — P7-RULE-12) and the reversals (source 6 — P7-RULE-11).
- **Attachments** (D-FIN-03, ADR-014): staging uploads listed in `attachment_ids` are re-pointed to `entity_type = 'expenses'` on create / PATCH through Part 8 **`Attachments.link`** (P8-RULE-03 — 422 `attachment_invalid { attachment_id, reason }`); P7.EXP.08 adds receipts to any non-deleted row (evidence, not money — allowed after approval). **P7-RULE-17 · P&L — `Pnl.compute`.** 🔒 D-FIN-04/05/09, D-PAYR-08, D-COM-02 + owner **E6 / F6 / C1** + research E11 + ADR-015 (live, read-only, one `REPEATABLE READ READ ONLY` transaction, 15 s timeout, `generated_at`). `GET /v1/pnl?month=YYYY-MM&branch_id=…` (P7.PNL.01, `pnl.view`):

- **Completeness notes** (never block the report) — each is a `notes[]` code with its field in `completeness`: `days_not_closed { count }` ⇔ `completeness.days_not_closed` (P7-RULE-03) · **`payroll_not_finalized`** ⇔ `completeness.payroll_finalized = false` (no FINALIZED / PUBLISHED / PAID run covers the month — the note is present exactly when the field is false) · `pending_expenses { count, amount }` ⇔ `completeness.pending_expenses` · `pending_incomes { count, amount }` ⇔ `completeness.pending_incomes` · `outstanding_must_return { amount }` ⇔ `completeness.outstanding_must_return_amount`. - A future month → 422 `date_in_future`. Report ⑥ (Part 8) and the dashboard P&L tile use `Pnl.compute` with the same code (`pnl.view` — contract 13).

**P7-RULE-18 · Idempotency and concurrency.** 🔒 D-VIS-10 + contract 15 (API-IDEM-01 v1.5) + G (d). **`Idempotency-Key` required** on P7.CSO.03 (cash outs), P7.CRT.02 (cash returns), P7.EXP.03 (expenses), P7.INC.03 (manual incomes) — the value is stored in the row's `client_request_id` (unique); missing → 400 `idempotency_key_required`; concurrent duplicate → 409 `idempotency_in_progress`. **By state, no key:** save, close, approve, reject, delete, cancel (repeat → 200 current state; a move that is no longer possible → 409 `invalid_transition`). **Reopen is the listed exception** — also by state and without a key, but a repeat answers 409 `invalid_transition` (P7-RULE-07 — review R2-20). `expected_updated_at` on master records, expenses, incomes and the closing draft (409 `conflict`); cash outs / returns have no `updated_at` → row locks. Lock order in this part = the one shared order (P7-RULE-02 — review R1-8): **day lock (advisory — shared for writers, exclusive and first statement for close / reopen) → payroll lock where a Part 5 function takes one → cash out / cash return / expense / income row (`FOR UPDATE`) → closing row**; everything READ COMMITTED with the checks after the locks. A writer never holds a row while it waits for the day lock, and the closer holds only the day lock and the closing row — so close and writers never deadlock (same order as Part 4 P4-RULE-10).
