## Goals / Non-Goals

**Goals**

- A person in `users` signs in with Google or an e-mail code, stays signed in, and is signed out the moment the session is revoked or the account stops being active.
- Every endpoint is closed unless its declaration and the caller's grants open it; the 403 / 404 / `company_scope_required` answers are the locked ones and are tested per data level.
- The permission catalogue, the seed roles and the development fixture exist, so every later change has people, branches and grants to test with.
- The audit writer and the idempotency helper exist and are tested once, so the money changes only supply their own fields.

**Non-Goals** — listed with the owning change in `proposal.md` → Non-goals. In short: no shell / iOS-PWA Google hand-off, no devices screen, no employee / role / branch forms or lists, no settings store or maintenance mode, no realtime push, no notifications, no audit log screen.

### D2. Guard pipeline — bounded by P1-RULE-04, API-AUTH-02, ADR-005 action item 1

Three global guards, registered in this order:

1. **`CsrfGuard`** — for `POST` / `PATCH` / `PUT` / `DELETE` on any route that is not under `/v1/public/` and not `@Internal()`: header `X-Requested-With` must equal `point-app`; `Origin` must equal `APP_ORIGIN`; when `Origin` is absent the origin of `Referer` must equal it; when both are absent the request is refused. Failure → 403 `csrf`. It runs first so that a forged request is refused before any session or database work.
2. **`SessionGuard`** — skipped for `@Public()` and `@Internal()` routes. Steps of P1-RULE-04: cookie → `SessionService.resolve` (one query: session ⨝ user ⨝ employee by `token_hash`) → `revoked_at` → `users.status` → `employees.status`. Fills `RequestContext`. Then the **maintenance step** of P1-RULE-04 through the port `MaintenanceGate.assertOpen(ctx)`: the implementation of this change always passes (`system.maintenance` cannot be written before P1.SYS.03 exists); `add-settings-store` replaces it. The position in the order is fixed now so that the later change adds no guard.
3. **`AccessGuard`** — reads the route's one access declaration (D11). A route without one is refused — the run-time half of the scaffold's lint rule.

### D3. One transaction per business action, opened by the service — bounded by API-AUD-01, CG-DB-03, CG-DB-06, CG-API-01, scaffold D4.8

- **The service opens the transaction.** A service method that changes data calls `TransactionRunner.run(async (tx) => …)` once — one business action, one transaction, READ COMMITTED. There is no transaction interceptor and no transaction in a controller. `$transaction` stays callable only in `common/database` (scaffold lint). A read that changes nothing opens no transaction.
- **Request context.** The runner writes `SELECT set_config('app.user_id', $1, true), set_config('app.session_id', $2, true), set_config('app.request_id', $3, true)` as its first statement (the parameterised form of `SET LOCAL`); empty string for user and session before sign-in — the Part 8 trigger turns an empty value into NULL. API-AUD-01 says "each request runs in a transaction"; the reading used is "each transaction of a request carries the three settings" (proposal → Recorded readings).
- **Outcomes that must be kept although the request is refused.** A wrong code has to leave the incremented counter, the lock and the `login.failed` / `login.locked` rows behind although the answer is 401. The auth service therefore does not throw inside `run()` for an expected refusal: the work returns an outcome (`{ kind: 'ok' | 'invalid' | 'locked', … }`), `run()` resolves — the transaction is committed — and the service method returns that outcome. The controller passes a refused outcome to the one shared mapper `toProblem(outcome)`, which raises the `ProblemException`; the controller makes no business decision (CG-API-01). The Google callback uses the same pattern (commit the `login.failed` row, then redirect). Only unexpected errors roll back.
- **Jobs and events.** A job is enqueued inside the transaction (`Jobs.send(tx, …)` — pg-boss's `db` option bound to the Prisma `tx`), so a rolled-back transaction leaves no job. In-process events (`auth.session_created`, `auth.session_revoked`) are collected during `run()` and emitted by the runner after commit (ADR-001 rule 1). Nothing subscribes in this change (D19).
- **Audit rows** are written by the runner just before commit (D12).
- No `lock_timeout` and no retry are used in this change (system-design §3.5 allows them only for the receipt counter).

### D4. E-mail code — bounded by P1-RULE-03, D-AUTH-04, DB Part 1b

- **Generation:** 8 digits from `crypto.randomInt(0, 100_000_000)`, left-padded with zeros (a code may start with 0).
- **Hash:** `code_hash = hex(HMAC-SHA256(OTP_HMAC_SECRET, user_id + ':' + code))`; comparison with `timingSafeEqual`.
- **Request — the answer does not wait for the look-up.** The handler validates the body, applies the two limits (D5) and answers 202; the service starts the issuing work with `BackgroundTasks.run` and does not await it. The work is the same call for every address: look the address up → not eligible → end; eligible → one transaction: lock the `users` row → set `consumed_at = now()` on every earlier unconsumed row of the user ("older rows are invalidated") → insert the new row with `expires_at = created_at + interval '5 minutes'` and `request_ip` → `Mail.enqueue(tx, …)`. Because the response is sent before any address-dependent statement runs, its time is the same for a staff address and an unknown one. If the process stops between the answer and the work, no code is sent and the person asks again after 60 seconds. Tests wait with `BackgroundTasks.drain()`.
- **Verify** (one transaction): lock the `users` row → if `login_locked_until > now()` → outcome `locked` (the code is not examined; count and lock end unchanged) → read the newest `login_otps` row of the user → success only when it is unconsumed, `now() < expires_at` and the hash matches.
- **What counts as a failure:** every verify for an eligible user, made while no lock is running, that does not succeed — wrong, expired, consumed, superseded, or no code at all. It adds 1 to `failed_login_count`; when the count is then 5 or more, `login_locked_until = now() + interval '20 minutes'`. The counter is reset only by a successful verify (P1-RULE-03 "counter reset on success") — so a wrong code after a lock has ended locks again at once.
- **Unknown or ineligible address:** always `otp_invalid` (the literal text of P1-RULE-03); no counter exists for it. A dummy HMAC is computed so that the response time does not differ. A locked existing address answers `login_locked` while an unknown address keeps answering `otp_invalid` — the literal texts stay (owner answer S10, P1-RULE-03 v1.6 note); the per-IP verify cap of D5 bounds how many addresses one machine can probe.
- **Lock and Google:** `login_locked_until` guards code guessing only. The Google callback neither checks nor changes `failed_login_count` / `login_locked_until` — P1.AUTH.04 names no lock, and a locked-out user (or the victim of someone else's five guesses) can still sign in with Google.
- **Schema:** `email` trimmed, lower-cased, e-mail format, ≤ 255 characters (OpenAPI); `code` `^[0-9]{8}$`; `device_label` ≤ 255. A schema failure is 400 `validation` and never touches the counter. Field codes inside `errors[]` (API-ERR-03 v1.6, Part 1 v1.6 §11b): the two catalogue codes the schemas name — `email_invalid` for the address format, `otp_format` for the code pattern, declared the way `add-shared-ui-components` D9 describes — and otherwise the Zod issue name unchanged (`too_big` with `params.maximum = 255` for an address of 256 characters, `invalid_type` for a missing member). `required` is a client-only message key the form shows for an empty field; the API never returns it.

### D5. Rate limits and how tests live with them — bounded by API-LIM-02, system-design §3.2 ("rate limiting state lives in-process")

- `RateLimiter` is an in-process sliding-window store with an injected clock (single API instance — ADR-008 revisit trigger for a second instance). Buckets used here: `otp:ip` (limit 10, window 3,600 s, key = client IP) and `otp:email` (limit 1, window 60 s, key = `HMAC(AUDIT_HASH_SECRET, lower(email))`).
- Order in P1.AUTH.01: schema → `otp:ip` → `otp:email` → answer 202 → issuing work. A request counts in a bucket only when it is accepted (answered 202), so a throttled retry does not extend the wait.
- The 60-second rule is applied to the address string for every address, and only from the in-process store — there is no second check against `login_otps`, because after an API restart that check would answer 429 for a staff address and 202 for an unknown one. A restart resets the cooldown for every address alike; an integration test restarts the limiter and asserts the same status for both kinds.
- `retry_after` = whole seconds, rounded up, until the oldest counted hit leaves the window; also sent as the `Retry-After` header (OpenAPI Part 1).
- Client IP = the address Caddy forwards (`X-Forwarded-For`, exactly one trusted hop — `TRUSTED_PROXY_HOPS=1`); never a value the client can set past the proxy.
- **Verify cap (API-LIM-02 v1.6, P1-RULE-03 v1.6):** bucket `otp_verify:ip`, limit 10, window 3,600 s, key = client IP. Order in P1.AUTH.02: schema → `otp_verify:ip` → the verify transaction of D4. The bucket is checked and counted before any look-up, counter change or audit write; a refused attempt (429 `rate_limited` with `retry_after` and `Retry-After`) is not counted, so the tenth attempt of the hour is processed and the eleventh is refused. Every processed attempt counts, whatever its outcome and whichever address it names. A body that fails the schema is answered 400 before the bucket and is not an attempt.
- **Tests stay inside the limits — no override exists in the shipped build.**
  - *Unit and integration tests* build the application with a fake clock and a fresh limiter per test; boundary cases move the clock, they never wait.
  - *End-to-end:* each fixture person signs in at most once per spec file and the session is reused through Playwright `storageState`. Spec files are sized so that one file sends at most 8 code requests and 8 verifies (both caps are 10 per hour per IP); the `e2e` job restarts the `api` container between spec files that request codes — the limiter is in-process, so a restart empties it, which is the documented property of D5, not a test hook.
  - *Manual workbook:* the cases are grouped in sections of at most 8 code requests and 8 verifies, each section starts with "restart the `api` container", the lock cases use a person no other section signs in (Ko Htet, Ko Thura), and every case that needs a wait states it (60 seconds for a resend, 20 minutes for the lock end, or a fresh section).

### D6. Session, cookie and re-issue — bounded by API-AUTH-01, ADR-005 decision 1, DB Part 1b

- **Token:** 32 bytes from `crypto.randomBytes`, base64url without padding (43 characters). `token_hash = hex(sha256(token))`. A token is created only by the server at a successful sign-in; a `point_session` value sent with a sign-in request is never adopted.
- **Same browser signs in again (P1-RULE-15):** the verify and callback controllers hand the request's `point_session` value to the sign-in service, which passes it to `SessionService.create` as `replacesToken`. Inside the sign-in transaction, after the new session row is written: resolve the token; when its session is still valid (row found, `revoked_at IS NULL`, user and employee active — the test of P1-RULE-04) set `revoked_at = now()`, `revoke_reason = 1` and `revoked_by_user_id` = the user who signed in, emit `session.revoked` (D12) and collect `auth.session_revoked`. An unknown or already revoked token is ignored; a failed sign-in never reaches this step. The cookie value is only looked up, never adopted (session fixation — threat model). The hand-off of P1.AUTH.06 calls the same function when `add-android-shell` builds it.
- **Cookie options in one place** (`modules/auth/session-cookie.ts`): `httpOnly`, `secure`, `sameSite: 'lax'`, `path: '/'`, `maxAge: 34_560_000`, no `domain`. `SESSION_COOKIE_SECURE` defaults to `true`; `false` is accepted only when `APP_ENV` is `development` or `test` (start-up check) — never in `staging` or `production` (API-AUTH-01 lists `Secure` without a condition). The dev stack is HTTPS anyway (scaffold D12).
- **Device label:** body `device_label` when sent, else derived from `User-Agent` as `<platform> · <browser>` (e.g. `Android · Chrome`); `X-Client` (`web`, `android-shell`, `windows-shell`) is kept in the label when it is a shell (API-AUD-02).
- **`last_seen_at`:** written when `now − last_seen_at ≥ 5 minutes`, by a single `UPDATE … WHERE id = $1 AND last_seen_at <= $2` on the plain connection (no business action, no audit; lost races are harmless).
- **Re-issue without a new column.** The session row has no "cookie issued at", so the rule is written against the row: `period(t) = floor((t − created_at) / 30 days)`. On a successful request, when `period(now) > period(last_seen_at)` the response carries `Set-Cookie` with the same token and a fresh `Max-Age`, and `last_seen_at` is written even inside the 5-minute throttle. Effect: one re-issue in each 30-day period in which the session is used; a cookie reaches the 400-day browser cap only after about 370 days without a single request. The token is not rotated: two parallel requests would otherwise invalidate each other. (API-AUTH-01 words the rule as "after it is 30 days old" — proposal → Recorded readings.)

### D7. Google sign-in (browser) — bounded by P1.AUTH.03 / 04, ADR-005, D-AUTH-08

- Library `openid-client`; issuer from `GOOGLE_ISSUER` (default `https://accounts.google.com`), client from `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`; redirect URI `<APP_ORIGIN>/api/v1/auth/google/callback`; scope `openid email`.
- **Start:** generate `state` (32 bytes), PKCE verifier and `nonce`; keep `{ code_verifier, nonce, return_to, created_at }` in an in-process store keyed by `sha256(state)` (10-minute TTL, single use — the same single-instance trade-off ADR-005 makes for the hand-off store); set cookie `point_oauth_state=<state>` (`HttpOnly; Secure; SameSite=Lax; Path=/api/v1/auth/google; Max-Age=600`). An API restart loses pending sign-ins; the user taps the button again.
- **`return_to`:** kept only when it matches `^/[^/].*$` (OpenAPI), contains no backslash or control character and `new URL(return_to, APP_ORIGIN).origin === APP_ORIGIN`; otherwise dropped. The callback redirects to the stored value or `/` — never to a value taken from the callback's own query.
- **Callback:** cookie state must equal the query `state` and exist in the store → code exchange with the PKCE verifier → ID token checked (signature, `iss`, `aud`, `exp`, `nonce`) → `email_verified` must be `true` → identity rules of the spec → one transaction: activation, `SessionService.create`, audit → 302. The state cookie is cleared in every outcome.
- **One failure page.** Every failure — state mismatch, Google error or cancel, unverified e-mail, no matching user, another `sub`, ineligible user — redirects to `/login?error=google_not_linked` (the only value Part 1 defines) and is audited `login.failed` with an internal `cause`. The screen shows one neutral message, so the redirect reveals nothing about which accounts exist.
- **`client` and `challenge` do not exist yet.** The query schema of P1.AUTH.03 has only `return_to` in this change; the hand-off parameters arrive, as locked, with P1.AUTH.06 in `add-android-shell`. Nothing answers 400 for them: an unknown query parameter is ignored like on any other endpoint, and the flow is the browser flow.
- **Logs:** the request log prints the route pattern without the query string, so the callback's `code` and `state` never reach a log line (CG-SEC-06); the redaction test of task 2.6 includes both.
- **Tests:** integration tests run against a stub OIDC issuer started by the test harness (discovery, JWKS, token endpoint; `GOOGLE_ISSUER` points at it). It is an identity-provider double, not a login endpoint of the app. Google itself is tested by hand (fixtures §7).
- **Manual Google recipe.** Google accepts redirect addresses only on a public top-level domain or `localhost` (to be confirmed when the OAuth client is created), and the scaffold's `http://localhost:3000` alias is read-only by design (scaffold D12). The manual test therefore uses its own dev override `docker-compose.google.yml`: `APP_ORIGIN=http://localhost:3000`; the Caddy block for the staff host is that address itself — the alias block and its `header_up Host` line are removed in this override, so `proxy.ts` sees the host of `APP_ORIGIN`; Chrome only (it keeps `Secure` cookies on `localhost`; `SESSION_COOKIE_SECURE` stays `true`); a database with the base seed only and a first admin created for a real Google address (D10).

### D8. Mail and the `email.send` job — bounded by ADR-007 decision 1, ADR-002

- `MailModule`: port `MailTransport.send({ to, subject, text, html })`; `MailpitTransport` (SMTP to `mailpit:1025`) and `ResendTransport` (HTTP API). `MAIL_TRANSPORT` = `mailpit` | `resend`. Start-up check: `APP_ENV=production` requires `resend`; any other environment refuses `resend` unless `MAIL_ALLOW_REAL=true` — a development machine cannot e-mail a real person by accident.
- Job `email.send`: 3 retries with backoff (ADR-002). Payload `{ template, to, locale, expires_at, params_enc }`. The handler sends nothing and completes when `now ≥ expires_at`. `Mail.enqueue(tx, …)` sends the job inside the caller's transaction (D3).
- **The code must not sit readable in the job table.** pg-boss stores job data as JSON in PostgreSQL, and D-AUTH-04 allows the code to be stored only as a hash. `params_enc` is therefore the template parameters encrypted with AES-256-GCM under `MAIL_PAYLOAD_KEY`. Retention stays as ADR-002 action item 5 sets it for every queue (completed jobs archived after 7 days, deleted after 30) — the stored payload is unreadable without the key, and the jobs panel (P1.SYS.05, later) keeps its `last_success_at`.
- Templates in `packages/i18n/messages/{my,en}/auth.json` (`auth.email.otp.subject`, `auth.email.otp.body`): the shop name, the code **ungrouped on a line of its own** (the test helper matches exactly 8 consecutive digits), the 5-minute validity; plain text + minimal HTML; no link, no digit in the subject. Locale = `users.ui_language` → system default 1 MY (AD-L10N-06). The texts are those of the brief's copy table (owner answer S18); the owner reads and corrects them in the brief or the pull request — keys and behaviour do not change.
- Daily-cap guard of ADR-007 (queue invites over 100 / day) belongs to the invite e-mail — `add-employee-management`.

### D9. Jobs — bounded by ADR-002

- **Install is an owner-role step of the one migrate entry point.** `db/scripts/migrate.mjs` gets a second step after `prisma migrate deploy`: install pg-boss's schema `pgboss` and its tables, create the three queues of this change (`email.send`, `auth.cleanup`, `sync.code_tables`) — queue creation is DDL in the pinned pg-boss — and grant schema usage and table privileges to `point_app`. Because `pnpm db:migrate`, the Compose `migrate` service, the CI jobs `db`, `integration` and `e2e` and the deploy runbook all call that script (scaffold D4.6), the step is picked up everywhere at once. A later change that adds a queue adds it to the same step. The API starts pg-boss with schema creation and migration switched off, so `point_app` needs no `CREATE` right. No table is added to `public` (still 91).
- `JobsModule` runs the workers inside the API process when `JOBS_IN_API=true` (the default — ADR-002's switch for moving workers out later).
- Jobs registered here: `email.send` (on demand) · `auth.cleanup` (cron hourly: `DELETE FROM login_otps WHERE expires_at < now()` — ADR-002 "deletes expired `login_otps` rows"; not a transactional row) · `sync.code_tables` (sent once at every API start with a singleton key).
- Handler unit tests call the handlers directly; one integration test goes through a real pg-boss and proves that a job sent inside a rolled-back transaction does not exist.

### D10. Permission catalogue, sync, seed roles, first admin — bounded by D-ROLE-08, D-ROLE-09, P1-RULE-12, ADR-011

- **File:** `packages/shared/definitions/permissions.json` (the scaffold created it as `[]`; ADR-011 action item 1 calls it `packages/shared/permissions.json` — the same file). A Zod schema validates it in a unit test. `packages/shared/src/permissions/catalogue.ts` exports `PERMISSIONS`, the union type `PermissionCode`, `permissionLevel(code)` and binds `can = createCan(PERMISSIONS)` from `add-shared-ui-components` D7 (first merge creates the folder, second imports).

### D11. Access declarations and the guard's decision table — bounded by API-PERM-02 / 03 / 04 / 07, ADR-012, P1-RULE-05, P1-RULE-11

```ts
@Can(code, { level: 'company' | 'shared' | 'private' })
@Can(code, { branch: '<path>' | '<path>?', empty?: 'private', orSelf?: '<path>' | '<resolver name>', scopeError?: 'forbidden' | 'out_of_scope' })
@Can(code, { target: 'employee:<param>', orSelf?: … })
@CanView(module, { level?: 'shared' | 'private', branch?: '<path>', target?: 'employee:<param>', orSelf?: '<path>' | '<resolver name>' })
@Staff()   @Self()   @Public()   @Internal()
```

Paths: `body.<field>`, `query.<field>`, `params.<field>`, `…[]` (every element) and `params.<id>→entity.<field>`. An entity path needs a loader registered by the owning module: `TargetResolvers.register('<route key>', (id) => Promise<{ branch_ids, match: 'all' | 'any', …orSelf fields } | null>)`. The `employee` target is the P1-RULE-11 target set, registered by `people`: `branch_ids` = the employee's active assignments, `match: 'any'` (an overlap is enough), and an empty set is reachable at company scope only.

`GrantSet` (built once per request from three small tables — ADR-005 "no cache at this scale"): `has(code)`, `isCompany(code)`, `branches(code)`, `covers(code, branchId)`, `anyOf(module)`, `branchesOfModule(module)`, `readScope: { all: boolean, branchIds: Set }`. A branch assignment is active when `effective_from ≤ today ≤ coalesce(effective_to, today)` on the Myanmar calendar date; an archived permission and a revoked role assignment contribute nothing.

`decide(declaration, grantSet, target, method)` is a pure function that returns `{ allow: true }` or `{ allow: false, status, code, required? }`. Order (first match wins):

| # | Condition | Result |
| --- | --- | --- |
| 1 | caller holds no `code`, and `orSelf` matches — the path value (in the request or in the loaded target) equals the caller's employee id or user id, or the named resolver returns true | allow |
| 2 | caller holds no `code` (no `orSelf`, no match, or the target does not exist) | 403 `forbidden`, `context.required = code` — the same answer whether or not the target exists |
| 3 | `level: 'company'` or `'private'` and no company-scope grant of `code` | 403 `company_scope_required` |
| 4 | `level: 'shared'` | allow |
| 5 | optional path is empty | company-master target → as row 3 (also with `empty: 'private'`) |
| 6 | entity or employee target: not found | 404 `not_found` |
| 7 | `orSelf` matches | allow |
| 8 | target not covered — `match: 'all'`: some branch uncovered; `match: 'any'`: no branch covered, or the set is empty and the grant is not company scope — on a `GET` | 404 `not_found` |
| 9 | the same on any other method | 403 with the declaration's `scopeError` — `forbidden` unless the declaration says `out_of_scope` |
| 10 | otherwise | allow |

- **Row 9 (API-PERM-03 v1.6).** A caller who holds the code but not for the target branch gets 403 `forbidden` — what every Part 1 declaration returns; `out_of_scope` is returned only where a part's endpoint text names it (Parts 2, 6 and 8 do, for specific endpoints). `decide()` therefore takes the code from the declaration, so a later part can declare `scopeError: 'out_of_scope'` where its endpoint text says so; the constant `out_of_scope` is added now and used by no endpoint of this change.
- `@CanView(module)`: "holds the code" = `anyOf(module)`; `context.required = "<module>.view"`; without `branch` / `target` the handler receives `AccessContext.scope = { all } | { branchIds }` built from `branchesOfModule(module)` and must filter with it (lists never answer 403 to a holder); a `branch_id` filter outside the scope yields an empty page without a query. With `branch` or `target` it is a single-resource read and rows 6–8 apply.
- `@Staff()`: `AccessContext.scope` = the read scope.
- The guard puts the resolved single branch (if exactly one) into `RequestContext.branch_id` for the audit writer (D12).
- A route without a declaration: 401 without a valid session (the session guard runs first), 403 `forbidden` with one.
- **Delivered now, first used later:** the `OrSelfResolvers` registry (`add-walkin-visit-checkout` registers `visit.lineActors` and the others). **Not delivered here** — each arrives with the first endpoint that needs it and extends this table: any-of branch paths written as `a|b` (Part 6), the row filter `{ branch: 'row' }` (Part 8 audit log), the `@Staff()` handler-policy rule (Part 8 attachments / exports), the field-grouped `PATCH` and the write actions of P1-RULE-11 (`add-employee-management`).
- `@Internal()`: `X-Internal-Key` compared with `INTERNAL_OPS_KEY` by `timingSafeEqual`; no endpoint of this change uses it.
- **Fixtures and the build rules.** Fixture codes (`fixture.view`, `fixture.shared_view`, `fixture.private_view`) are not in `permissions.json`; a test-only type augmentation in `apps/api/test/` widens `PermissionCode` for the fixture controllers, and the tests pass their own catalogue to `PermissionCatalogue.sync`. The controller without a declaration (`undeclared.controller.ts`) is listed with the must-fail lint fixtures, which the normal `pnpm lint` run excludes (scaffold D10).

### D12. Audit writer — bounded by API-AUD-01, CG-SEC-10, P1-RULE-10, DB Part 8

- **Three parts, one row.** (1) `@Audited({ actions: […], target?: 'employee' })` on a handler is an interceptor that only registers the audit intent — the actions this endpoint may write — in the request context before the handler runs. (2) The service, inside its `run()`, calls `Audit.emit({ action, entity_type, entity_id, before?, after?, reason? })` for what it did, or `Audit.skip()` when it did nothing — an idempotent replay, an unchanged repeat. Emitting only fills the audit slot of the request context. (3) `TransactionRunner` writes the slot's rows with `source = 1` inside the same transaction, just before commit, and empties the slot. Nobody inserts an `audit_events` row by hand.
- **The check.** When the handler of an `@Audited()` endpoint returns successfully and the intent is still pending — no transaction ran, or the service neither emitted nor skipped — the interceptor raises an internal error (500). Every integration test of such an endpoint therefore fails until the service does one or the other; a dedicated fixture proves the check. An emitted action that the decorator does not declare fails the same way.
- **`branch_id`:** `RequestContext.branch_id` when the guard resolved one branch → else the `branch_id` the service passed with the event when the entity has exactly one → else, for `target: 'employee'`, `PeopleDirectory.primaryBranchId` → else NULL. Primary branch = active assignment with the earliest `effective_from`; ties are broken by `created_at`, then `id`.
- **Deny-list** applied before insert: keys `token`, `token_hash`, `code`, `code_hash`, `google_subject`, `id_token`, `authorization_code`, `state`, and any key ending `_secret` are dropped — a test feeds each key and expects it gone.
- **Sign-in rows** go the same way: P1.AUTH.02 and P1.AUTH.04 carry `@Audited({ actions: ['login.success', 'login.failed', 'login.locked', 'session.revoked'] })` (the last one for a replaced session — P1-RULE-15; the service passes the primary branch of that session's employee with the event), P1.AUTH.05 `@Audited({ actions: ['session.revoked'], target: 'employee' })`. Payloads: `login.success` `{ method, device_label }` (the event carries the new session as `actor_session_id` and the user as actor, because the request context has none yet) · `login.failed` `{ method, email_hash, ip, cause }` with `email_hash = hex(HMAC-SHA256(AUDIT_HASH_SECRET, lower(email)))` and `cause` ∈ `wrong_code`, `expired`, `no_code`, `locked`, `unknown_email`, `ineligible`, `state_mismatch`, `google_error`, `email_unverified`, `no_match`, `subject_mismatch` · `login.locked` `{ until, ip }` · `session.revoked` `{ revoke_reason }`. `entity_type = "users"` for `login.*` (`entity_id` = the user when the address matched one), `"user_sessions"` for `session.revoked`. A verify for an unknown address has no user row to lock, so its transaction contains only the audit row.
- Jobs use `Audit.emitSystem` (`source = 3`, no actor) inside their own `run()`.
- `PATCH /v1/me` carries no `@Audited()` (P1.ME.02: not audited); `GET` is never audited.
- Append-only is not re-implemented: the baseline trigger and the `point_app` grants of the scaffold enforce it.

### D14. Idempotency helper and how it is tested — bounded by API-IDEM-01 / 02, CG-IDEM-02, D-DB-12

- `@Idempotent()` on a handler: validates the header (missing → 400 `idempotency_key_required`; not a UUID → 400 `validation` with `field = "Idempotency-Key"`) and exposes the value through `@IdempotencyKey()`.
- The service calls it as the first statement of its transaction — `this.db.run((tx) => this.idempotency.run(tx, { key, find, same, create }))` (the shape of the CG-IDEM-02 example):
  1. `pg_try_advisory_xact_lock(hashtextextended('idem:' || key, 0))` → false → 409 `idempotency_in_progress`;
  2. `find()` → row found → `same(row)` false → 422 `idempotency_mismatch`; true → `{ replayed: true, row }`, `Audit.skip()` is called, and the response step sends 200 and `Idempotent-Replayed: true`;
  3. not found → `create()`. A unique violation on the endpoint's `client_request_id` index (the last line behind the advisory lock) aborts the transaction, so nothing continues in it: the one error mapper answers 409 `idempotency_in_progress` and the client's retry reaches step 2 and replays (CG-DB-12).
  The identifying fields are whatever `same` compares — each part lists them (API-IDEM-02). This is the algorithm `add-walkin-visit-checkout` D7 describes; that change passes its own `find` / `same` / `create`.
- **No production endpoint is added to exercise it.** The API design contains no endpoint for that purpose, and inventing one would put an unspecified route into production. The contract is tested with a fixture controller (`POST /v1/_fixtures/idempotent-rows`) in `apps/api/test/fixtures/`, registered only in the test application module, writing to table `fixtures.idempotent_rows` that the test set-up creates. The scaffold's unit test "`AppModule` has no route starting with `/v1/_fixtures`" guards against a leak. The in-progress case uses a latch inside the fixture service's transaction. The first real consumer, `POST /v1/visits`, repeats the four outcomes in its own integration tests.
- The same fixture mechanism carries the guard semantics no production endpoint of this change reaches (company write, branch action, entity path, mixed, shared, private, scoped list, undeclared route, `@Internal()`), and the audit branch rule.

The three generated secrets (`OTP_HMAC_SECRET`, `AUDIT_HASH_SECRET`, `MAIL_PAYLOAD_KEY`) must be present and at least 32 bytes; the process refuses to start otherwise. `GOOGLE_CLIENT_SECRET` and `RESEND_API_KEY` are provider secrets and are listed with them in `docs/ops/secrets-rotation.md`.

## Threat model

| Threat | What an attacker tries | Covered by (locked rule → where) |
| --- | --- | --- |
| **Session fixation** | Plant a known session id in the victim's browser before sign-in | API-AUTH-01: the token is created by the server at a successful sign-in only and stored hashed; a client-supplied `point_session` is never adopted; the host-only cookie cannot be set from the public host (ADR-009) → D6; tasks 4.1, 5.8 |
| **Session theft / reuse** | Read the cookie from script or over HTTP; use a database dump | `HttpOnly; Secure; SameSite=Lax`, no `Domain` (API-AUTH-01); only `sha256(token)` at rest (D-AUTH-06); `Secure` can be switched off only in development and test → spec "The session lives in the cookie …"; D6 |
| **Code brute force** | Guess the 8 digits | P1-RULE-03 / API-LIM-02: 5 consecutive failures → 20-minute lock, counted per user under a row lock so parallel guesses cannot exceed 5; the counter is reset only by a success, so every wrong code after a lock locks again; 5-minute expiry; single use; latest code only → D4; tasks 5.1, 5.4, 5.5 |
| **Code flooding / mail bombing** | Request codes for a victim's address in a loop | API-LIM-02: 1 per 60 s per address, 10 per hour per IP → D5; tasks 5.2, 5.3 |
| **Verify flooding** | Send verifies for many addresses from one machine: lock every known staff address every 20 minutes and write unlimited permanent `login.failed` rows | API-LIM-02 (v1.6): 10 verify attempts per hour per IP, counted before any look-up, counter change or audit write; the eleventh answers 429 and writes nothing → spec "Code verify is limited to 10 attempts per hour per IP"; D5; task 5.6 |
| **CSRF** | A page on another origin makes the signed-in browser send a changing request, or signs the victim in to the attacker's account | API-AUTH-02: `X-Requested-With: point-app` + `Origin` = app origin on every changing request, sign-in endpoints included; no CORS (ADR-009), so the header cannot be sent cross-site; Google callback is a GET bound to the browser by the state cookie → D2, D7; task 4.4 |
| **Open redirect on the Google return** | Send a victim a start link whose `return_to` leads to a phishing page after a real sign-in | P1.AUTH.03 "restricted to same-origin paths": pattern, no backslash, origin comparison; value stored server-side with the state, never read from the callback query; the client applies the same rule → D7, D17; tasks 5.13, 7.2 |
| **Login CSRF / code injection on the Google callback** | Replay or forge the callback | `state` cookie + single-use server entry, PKCE, `nonce`, ID-token signature / `aud` / `iss` / `exp`, `email_verified` → D7; tasks 5.14, 5.15 |
| **Account takeover through Google** | Create a Google account that carries a staff address | D-AUTH-08: the address must match on the first sign-in and be verified by Google; afterwards only the stored `sub` is accepted → spec "A Google account is tied to the user …" |
| **User enumeration** | Learn which addresses are staff | D-AUTH-04 / P1-RULE-03: same 202 for every address, sent before the address is looked up (D4); cooldown from one store for every address, also after a restart (D5); `otp_invalid` for unknown / wrong / expired with identical members; one Google failure page (D7); dummy HMAC for timing (D4). **Accepted by the owner (S10, P1-RULE-03 v1.6 note):** `login_locked` is answered only for a real account; one machine can test at most 10 guesses per hour (D5) |
| **Secrets in logs, audit rows or the job table** | Read a code or token from a log line, an audit row or `pgboss.job` | API-AUD-01 last sentence, D-AUTH-04 / 06, CG-SEC-06: audit deny-list (D12), logger redaction and no query string in the request log (D7), encrypted mail payload (D8), e-mail address only as HMAC in `login.failed` (P1-RULE-10) → spec "Codes, tokens and their hashes never reach …"; tasks 2.6, 2.9, 5.11 |
| **Lock-out of a colleague** | Type five wrong codes for someone else's address | Bounded, not removed: the lock lasts 20 minutes and blocks code sign-in only; Google sign-in still works (D4); existing sessions are untouched. The per-IP verify cap (API-LIM-02 v1.6) limits one machine to two locked colleagues per hour (10 attempts ÷ 5) |
| **Privilege through a forgotten declaration** | Call an endpoint nobody guarded | API-PERM-02: lint rule (scaffold) + run-time default deny (D2) → spec "Every endpoint's access declaration is enforced …" |
| **A second admin minted from the server shell** | Run the first-admin command again | P1-RULE-14: the command succeeds only while no active company admin exists (an invited one counts); the audit rows name the operating-system user → spec "The first company admin of an environment …"; D10; tasks 3.9, 3.10 |
| **A stolen or planted cookie kept alive by a new sign-in** | Rely on the browser's old session staying valid after someone signs in again | P1-RULE-15: the session of the cookie that came with a successful sign-in is revoked in the same transaction; the cookie value is only looked up, never adopted → D6; task 5.18 |
| **Forged client IP** | Evade the per-IP limit with a made-up `X-Forwarded-For` | D5: only the hop Caddy adds is trusted; unit test with a spoofed header (task 2.7) |
| **Test routes in production** | Reach a fixture endpoint | scaffold D8: fixtures live under `test/`, excluded from the build, unit test on `AppModule` routes → task 9.2 |

## Risks / Trade-offs

| Risk | Mitigation and the test that covers it |
| --- | --- |
| Failed sign-in writes are rolled back with the 401 | The service returns the outcome after `run()` resolved (D3); integration test: wrong code → counter + `login.failed` row present after the response |
| An action endpoint forgets its audit row | `@Audited()` intent check (D12): the request fails with 500 in every integration test until the service emits or skips; fixture test of the check itself |
| Parallel wrong codes slip past the fifth-failure lock | `users` row lock in verify (D4); integration test fires 10 parallel wrong codes → exactly 5 `login.failed` with `cause = wrong_code`, 5 with `cause = locked`, one `login.locked`, `failed_login_count = 5` |
| The un-awaited issuing work of a code request fails silently | `BackgroundTasks` logs every rejection with the request id and is awaited at shutdown; integration test makes the mail transport throw and finds the error log and the 202 |
| In-process stores (rate limiter, Google state) are lost on restart and do not work with two API instances | Accepted for the single instance (ADR-005, ADR-008); a start-up log line names the stores; revisit with ADR-008's trigger |
| The rate limits throttle the test suites | D5: fake clock in integration tests, `storageState` and a container restart between e2e spec files, workbook sections; no override in the build |
| Re-issue rule misfires (never, or on every request) | Unit tests of `period()` at 29 d, exactly 30 d, 30 d + 1 min, 59 d 23 h, 60 d; integration test of the spec scenarios with a fake clock |
| A guard row in D11 is wrong for one level | `decide()` is a pure function with a table-driven unit test (one case per row and per level) before the guard is wired; fixture integration tests repeat the spec scenarios |
| A list handler forgets to apply `AccessContext.scope` | The repository method takes `scope` as a required parameter; the fixture list test asserts 3 / 6 / 0 rows per caller |
| Seed drifts from `spec-fixtures.md` | One fixture table in code; a unit test asserts the nine codes and e-mail addresses, the three branch codes and the prices 6,000 / 7,000 / 8,000 / 10,000 / 3,000 / 2,000 |
| Fixture seed reaches production | `APP_ENV` check + fixtures excluded from the image; unit test of the refusal; CI checks the production image has no `db/seed/fixtures` |
| The pg-boss schema is missing in one environment | One migrate entry point (D9); the API refuses to start jobs and logs a fatal line when schema `pgboss` is absent; job `e2e` runs the same script as production |
| pg-boss's API differs from what D8 / D9 assume (queue DDL, `db` executor, retention options) | Task 2.8 starts by checking the three points against the pinned version and records the result in `VERSIONS.md`; the rule "send inside the transaction, no job after a rollback" is asserted by an integration test, whatever the option is called |
| The mail payload key is lost or rotated | Jobs older than 5 minutes are useless anyway; a decrypt failure completes the job with a warning log |
| Google cannot be automated | Stub issuer for every rule; manual checklist with a real account on the `localhost` override (task 8.9); the e-mail code stays the fallback path |
| Web group blocked by `add-shared-ui-components` | D17: only its pull request 1 is a hard prerequisite; primitives + swap task otherwise |
| The change is larger than one 1–3 day change | Accepted by the owner as an exception (S2, D-PLT-20 v5.2.17 note); three pull requests in task order (groups 1–3 definitions, platform services, catalogue and seeds · 4–6 sessions, guards, sign-in, `/me`, reads · 7–9 web, e2e, verification), each reviewable alone; pull requests 1 and 2 merge on CI + review, the workbook runs on pull request 3 (CG-GIT-05) |
| `email.send` fails in the pilot (domain not verified) | Expected and documented (D-ARC-02): the pilot signs in with Google in the browser tab; jobs expire after 5 minutes and are not retried past expiry |

## Migration Plan

1. `db/scripts/migrate.mjs` gains its second step (D9): after `prisma migrate deploy`, install schema `pgboss`, create the three queues and grant them to `point_app`, all as the owner role. No change to `docs/db/`, no table in `public`. Nothing else has to change for the Compose `migrate` service, the CI jobs and the runbook — they already call the script.
2. Order inside a release: `node db/scripts/migrate.mjs` (migrations + pg-boss install) → API start → `sync.code_tables` (21 codes, company row, three seed roles on the first run) → the first-admin command once per environment (P1-RULE-14; it needs the seed Admin role, so it runs after the first API start).
3. CI: job `integration` gets a `mailpit` service container (SMTP 1025, API 8025) in its one `services:` block; job `e2e` restarts the `api` container between spec files that request codes (D5).
4. Development: `pnpm db:seed` after `pnpm db:migrate`. The scaffold's `e2e/smoke.spec.ts` and `e2e/edge.spec.ts` assertions that the modified requirements replace (`[data-testid="staff-placeholder"]`; `GET /v1/health` on the staff host → 404 HTML) are rewritten in the pull request that replaces the placeholder.
5. Secrets (`OTP_HMAC_SECRET`, `AUDIT_HASH_SECRET`, `MAIL_PAYLOAD_KEY`, Google client) are added to `docs/ops/secrets-rotation.md`. Rotating `OTP_HMAC_SECRET` invalidates codes in flight (at most 5 minutes); rotating `AUDIT_HASH_SECRET` breaks comparison of older `email_hash` values and is done only on compromise.
6. Archive order: `add-repo-scaffold` is archived first — the two `MODIFIED` requirements of this change's `platform-runtime` delta need the archived spec to exist.
7. Rollback = revert the pull requests. The rows the base seed created (permissions, three roles, the company) are harmless to an older build; sessions created meanwhile are simply unused.
